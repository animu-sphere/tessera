# Product vision

Tessera is a deterministic GPU-native UI runtime for humans and agents. It is backend-neutral, declarative, deterministic, inspectable, replayable, and operable by people and by machines, for editors, games, DCC tools, and visualization. Its value is not a fast renderer alone: one runtime contract carries UI, meaning, operation, verification, and automation, so the loop of building, inspecting, semantically operating, replaying, verifying, and optimizing UI stays inside the runtime. The combination of [semantic projection](../architecture/semantics.md), the [command registry](../architecture/commands.md), [inspection](../architecture/inspection.md), [replay](../architecture/replay.md), snapshots, and [UI invariants](../architecture/inspection.md#proposed-ui-invariants) is the core of that contract. Tessera does not aim to replace Qt completely or reimplement the Web.

The developer-facing goal is to make ordinary UI easy without making advanced UI impossible. Application authors should primarily use an ergonomic authoring API and a reusable component/widget library. Predictable composition, simple state and derived values, commands, styling and practical text editing should make it possible to turn an application idea into working UI without understanding reactive graph classes, mounting machinery, reconciliation or renderer internals. The deterministic runtime supports that experience as the common execution foundation.

Real applications guide authoring and widget priorities. A small Settings editor, asset browser, UI inspector or OpenUSD utility can reveal more useful requirements than speculative subsystem expansion. Examples should be copyable starting points, and user documentation should begin with a first application before internal architecture; the [Settings consumer](../integrations/settings-app.md) and [authoring proposal](../proposals/cpp-authoring.md) define those design inputs without claiming usable APIs.

The [use cases](use-cases.md) describe intended consumers; [principles](principles.md) and [non-goals](non-goals.md) constrain product choices. Implementation evidence belongs only to the [support matrix](../reference/support-matrix.md), and active work to the [roadmap](../roadmap/current.md).
