# UI model

## Implemented foundation contract

The public headers are [document.hpp](../../include/tessera/ui/document.hpp), [tree.hpp](../../include/tessera/ui/tree.hpp), and [serialization.hpp](../../include/tessera/ui/serialization.hpp). They depend only on the C++20 standard library. The serialized fields and normalization/rejection rules are owned by [JSON v1](../../formats/tessera-ui/README.md).

`UiDocument` owns one `UiNode` by value. Each node owns an ordered vector of children; copying performs a deep copy. This representation cannot express cycles, shared children, or multiple parents. Only `NodeKind::box` and `NodeKind::text` exist. Text nodes are leaves. Builder data is mutable until validated; invalid candidates do not produce a runtime tree or serialized result.

`UiTree::create` validates a borrowed const document before copying its own immutable snapshot, so a rejected candidate is not consumed or recursively copied first. `UiTree` is neither copyable nor movable; its owning `unique_ptr` can move. Inspection returns borrowed const node pointers valid until the tree is destroyed. Preorder indices and a process-unique monotonically allocated tree identity form `NodeHandle`; handles from another or destroyed tree fail lookup in a later tree. Index 0 is the root, and the all-zero handle is invalid. Tree identities are never reused; identity exhaustion throws. There is no node removal/reuse in this slice. No runtime handle is serialized. A process identity counter does not provide multithreaded mutation or callback guarantees.

Author IDs are optional document-scoped names used for diagnostics, lookup, and references. Duplicate IDs fail validation. They are distinct from runtime handles and from [reconciliation keys](#implemented-keyed-instance-reconciliation), which are not document fields. Class names are stored in authored order; the [prototype style resolver](styling.md#implemented-prototype-style-resolution) matches them regardless of that order.

The implemented semantic property vocabulary is deliberately small:

| Property | Nodes | Value | Behavior |
| --- | --- | --- | --- |
| `text` | Text only, required | UTF-8 string, including empty text | Measured by layout and shaped by paint through the injected `TextShaper`. Also names [semantic](semantics.md#implemented-prototype-projection) entries |
| `focusable` | Box/Text | Boolean | Stored interaction intent read by [focus dispatch](input.md#implemented-prototype-focus-dispatch) and exposed as semantic state |
| `disabled` | Box/Text | Boolean | Excludes the node/subtree from pointer targeting and semantic actions; absent means false; see [input](input.md) |
| `labelled_by` | Box/Text | `NodeReference` to an existing author ID | Existence validation; names the prototype semantic entry |

`Property` has explicit boolean, binary64, string, and reference alternatives. No current semantic property accepts a number; unknown properties or mismatched types fail without coercion. Absent boolean properties remain absent rather than materializing defaults. Layout/style properties and asset references are deferred; they are not arbitrary semantic properties.

`events` stores `activate`/`cancel` action names. Every bound action must exist in the caller's `ValidationContext.actions`; the default empty context rejects all bound actions. Validation snapshots the names for the call only. Pointer and focus dispatch consume `activate` names, and focus dispatch consumes `cancel` names, to return host action requests as defined in [input](input.md). The document stores no callback, and the host remains responsible for action implementations.

Document/node `extensions` preserve namespaced backend-neutral JSON metadata. Validation and runtime behavior do not interpret its contents. Names, strings, and metadata must be valid UTF-8; numeric metadata must be finite. Diagnostics and bounded recursion are described by the encoding page.

`Result<T>` returns an optional value and diagnostics; a failed load/save/create has no usable partial value. Document diagnostics are errors with stable codes, JSON-pointer locations, actionable messages, and source offsets when loaded. `load_document_with_sources` additionally returns node/property source spans as [inspection](inspection.md#implemented-prototype-capture-and-target-resolution) tooling metadata and enriches failures under the [source diagnostic contract](inspection.md#implemented-source-diagnostic-boundary). It preserves document semantics and existing diagnostic fields. Allocator failures and exhausted tree identities remain standard C++ exceptions, rather than validation diagnostics. There are no global node/action registries or implicit filesystem/resource loading operations.

## Common representation

Define the runtime IR before committing to an authoring language. Every frontend must produce the same backend-neutral model:

```text
UiDocument
  format version
  root: UiNode
  style / asset references

UiNode
  type
  optional author id
  classes[]
  typed properties
  style references / local style
  event binding identifiers
  children[]
```

The minimum document is implemented as one rooted, ordered tree. Sibling order is meaningful; property-map iteration must not determine behavior. Validation diagnoses unknown node types, invalid property types, invalid references, and duplicate author IDs. Style/asset references in the broader diagram remain proposed.

Runtime node handles, serialized author IDs, and reconciliation keys serve different purposes. Handles identify live instances; author IDs support references and diagnostics; keys preserve identity across component updates. The implemented handle/author-ID rules are above; owner-level key semantics are in [keyed instance reconciliation](#implemented-keyed-instance-reconciliation), and the remaining rules are proposed under [state and reconciliation](#state-and-reconciliation).

## Primitives and components

Candidate primitive vocabulary: `Box`, `Text`, `Image`, `Button`, `ScrollView`, `Spacer`, `Stack`, `Grid`, and `Canvas`, with a controlled custom-node extension point. `Container` is a category; use `Box` as the initial concrete container name. `Panel` and `List` can begin as composed components rather than additional storage categories. Scrolling is a Box's resolved [`overflow: scroll`](layout.md#implemented-prototype-algorithm); a `ScrollView` primitive or component lowers to it.

A user component maps `props + local state` to a subtree. Examples include `HealthBar`, `InventorySlot`, `Toolbar`, and `PropertyEditor`. A component provides composition, an owner scope, and an identity boundary over the [reactive kernel](reactive-runtime.md#proposed-kernel-boundary); reactive values can also belong to explicit scopes outside a component. Composition is preferred to widget inheritance. Primitive storage kinds and component authoring names need not have a one-to-one correspondence.

The candidate list is vocabulary, not a requirement to implement every primitive. Tool consumers such as data grids, tree tables, timelines, command palettes, and node editors are compositions of these primitives with [virtualization](layout.md#proposed-virtualization-foundation) and [commands](commands.md), not dedicated runtime widgets.

The [implemented component description](#implemented-component-description-and-lowering) expresses typed props, semantic property mappings, named slots, [declared action/event mappings](#implemented-component-actions-and-events), [typed style overrides](#implemented-component-style-bindings), and [named local-state declarations](#implemented-keyed-component-mounting) over ordinary Box/Text documents. [Composed slots](#implemented-composed-component-slots) preserve the styles of independently lowered children, and [nested invocations](#implemented-nested-component-invocations) compose the same descriptions. Proposed extensions express declared signals and automatic invocation setup. Keep drawing primitives, interactive controls, and application composites distinguishable without making them separate runtimes. C++ builders and later textual/visual frontends should have equivalent meaning for the same supported vocabulary; [component source mapping](#implemented-component-source-mapping) preserves authored locations, with richer frontend provenance under [inspection](inspection.md#proposed-inspection-records-and-source-mapping). These extensions require explicit identity, validation, and lifetime rules.

## Properties and validation

Separate semantic node properties, [style properties](styling.md), and host-resolved event bindings. Use a small explicit type vocabulary with named validation rules; avoid opaque reflection or silently coercing arbitrary values.

Event bindings identify host-registered actions rather than embedding function pointers or executable scripts in the document. Unknown actions must produce diagnostics under a declared policy. Registration and dispatch details are owned by [input](input.md).

Diagnostics should carry a stable code, message, document/node/property location, and source span when available. Recoverable warnings must be distinguishable from errors that prevent instantiation. Validation should complete before replacing a live document.

[Inspection](inspection.md#proposed-diagnostics-and-comparisons) adapts validation into a common tooling envelope while preserving original codes and locations. That proposal does not change the implemented diagnostics or JSON v1.

## Serialization

Required properties:

- Explicit format version and deterministic output for equivalent documents.
- Stable child ordering and documented canonical property formatting.
- Round trips preserve semantic data, including editor extension data under a defined policy.
- Unsupported versions fail clearly; migrations must be explicit.
- No renderer objects, GPU handles, platform input codes, or runtime callbacks in serialized data.

Documents are serialized as [JSON v1](../../formats/tessera-ui/README.md) or constructed directly as C++ values. Defaults, extension names, numeric precision, and rejection policy are recorded there. A later TypeScript-inspired DSL and optional JSX/TSX compiler lower into the IR. This does not require executing JavaScript inside the host.

## State and reconciliation

Applications retain ownership of game/application state. Tessera supplies minimal bindings and local view state, with a view model connecting external state to UI. The [reactive runtime](reactive-runtime.md#proposed-kernel-boundary) defines mutable sources, cached derivations, owner scopes, batches, effects, and resource observations. Public API names are open; a `State` or `Binding` convenience must compose these semantics rather than introduce another system.

Reconciliation uses explicit stable keys scoped to one sibling collection or identity boundary. Duplicate keys fail before publication. Reordering a compatible keyed child preserves its logical instance, local state, owner, focus, and subscriptions rather than reconstructing every row. Removal or incompatible kind/identity replacement closes the old owner and creates a new lifetime; reusing a key later cannot revive disposed state or accept its late results. [Keyed instance reconciliation](#implemented-keyed-instance-reconciliation) implements these rules for reactive owners, and [typed property bindings](#implemented-typed-property-bindings) and [component lowering](#implemented-component-description-and-lowering) produce document candidates. Unkeyed child matching and cross-parent moves require an explicit compatibility policy before exposing them; serialized keys and component descriptions are proposals for authoring formats.

Collection insert/remove/move/item-update operations can target keyed instances without requiring a new collection API. Logical item identity, realized presentation instances, and visible paint records are distinct; [virtualization](layout.md#proposed-virtualization-foundation) must not store logical selection/focus in recycled render nodes. [Input](input.md#implemented-prototype-focus-dispatch) owns recovery when a logical target disappears, while [reactive ownership](reactive-runtime.md#proposed-reactive-ownership) owns subscription/effect cleanup.

Compatible-state preservation during reload uses the same identity rules; see [Path-finder integration](path-finder-integration.md).

Property bindings follow [dependency and change detection](reactive-runtime.md#proposed-dependencies-and-change-detection) and [batch scheduling](reactive-runtime.md#proposed-update-batches-and-scheduler). Dirty property/subtree updates must match full-tree results. Test state capture/restore uses only host-declared slots through [inspection](inspection.md#proposed-inspection-records-and-source-mapping), with application state ownership unchanged.

## Implemented keyed component mounting

[component.hpp](../../include/tessera/ui/component.hpp) defines `ComponentLocalState` and `ComponentDescription::local_state`; [component_mount.hpp](../../include/tessera/ui/component_mount.hpp) defines `ComponentMount`, `ComponentStateValue`, and `ComponentCollection`; [component_mount.cpp](../../src/ui/component_mount.cpp) implements owner/state setup above [keyed reconciliation](#implemented-keyed-instance-reconciliation). One collection serves one host-supplied scope and neither owns nor disposes that scope. Reconciliation controls component-owner creation and disposal; the host attaches work to those owners and disposes the enclosing scope for shutdown rather than directly disposing an individual component owner. The collection is movable and noncopyable. Its destruction releases weak records; the host delivers external cleanup explicitly.

Each local-state declaration has a stable name, exact `PropertyType`, and required literal `initial_value`. The four types are Boolean, finite number, UTF-8 string, and author-ID reference. Names, keys, kinds, and reference initial values use 1–256 UTF-8 bytes without control characters. Initial strings contain at most `max_component_state_text_bytes` (4,096) bytes. A description declares at most `max_component_local_state` (256) unique slots; a collection candidate contains at most 4,096 components and 4,096 local-state slots combined. All state, calculated values, and effects share the runtime's live-value budget. Invalid initial values, duplicate slots/keys, null descriptions, and excessive bounds reject the complete candidate before runtime entry or state-record copying, with located diagnostics at `/components/<index>`.

`reconcile(runtime, mounts)` borrows each `ComponentMount::component` description for the call and registers only its kind and local-state schema. Ordinary lowering validates the document, props, actions, styles, slots and source maps separately; owner creation does not imply presentation acceptance. A fresh keyed owner receives one ordinary `Signal<T>` per declared slot in declaration order. Its state values use the owner's value namespace, so additional host values/calculations must use different names. `state<T>(key, name)` returns the exact-type weak signal without reading, evaluating or subscribing; missing keys/slots and wrong types return diagnostics at `/components/<escaped-key>/local_state/<escaped-name>`. Signal writes obey the ordinary reactive contract; the initialization bounds do not impose a separate write validator. Presentation values pass through ordinary lowering validation.

Equal keys and kinds require identical sets of state names and exact types. Declaration order and initial-value changes preserve accepted values, revisions, subscriptions and owner lifetimes. A renamed, added, removed or differently typed slot under the same kind rejects the entire candidate with `component_state_schema`; the caller changes kind to declare complete recreation. Removal or kind replacement disposes the previous owner in previous collection order and invalidates its state, calculations, effects and async sources. A key recreated later receives new initial values and a never-reused lifetime. External operations remain queued for host delivery; submitted resources follow the rendering completion boundary independently.

Registration joins a bounded nested runtime batch and enforces UI-thread, structural-entry and scope/runtime lifetime checks even for an empty candidate or compatible reorder. It does not flush, lower, publish, deliver effects/cleanup, retain an accepted presentation, mount invocation children or preserve state across a new collection. Runtime failures propagate as `ReactiveError`; allocation failures propagate as ordinary C++ exceptions. If state setup fails, every owner created by that call is disposed through ordinary owner disposal, including initialized siblings, and weak records are repaired. Reused owners survive; already removed/replaced owners are not restored. Failed setup lifetimes stay consumed. This failure rule is distinct from the [atomic reload proposal](path-finder-integration.md#live-reload-transaction).

The host attaches calculated bindings, effects, cleanup and async observations through [initial setup](#implemented-component-initial-setup) or the returned `KeyedUpdate::created` indices, and supplies state signals to ordinary arguments. Template/invocation provenance follows ordinary lowering; state declarations have no dedicated source fields or inspection encoding. [Mounting checks](../../tests/ui/component_mount_tests.cpp) cover named compatibility, candidate rejection, setup failure repair, ordinary publication and full-tree source observations. [Invocation-tree mounting](#implemented-component-invocation-mounting) composes this collection boundary; declared signals, detachment and fallback follow the proposal below.

## Implemented component initial setup

[component_mount.hpp](../../include/tessera/ui/component_mount.hpp) defines optional `ComponentMount::setup` and the copyable `ComponentSetup` context. Reconciliation invokes setup only for fresh keyed lifetimes, after registering every fresh owner's declared state, in ascending candidate order inside the mounting batch. Compatible reuse never invokes setup, including a changed or newly supplied callback. The collection borrows callbacks for the call and does not retain them. Definition and argument validation, lowering and presentation acceptance use their ordinary boundaries.

`ComponentSetup::instance()` exposes the key, kind, lifetime and weak owner. `state<T>(name)` returns a weak signal of the declared exact type without reading or evaluating; wrong types and unknown names use the same escaped state paths as collection lookup. The context owns its identity and state-handle map, so a host may retain a copy; it does not prolong the owner, and reads or writes through its signals reject after removal, replacement or failed setup. Collection records stay provisional until all setup succeeds; callbacks use the context to access fresh state rather than looking it up in the previous collection.

Setup is synchronous host registration code. It can attach ordinary calculations, effects, cleanup and async observations to the supplied owner, or create child collections beneath that owner. Value names share the local-state namespace; additional names must be distinct. Host execution, async completion and detachment delivery follow explicit update/cleanup boundaries. Mounting does not flush, publish or deliver effects/cleanup; ordinary settled reads and publication reject the open mounting batch. Recursive reconciliation of the same collection returns `component_setup_reentry` at `/components`; another collection may join the batch. Callbacks must leave the collection's owners live and preserve the borrowed mount inputs for the duration of the call.

Runtime errors preserve their `ReactiveError` diagnostics; other callback exceptions become `component_setup_failure` at `/components/<index>/setup`. Allocation failure propagates as `std::bad_alloc`. State registration, context-copy or callback failure disposes every owner created by the call, including initialized siblings, invalidates their work and queues their cleanup for explicit host delivery. Records are repaired against live owners. Compatible owners survive unless host code disposed their scope; removed/replaced owners are not restored and failed lifetimes remain consumed. External side effects or writes to preexisting owners are not rolled back. Setup is therefore not an [atomic reload transaction](path-finder-integration.md#live-reload-transaction).

[Mounting checks](../../tests/ui/component_mount_tests.cpp) verify callback ordering, reuse, weak context retention, recursive entry rejection, registration failure repair, effect invalidation and stale async delivery. The [tool panel](../../examples/tool-panel/main.cpp) attaches each row's name observation, label calculation and thumbnail cleanup through setup and [invocation-tree mounting](#implemented-component-invocation-mounting). Declared signals, UI fallback and source-aware declaration diagnostics follow [automatic lifecycle](#proposed-automatic-component-lifecycle).

## Implemented component invocation mounting

[component_tree_mount.hpp](../../include/tessera/ui/component_tree_mount.hpp) defines `ComponentInvocationMount`, `ComponentTreeUpdate` and the movable, noncopyable `ComponentTreeCollection`; [component_tree_mount.cpp](../../src/ui/component_tree_mount.cpp) composes [keyed component mounting](#implemented-keyed-component-mounting) beneath one host-owned scope. The host disposes that scope for shutdown; destruction of the collection releases weak records without disposing owners or delivering external work. Keep the collection and borrowed inputs intact during reconciliation and callbacks. A moved-from collection rejects reconciliation.

`reconcile(runtime, invocations, mounts, root)` borrows the ordinary invocation tree and a parallel span containing one stable key and optional initial setup callback per input entry. Nonempty input uses the ordinary root-index, unshared-tree, named-slot, root-kind/cardinality, argument-count and aggregate geometry preflight from [invocation lowering](#implemented-nested-component-invocations). Empty spans with root zero unmount the accepted root. Mounting validates all keys/kinds, unique slot names, local-state declarations, aggregate state count and retained named schemas before runtime mutation. Names use the mounting UTF-8 bounds; all state declarations combined fit 4,096 slots. A deep invalid declaration or incompatible retained schema rejects the entire candidate, including replacements elsewhere in the tree. Mounting does not validate all presentation schemas or read arguments; ordinary lowering validates and accepts presentation separately.

The root key is scoped to the collection. Each component has a keyed child collection for each nonempty invocation slot, beneath a reactive slot owner. Child identity is the compatible parent lifetime, exact slot name, key and kind; duplicate keys in one slot reject, while equal keys in different slots or parents are independent. Input indices, array/root-index changes, slot declaration order and compatible sibling reorder do not identify lifetimes. Compatible schemas retain values, revisions and registrations by state name/type. A kind replacement or removal disposes the owner's entire subtree through ordinary reactive disposal; moving a distinct key between slots or parents recreates it. Equal destination keys and kinds continue to identify the destination's accepted instance. Raw and already-composed children are presentation content and receive no invocation owners.

Slot scopes reserve child-owner names beginning with `__tessera_slot_`; setup code uses other child-owner names. These scopes share ordinary live-owner and owner-depth budgets, and can make runtime depth/count rejection occur before document geometry limits. Removed/empty slot scopes close in their previous accepted declaration order. Whole-component disposal follows reactive child creation order. A slot whose children become empty releases its scope; later recreation receives fresh public component lifetimes. Tree-issued `ComponentSetup::instance().lifetime` values are unique and never reused within this collection, independently of each internal sibling collection's counter.

Each sibling collection first registers all fresh local state, then calls fresh setup callbacks in candidate order under the ordinary mounting batch. After that collection succeeds, mounting visits each component's declared slots and their ordered children. Parent setup therefore precedes descendant setup; all sibling setup precedes descent into those siblings. Reused lifetimes never rerun setup. Callbacks use the ordinary owned weak `ComponentSetup` context to register calculations, effects, cleanup, async observations or additional host-owned work. Success returns contexts aligned to input indices and `created` indices in setup order. Context copies own their identity/state-handle maps without retaining runtime owners; state lookup keeps ordinary component-key paths. Arguments can use these weak signals or host-registered calculations before explicit flush and lowering.

Recursive reconciliation of the same tree returns `component_setup_reentry` at `/invocations`. The tree joins one runtime batch, and each sibling registration joins it; no settlement, presentation acceptance, publication, effects, cancellation or cleanup delivery occurs automatically. Candidate diagnostics identify `/invocations/<index>`. Non-runtime setup exceptions become `component_setup_failure` at that invocation's `/setup`; reactive failures keep their runtime location, and allocation failures propagate. Failure disposes every fresh owner reached by the call, including successful ancestors or earlier branches, then repairs expired node/state/slot records. Compatible live owners survive; removed/replaced owners and issued lifetimes are not restored. Callback side effects and writes to preexisting owners are not rolled back. This boundary is not an atomic reload transaction.

[Tree mounting checks](../../tests/ui/component_tree_mount_tests.cpp) verify parent/slot identity, state retention through reorder and array changes, deep preflight rejection, subtree replacement, stale async completion, explicit once-only cleanup/effect delivery, failed descendant repair, runtime limits and ordinary full-tree presentation/focus. The [tool panel](../../examples/tool-panel/main.cpp) mounts its inventory and rows from the same invocation records it later lowers, with row-owned pinned state, name observations, captions and cleanup. Setup can attach [owner-bound async detachment](#implemented-owner-bound-async-detachment). Definition/expression sources continue through ordinary lowering; mounting has no declaration-origin, signal/effect/async schema, UI fallback or reload migration contract. Those extensions follow [automatic lifecycle](#proposed-automatic-component-lifecycle).

## Proposed automatic component lifecycle

Automatic lifecycle extends [invocation mounting](#implemented-component-invocation-mounting), [keyed mounting](#implemented-keyed-component-mounting) and [initial setup](#implemented-component-initial-setup) to associate a component's scoped key and type with named local-state slots, declared signals, effects, cleanup, async observations, source origin, fault boundary, and reload-compatibility metadata. Lowering uses the ordinary component/document representation; automatic setup composes [reactive owners](reactive-runtime.md#implemented-in-process-graph-contract), keyed mounting, and [publication](reactive-runtime.md#implemented-effect-and-publication-boundary). Public authoring syntax and concrete signal/effect registration types are open decisions.

Local-state and signal declarations need stable names and exact types so compatible updates retain accepted values without depending on declaration order. State compatibility is explicit by component identity/type and slot schema; an incompatible slot or subtree follows the declared reset policy under [reload](path-finder-integration.md#live-reload-transaction). Component-local view state does not take ownership of application data or history.

Compatible keyed reorder retains the owner and its registered state, effects, and observations. Removal or incompatible replacement closes the lifetime, disposes children deterministically, invalidates queued work, and queues once-only external cleanup for host delivery after traversal. Component-bound declarations build on [owner-bound async detachment](#implemented-owner-bound-async-detachment) to register host cancellation/detachment with that lifetime; a late completion must match the live owner/request/attempt and cannot update a recreated key. Submitted assets obey [completion-safe retirement](rendering.md#implemented-frame-contract) independently of logical disposal.

Lifecycle creation preserves definition, invocation, argument, and available declaration origins for inspection and diagnostics. Component failures project the [fault boundary](reactive-runtime.md#implemented-subtree-fault-boundary) through a declared [UI fallback](#proposed-error-boundaries), without publishing partial content. Verify a keyed row that creates state and an observation, survives reorder, is removed, rejects late completion, and is recreated with a fresh lifetime and owned source/inspection records.

## Implemented component description and lowering

[component.hpp](../../include/tessera/ui/component.hpp) defines the data-only `ComponentDescription`, `ComponentProp`, `ComponentProperty`, `ComponentSlot`, `ComponentValue`, and `ComponentArguments`; [component.cpp](../../src/ui/component.cpp) owns `lower_component`. A description has a stable `kind`, an ordinary valid document template, ordered prop declarations, semantic property mappings, ordered slot declarations, [action/event declarations](#implemented-component-actions-and-events), and [style declarations/mappings](#implemented-component-style-bindings). It contains no executable builder or renderer callback. Template Text nodes require authored placeholders. Component descriptions and arguments are host-built values outside the serialized document format.

A prop names an exact `PropertyType`: Boolean, finite number, UTF-8 string, or author-ID reference. A literal default makes it optional; without a default it is required. Unknown arguments, duplicate declarations, invalid types/defaults, and mismatched values fail without coercion. Each property mapping names a declared prop, a template author ID, and a reflected semantic property. The property descriptor defines the accepted node kinds, exact value type, and affected stages. Each target/property has one writer; one prop can supply several targets. Numeric props can be declared and validated, but the semantic property vocabulary supplies no numeric target.

A slot names one unique empty Box in the template, accepted child-root kinds (Box, Text, or both), and inclusive minimum/maximum child counts. Absent slots supply zero children. Supplied children preserve their order, classes, events, and metadata; descendants use ordinary document validation. Slots cannot replace authored children or target Text. Slot content is opaque to the enclosing component's property mappings and slot declarations. A host composes nested components by lowering their documents first and supplying their roots through raw slots or their complete results through [composed slots](#implemented-composed-component-slots), or by supplying [invocation descriptions](#implemented-nested-component-invocations).

Descriptions and arguments each hold at most 256 props and 256 slots; descriptions hold at most 4,096 combined property/event/style mappings. Kind, prop, and slot names are nonempty UTF-8 of at most 256 bytes without control characters. Slot bounds lie between zero and the document node limit. The complete template/schema and supplied literal values, slot actions/properties/metadata, projected depth, and combined node count are checked before reading reactive values or copying subtrees. Cross-slot references are checked for existence in the final document; author IDs share the document namespace, so collisions fail. IDs are preserved verbatim; the host supplies document-unique IDs when composing instances. Located diagnostics distinguish schema, argument, slot, and final document failures; no partial value is returned.

`ComponentValue` holds a literal `Property` or a weak `Signal<T>`/`Computed<T>` for the four prop value types. Lowering requires [settled presentation reads](reactive-runtime.md#implemented-settled-presentation-reads), even for literal-only arguments. It checks whole-graph eligibility, then snapshots every declared supplied reactive prop once in declaration order without demand evaluation or dependency tracking, including props without a property mapping. Defaults and read values obey the same value checks. Reactive reference/fault errors retain their code, report `/props/<escaped-name>`, and include the original reactive location in the message; graph settlement/entry errors retain their original location. A faulted prop rejects the candidate; the host can explicitly compose a literal fallback.

Successful lowering returns `BoundComponent`, extending `BoundDocument` with the [style override array](#implemented-component-style-bindings), preserving template/document extension metadata and applying prop mappings and slot insertion to an owned copy. Changed mapped properties contribute their descriptor stages relative to the template. Nonempty inserted slot content contributes all stages; an empty optional slot contributes none. These observations do not authorize incremental evaluation. The complete result passes ordinary document validation and uses full-tree style/layout/semantics/paint as its presentation reference.

The host creates/reuses owners through [keyed reconciliation](#implemented-keyed-instance-reconciliation) or [component mounting](#implemented-keyed-component-mounting), using the description kind as the compatibility key, and stores prop sources and local state in the instance owner. Lowering validates local-state declarations with the mounting validator before settled reads, but neither allocates/disposes owners nor retains their lifetime, publishes effects, manages focus, or stores the previous presentation. Kind replacement expires old reactive arguments through ordinary owner disposal. The host accepts a complete presentation before publication and retains its last valid presentation on rejection. Optional template and invocation origins follow [component source mapping](#implemented-component-source-mapping). Automatic invocation setup and resource retirement follow the composition and ownership proposals.

[Component checks](../../tests/ui/component_tests.cpp) compare full-tree presentation against authored documents and verify schema/argument rejection, slot references/actions/metadata, bounds, weak lifetimes, faults, and explicit publication. The [tool panel](../../examples/tool-panel/main.cpp) lowers keyed row captions and focusable defaults, then inserts the resulting Text roots through a typed inventory slot.

## Implemented component actions and events

[component.hpp](../../include/tessera/ui/component.hpp) defines `ComponentAction`, `ComponentEvent`, and `ComponentActionValue` for [component lowering](#implemented-component-description-and-lowering). An action declaration has a component-local name and an optional literal host-action default. Without a default, its argument is required. Action and prop names occupy separate namespaces. `ComponentArguments.actions` supplies a literal string or a weak `Signal<std::string>`/`Computed<std::string>`; there is no coercion, callback, command implementation, or implicit host registration.

An event mapping names a declared component action, a template author ID, and `activate` or `cancel`. Box and Text targets accept both events. Each target/event has one writer; one action can supply several targets. A mapping inserts or replaces the template's ordinary event binding. The template must validate independently, including any existing bindings. Mappings can address a slot's template Box but cannot address supplied slot content, which preserves its own bindings unchanged.

Descriptions and arguments each hold at most `max_component_actions` (256) actions; event mappings share the component's 4,096 combined property/event/style mapping budget. Declaration and supplied/default host-action names are nonempty UTF-8 of at most 256 bytes without control characters. Every default, including an overridden or unmapped one, and every supplied literal must name an action in `ValidationContext.actions` before any reactive read or subtree copy. Duplicate declarations, missing/unknown arguments, unknown action mappings, unsupported events, missing template targets, and duplicate event writers return located errors with no candidate. Name-validation errors use `component_name`; host registration failures use the ordinary `unknown_action` code.

After schema/literal/slot validation and whole-graph settlement checks, lowering snapshots prop arguments first, then action arguments in declaration order if the props succeeded. Every declared supplied reactive action is read once, including unmapped actions, without calculation or dependency collection. The resulting name must pass the same name/registration checks. Reactive reference/fault failures retain their code, use `/actions/<escaped-name>`, and include the original reactive path in their message; whole-graph entry/settlement failures retain their original path. No external code runs during lowering, and a rejected action candidate captures no effects. Compatible owner reuse preserves references; disposed or replaced owners invalidate them through the reactive lifetime boundary.

Input adapters use the ordinary [action request boundary](input.md#action-registration-and-lifetime); generation and binding-owner rechecks belong to commands. The boundary has no event removal, payload mapping, source spans, automatic publication, or serialized component declarations.

## Implemented component style bindings

[component.hpp](../../include/tessera/ui/component.hpp) defines `ComponentStyle`, `ComponentStyleBinding`, `ComponentStyleValue`, and `BoundComponent`; [component.cpp](../../src/ui/component.cpp) lowers them through `lower_component`. A style declaration names a required argument or supplies a literal `StyleDeclarations` default. This observation does not compare resolved values with a previous generation or authorize incremental work. Lowering validates declarations and the final document; the host must also accept full style resolution, including any cascade conflicts, layout, semantics, and paint before publication. JSON document encoding, theme resolution, automatic mounting, and source mapping are unchanged by this boundary.

## Implemented nested component invocations

[component.hpp](../../include/tessera/ui/component.hpp) defines `ComponentInvocation` and `lower_component_tree`; [component.cpp](../../src/ui/component.cpp) owns tree validation and lowering. An invocation owns a `ComponentDescription`, ordinary `ComponentArguments`, and an `invocation_slots` map of ordered child indices into the caller's invocation span. The root index defaults to zero and can select any entry. Indices identify records within this call; they are distinct from author IDs, sibling keys and reactive owners. Descriptions and invocation arrays are host-built data outside document serialization.

The span contains between 1 and `max_component_invocations` (4,096) entries. Every entry must be reachable from the root exactly once. Invalid root/child indices report `component_invocation_index`; cycles, reused children and unreachable entries report `component_invocation_cycle`, `component_invocation_reuse` and `component_invocation_unreachable`. Reusing one description requires separate invocation records and document-unique author IDs; there is no automatic ID rewriting. Invocation slots use declared names, root kinds and cardinalities. Raw, composed and invocation slot maps share the 256-slot argument budget, and each slot has exactly one writer, including empty vectors. Conflicts use `component_duplicate_slot_argument`.

Topology, declaration/argument count bounds, aggregate authored node count and projected composed depth are checked before reactive reads or subtree copies. All invocation templates and supplied raw/composed children together must contain at most 10,000 nodes; the invocation and composed document depths must each fit 64 levels. Geometry errors use `component_document_limit`. These guards also count malformed or unknown raw/composed slot content. They do not validate all schemas or snapshot all arguments in advance.

Lowering follows child-before-parent postorder, traversing each description's slot declaration order and each supplied child vector's order. Each invocation reuses the ordinary component schema/literal/slot validation, settled prop/action/style reads and final document validation. Child candidates move into temporary composed-slot storage and are borrowed during parent validation; no argument subtree is copied to assemble that storage. Parent mappings address only their template; styles, anonymous-node alignment, metadata and events follow the composed-slot contract. Each child result validates as an independent document before insertion, so references must resolve within that child's composed subtree. Already-lowered composed children retain their ordinary final-parent reference rules.

Failure returns no root candidate and releases temporary results without changing runtime owners, sources, publication or an accepted host presentation. Component-local diagnostics are prefixed with `/invocations/<index>`; whole-graph entry errors retain `/reactive` paths. Schema failures in a parent can follow settled reads in its children; no calculation or external application runs. Allocation failures propagate as ordinary C++ exceptions. Success returns the root's owned document, aligned overrides and ordinary affected-stage observations. Repeating the call after host updates and flush snapshots the latest weak arguments; it does not subscribe, mount components, refresh retained composed children or publish effects. Owner/local-state setup, fallback policy, generations, full-tree presentation acceptance and publication belong to the host.

## Implemented component source mapping

[component.hpp](../../include/tessera/ui/component.hpp) adds optional `DocumentSourceMap` values to `ComponentDescription.sources` and `BoundComponent.sources`, and optional `ComponentArgumentSources` to `ComponentArguments.sources`. The [inspection source-map contract](inspection.md#implemented-prototype-capture-and-target-resolution) owns their output record schema, bounds and validation. Descriptions associate template nodes with authored locations; arguments associate invocation and supplied expression locations with an instance. Lowering returns owned metadata aligned to the resulting document, outside document serialization and style overrides.

Ordinary lowering validates the template map after document validation and each supplied composed child's map after child document/geometry validation, before reading the parent's reactive arguments or copying subtrees. Errors retain the source-map code and are located under `/component/sources` or `/slots/<escaped-name>/<child>/sources`. Nested invocation lowering uses the same checks and prefixes component-local errors with `/invocations/<index>`; a parent map failure can follow settled child reads under the ordinary postorder contract. Rejection changes no owner, reactive value, accepted host presentation or publication.

If a template, argument metadata or composed child supplies sources, lowering emits one record per resulting node in preorder. It rebases node pointers to the resulting hierarchy, resolves mapped records' file identities before insertion, and preserves node spans and untouched property spans. Raw children and templates without maps receive explicit unmapped records. Each mapped semantic property loses its placeholder's property span and is marked unmapped, including defaults, inserted properties and values equal to the placeholder: a template value is not the origin of an instance argument. The node's declaration span remains available. Slot content is opaque to parent mappings.

`ComponentArgumentSources` contains an optional invocation `SourceLocation` and independent `props`, `actions` and `styles` origin maps keyed by argument name. Each map has at most 256 entries and may describe only explicitly supplied arguments, including declared arguments without output mappings; defaults have no argument origin. Unknown/absent argument origins report `component_source_argument` under `/sources/<namespace>/<escaped-name>`; excessive counts use `component_limit` at `/sources`. File/range failures use the ordinary source-map codes. These checks precede reactive entry and subtree copying. Invocation-tree topology traversal checks every reachable invocation's argument origins before any child lowering, with `/invocations/<index>` locations; template and composed-child map validation follows ordinary postorder.

Every template node receives this instance's optional invocation origin. Property mappings copy a supplied prop origin to `NodeSource.property_arguments` under the resulting semantic property name; event mappings copy action origins to `event_arguments` under the resulting event name; style mappings copy the style argument origin to `style_argument` for the complete override. One supplied argument can therefore have several observed targets. Origins describe expressions, not the serialized bytes of their settled values. They have independent file identities and ordered half-open ranges: an argument may be authored outside its invocation range or file. A binding without an argument origin clears any previous origin for that target. Parent invocation origins and bindings do not propagate into raw or composed slot content.

Repeated composed-slot and invocation lowering preserve independently authored child files and anonymous-node alignment. The result has no source map if neither the template, argument metadata nor any composed child supplies one. An owned map accompanies its candidate through host acceptance; later lowering or disposal cannot mutate it. The host passes it with that candidate's coherent tree/styles/layout to ordinary inspection, whose owned elements and invariant observations retain the resolved origins, including invocation-only nodes with no template span. The complete output map validates against the resulting document. The metadata changes neither serialized fields, affected-stage observations, style/layout/semantic/paint values nor publication rules, and opens no source file.

Lowering enriches rejected template, argument, composed-child and final document candidates through the [source diagnostic boundary](inspection.md#implemented-source-diagnostic-boundary). It resolves source envelopes before path relocation, preserves independent child files and uses expression/invocation fallbacks only from validated argument metadata. Constructing the candidate's map before final semantic validation permits rejected instance references and cross-component IDs to retain their origins; no rejected candidate is returned or published.

This boundary has no prop/default declaration spans, individual style-field spans, authored template event spans, source-content authentication, edit/reload protocol or component serialization. These extensions follow [inspection source-mapping proposals](inspection.md#proposed-inspection-records-and-source-mapping).

The [tool panel](../../examples/tool-panel/main.cpp) loads embedded inventory and row templates with opaque fixture identities, then captures the flattened inventory using its composed map.

## Implemented typed property bindings

[bindings.hpp](../../include/tessera/ui/bindings.hpp) defines `BoundProperty`, `PropertyBindings`, and `BoundDocument`; [bindings.cpp](../../src/ui/bindings.cpp) owns candidate lowering. `bind<BoundProperty::text>(author_id, value)` accepts a `Signal<std::string>` or `Computed<std::string>`; `focusable` and `disabled` accept Boolean values, and `labelled_by` accepts `NodeReference` values. Mismatched types have no binding overload. Bindings store weak reactive references, hold no callbacks or owner lifetime, and are host-built data outside the serialized document. [Component lowering](#implemented-component-description-and-lowering) adds prop declarations and slots using the same reflection and settled-read boundaries; [component events](#implemented-component-actions-and-events) lower declared action arguments separately, and [component styles](#implemented-component-style-bindings) produce typed instance overrides. Arbitrary property names and optional removal follow the composition proposals.

One set contains at most `max_property_bindings` (4,096) entries in registration order. Target IDs are nonempty UTF-8 of at most 256 bytes without control characters. Registration returns the inserted index or located `invalid_binding_target`, `duplicate_binding`, or `binding_limit` diagnostics; rejection leaves the set unchanged. Each target/property pair has one writer; competing values must be composed in the graph. Author IDs address presentation nodes, while the stored reactive references retain their original instance lifetime: reusing an ID does not revive a removed instance's bindings.

`apply(runtime, authored, validation_context)` validates the input before copying it; required properties, including Text's authored placeholder, must be present. It indexes the valid copy by author ID and checks every target before reading values. Missing targets produce `binding_target_missing` at `/bindings/<index>/target`; incompatible node kinds produce `binding_node_kind` at the node's property path. The reflection descriptors define accepted node kinds and affected stages.

After target validation, apply uses [settled presentation reads](reactive-runtime.md#implemented-settled-presentation-reads): the whole graph must satisfy publication eligibility, and every bound value must belong to that runtime and a live, healthy owner. Reads neither refresh calculations nor collect dependencies. Global entry/settlement failures retain their reactive location. Individual reference/fault failures retain their reactive code, report the document property path, and include the original reactive location in the message. All individual reactive failures are reported in binding order without returning a partial candidate.

Successful reads replace only their target properties in the copy. The complete candidate then uses ordinary document validation, including UTF-8, action registration, and reference existence; any failure returns no value. Authored nodes, order, classes, events, and extension metadata are preserved. `BoundDocument::stages` is the conservative union of descriptors for properties whose stored value differs from the supplied input, counting insertion as a difference; it compares against that input, not a previous publication. These bits are observations, not permission to skip inherited style or geometry work. Full-tree style/layout/semantic/paint evaluation is the presentation reference.

Apply never flushes, publishes, delivers effects, or owns the last accepted UI. The host settles updates, builds and validates the bound candidate and its presentation stages, retains the prior presentation on rejection, and calls `publish()` only after accepting the complete candidate. A faulted binding rejects the candidate; subtree fallback mapping is explicit host composition. ## Implemented keyed instance reconciliation

[keyed.hpp](../../include/tessera/ui/keyed.hpp) defines `KeyedChild`, `KeyedInstance`, `KeyedUpdate`, and `KeyedCollection`; [keyed.cpp](../../src/ui/keyed.cpp) owns matching. A collection maps one sibling collection to [reactive owners](reactive-runtime.md#implemented-in-process-graph-contract) created beneath a host-supplied scope owner. It never owns or disposes that scope, and one scope serves one collection. The collection is movable and noncopyable; it uses no host, renderer, or `UiTree` types, and its keys are neither document fields nor implicit author IDs.

`reconcile(runtime, children)` takes the complete candidate in presentation order. A child names a `key` and a `kind`; both are nonempty valid UTF-8 of at most 256 bytes without control characters, so a key can also serve as a reactive owner name and author ID. Keys are unique within the candidate, which holds at most `max_keyed_children` (4,096) children. Validation reports every `invalid_key`, `invalid_kind`, and `duplicate_key` at `/children/<index>/key` or `/kind`, and `keyed_child_limit` at `/children`; a rejected candidate changes nothing and allocates no lifetime.

A previous instance with an equal key and kind is reused with its owner, lifetime, local values, bindings, effects, and cleanup registrations; reordering creates and disposes nothing. A key absent from the candidate removes its instance, and a key whose kind differs replaces it. Replacement and new keys create an owner named by the key beneath the scope, so a replacement reuses the disposed name under a new lifetime. Lifetimes are allocated in candidate order, start at one, and are never reused within a collection. Disposal follows the previous instance order and uses ordinary owner disposal, so cleanup is queued for the host's explicit [cleanup delivery](reactive-runtime.md#implemented-external-cleanup-boundary) and disposed values fail later reads.

A successful `KeyedUpdate` returns the instances in candidate order, the ascending indices of instances it created, and removed or replaced instances in previous order. The host registers local state, prop sources, bindings, and cleanup in each created owner. `instances()` and `find(key)` return the current record; `current(key, lifetime)` tells the host whether a result addressed to a lifetime still names the live instance, so a late result for a removed or replaced instance is dropped even after its key returns.

Owner creation and disposal follow the runtime's thread, calculation, effect-delivery, foreign-owner, budget, and disposed-owner rules, and their failures propagate as `ReactiveError`. New keys are created before any disposal, and a failure while creating them disposes the owners already created by that call and leaves the collection unchanged. A later failure, which requires a disposed scope or a foreign runtime, leaves the collection without the instances it disposed. The record therefore never retains a disposed owner or omits an owner it created. Because new keys are created first, they count against the live owner budget before removed instances release theirs.

The collection does not build nodes or move focus. The host lowers the instances into an ordinary full-tree document, typically using keys as author IDs so that [focus recovery](input.md#implemented-prototype-focus-dispatch) follows the logical row. Conditional children are a collection whose candidate omits a child or changes its kind. [Typed property bindings](#implemented-typed-property-bindings) project the instances' reactive values into that candidate; component descriptions, serialized keys, unkeyed matching, and cross-parent moves follow the proposals above. [Keyed checks](../../tests/ui/keyed_tests.cpp) and the [tool panel](../../examples/tool-panel/main.cpp) exercise these rules.

## Implemented typed async view observations

[async.hpp](../../include/tessera/ui/async.hpp) defines `AsyncValue`, `AsyncAttempt`, `AsyncStart`, `AsyncObservation`, `AsyncReadyValue`, and `AsyncFailure`; [async.cpp](../../src/ui/async.cpp) owns transitions and validation. An `AsyncValue` allocates one ordinary reactive source beneath an explicit owner, with an exact `PropertyType` schema (Boolean, finite number, UTF-8 string, or author-ID reference). It starts `idle` without a value. Copies alias that source through weak reactive references; neither an observation handle nor an attempt token owns the runtime or prolongs the owner. Execution has no provider, future, thread or renderer interface; external detachment uses the [owner cleanup contract](#implemented-owner-bound-async-detachment).

The host owns execution and delivers transitions in explicit logical order on the runtime's UI thread at update points, optionally within ordinary update batches. `begin(request)` starts `loading` from idle or a terminal state, or supersedes a loading attempt. Each successful start increments the observation-local attempt sequence, even when the request ID is unchanged. Superseding returns the previous attempt in `AsyncStart::detached` for host cancellation/detachment after return; the runtime performs no external operation. `ready_cached(request, value)` explicitly declares a synchronous cache hit and accepts `idle -> ready` without an intermediate loading value. It rejects every other starting state. Attempt sequences and accepted-value revisions reject exhaustion rather than wrapping.

Each opaque token addresses one observation lifetime, request ID, and attempt. `progress`, `complete`, `fail`, and `cancel` require that exact current token and `loading` state. A token from another observation or an earlier attempt reports `async_stale_attempt`; a repeated or post-cancellation terminal delivery reports `async_transition`. Owner disposal expires the source before late delivery, which reports the ordinary reactive lifetime error. A replacement owner cannot accept the old token even if its author ID, source name, request ID and sequence match. Transitions return located diagnostics beneath `/async/<escaped-name>` and change nothing on rejection; reactive failures preserve their codes and include their original location. Allocation failures propagate as standard C++ exceptions.

Progress starts absent, accepts only finite fractions in [0, 1], and cannot decrease within an attempt. Equal progress writes use ordinary equality suppression. `complete` installs one whole validated value and enters `ready`; `fail` enters `failed` with a bounded error code/message and `retryable` flag; `cancel` enters `cancelled`. Terminal transitions clear progress. Retryability is descriptive and never starts work. A new attempt clears the previous failure and progress. Failure, cancellation and replacement retain the last accepted ready value; `stale()` reports that a retained value belongs to an observation whose status is not ready. The retained value carries its original request, attempt, and increasing accepted-completion revision until a new complete value replaces it. There is no partial payload or history beyond this one retained value.

Observation names, request IDs, error codes and reference IDs are nonempty UTF-8 of at most 256 bytes without control characters. String values accept at most `max_async_text_bytes` (4,096) UTF-8 bytes; failure messages use the same bound and must be nonempty. Payloads use the exact declared type without coercion. Reference syntax is validated, while existence in a presentation document belongs to ordinary document validation. Each source counts against the reactive node budget. Constructor schema/name errors throw `ReactiveError` before source allocation; runtime owner/name/budget errors follow ordinary source creation rules.

`read()` participates in ordinary dependency tracking; calculations can derive a typed component prop from the observation. `snapshot(runtime)` uses the existing settled, non-evaluating snapshot boundary. Returned observations own their primitive values and remain immutable across later transitions or disposal. Transitions do not flush, publish a presentation, deliver effects, or roll back host data. The host settles its batch, lowers components, accepts full-tree style/layout/semantic/paint evaluation, and publishes explicitly. Invalid payloads leave both the source and the previous accepted presentation available. Kernel thread, pure-calculation, lifetime, and foreign-runtime guards apply unchanged.

The host can register [owner-bound async detachment](#implemented-owner-bound-async-detachment) when work must close with its owner, and acts on a successful `cancel` or `detached` token outside traversal. Logical cancellation does not claim that underlying work stopped. Primitive observations own no external asset or submitted GPU storage; resource adapters must obey [render completion](rendering.md#implemented-frame-contract) independently. Declared component async schemas, resource payloads, reload integration, and async recording/inspection encoding follow [automatic lifecycle](#proposed-automatic-component-lifecycle) and the [async resource proposal](#proposed-async-state).

[Async checks](../../tests/ui/async_tests.cpp) cover cache hits, retry/supersession, monotonic progress, stale-value identity, exact payload validation, cancellation, owner replacement, thread/calculation rejection, batched component presentation and explicit effects. The [tool panel](../../examples/tool-panel/main.cpp) projects host-delivered inventory names through keyed row-owned observations: unchanged data keeps the accepted source, replacement failure retains the old name, retry drops an earlier completion, and a complete name reaches the ordinary invocation tree.

## Implemented owner-bound async detachment

[async.hpp](../../include/tessera/ui/async.hpp) defines `AsyncValue::on_detach(runtime, callback)`; [async.cpp](../../src/ui/async.cpp) attaches it to the observation's original weak owner through [external cleanup](reactive-runtime.md#implemented-external-cleanup-boundary). The host supplies one nonempty `std::function<void(const AsyncAttempt&)>` per observation lifetime, including all copied handles. Registration may precede or follow `begin`. It uses the observation name in that owner's separate cleanup namespace and reserves one ordinary cleanup slot, sharing the live-and-pending cleanup/effect budget. A colliding cleanup name, foreign runtime, invalid entry, disposed source or full budget rejects registration without accepting the callback. Empty and repeated registrations report `async_detach_callback` and `async_detach_registered` at `/async/<escaped-name>/detach`; runtime registration failures retain their codes with the observation location.

Accepted transitions maintain one owned pending attempt address shared by all observation copies. Rejected transitions leave it intact; loading progress preserves it; supersession replaces it; cache, completion, failure and explicit cancellation leave no active address. Token allocation precedes the source write; if the kernel accepts the source revision before an invalidation allocation fails, detachment tracks that accepted revision while the exception propagates. This bookkeeping adds no calculation, publication or source revision. Compatible keyed reorder preserves the registration and active address with the owner. Removal, replacement, failed fresh setup or explicit scope disposal queues the registration through ordinary child-first owner disposal.

`deliver_cleanups()` invokes the callback only if the observation was loading when its owner closed, passing the latest attempt address without reading the disposed reactive source. The queue retains that address and callback even after all observation handles are released. Disposal, batch close, reads, settlement and publication perform no external operation. Idle and terminal observations consume an empty registration, including failed/cancelled replacements retaining a stale accepted value. A disposed or recreated observation rejects late deliveries through the ordinary lifetime/attempt checks.

Delivery consumes the address before invocation, releases callback captures afterward, rejects reactive reentry, reports callable failures at the owner's ordinary cleanup path and continues with following cleanup. Each registration delivers at most once, even when its host operation fails. Runtime destruction releases captures without invoking them; shutdown delivery requires explicit owner disposal and cleanup delivery. Supersession continues to return `AsyncStart::detached` for explicit host detachment, and successful `cancel` requires the host to detach that work outside traversal. This callback covers owner disposal only and makes no executor, underlying cancellation, GPU retirement, resource payload or reload promise.

## Proposed async state

General resource observations extend the [typed view boundary](#implemented-typed-async-view-observations) without exposing backend futures or threads to components. Image, font, and other resource loading; shader compilation; remote data; AI responses; filesystem scans; asset import; and thumbnail generation share its state vocabulary. The host or an optional library owns execution and delivers transitions only at [update points](architecture.md#update-and-snapshot-rules); a component observes the settled state of its generation. Removing the owning component cancels or detaches the work, and a late result for a removed or replaced owner is dropped with a diagnostic rather than applied. [Replay](replay.md) records transitions as declared readiness inputs, never wall-clock completion.

### Async transition and ownership rules

Resource observations preserve the typed view boundary's request/attempt, transition, monotonic progress, failure/cancellation and stale-value rules. Their owner is a component instance identity (including its reconciliation lifetime) or an explicit host scope; an author ID alone cannot retain ownership through replacement.

An adapter supplies a bounded payload schema and owned accepted resources instead of primitive `Property` values. Progress is declared by execution rather than inferred from elapsed time. Failure/cancellation never silently installs a partial resource.

The host queues owned transitions and publishes them in explicit logical order at update points. The runtime validates owner/request/attempt, transition, and payload schema before settling a candidate generation; snapshots being inspected or rendered stay immutable. Published resources retain the [render completion lifetime](rendering.md#implemented-frame-contract) even if the logical owner cancels. Cancellation is a logical terminal state and need not claim that underlying work stopped; a late result is discarded. Errors in the host operation use this state/result boundary, while subtree construction errors use error boundaries.

[Replay](replay.md) readiness fixtures must declare request IDs, resource identities/digests, attempted transitions, and their update sequence; a test adapter supplies the resulting values, without filesystem/network timing. [Inspection](inspection.md#proposed-inspection-records-and-source-mapping) exposes only declared state slots and owned observations. [Commands](commands.md#proposed-transaction-boundary) own edit transaction tokens; an async request never commits application data merely by becoming ready.

Open decisions: resource payload types and bounds, host subscription delivery/backpressure, and whether a consumer needs more than one retained ready revision. Resource fixtures cover cancellation/removal/reload with reused author IDs, bounded payload rejection, and replacement while an earlier GPU submission owns the old bytes, preserving the typed view transition checks.

## Implemented controlled host-state boundary

The [Replay host update boundary](replay.md#implemented-controlled-host-updates), defined in [replay.hpp](../../include/tessera/replay/replay.hpp), implements the async ownership rules for declared boolean fixture slots and host-built immutable replacement views. Loading attempts use strictly increasing request numbers; only the current attempt can complete, and view replacement cancels other pending owners before publication. Failure/cancellation retain accepted values, and rejected candidate views retain the previous generation. It has no component subscription, progress payload, provider execution, or application mutation. [Typed async view observations](#implemented-typed-async-view-observations) provide in-process component projection; general resources and their recording integration follow the [resource proposal](#proposed-async-state).

## Proposed error boundaries

Dynamic UI, live reload, and agent-generated UI must fail locally. An error boundary is a declared subtree whose validation, build, or binding failure is contained: the boundary presents a declared fallback and reports diagnostics linked to source locations under [inspection](inspection.md#proposed-inspection-records-and-source-mapping), while the rest of the tree keeps its identity, focus, and state. At document level the same rule is the [reload transaction](path-finder-integration.md#live-reload-transaction): a new document is validated and built as a candidate generation, swapped in only on success, and otherwise rejected while the previous valid generation stays live. Boundaries never catch host action failures; those return through the [command](commands.md) result contract. Reactive calculation failures reach a subtree through the [reactive fault boundary](reactive-runtime.md#implemented-subtree-fault-boundary), which contains and locates them but leaves fallback presentation to this boundary.

## Proposed context

A subtree can receive shared services through an explicit context: theme, locale, asset provider, [command registry](commands.md), selection model, undo stack, font environment, or diagnostics sink. A context value has a declared type, an owner that outlives every consumer, and a scope limited to the subtree that provides it; consumers resolve the nearest provider and diagnose a missing one. Context is not a global service locator, does not let components reach host internals, and does not move application state into the runtime. Changing a provided value invalidates its consumers under the ordinary update rules.

[Localization](localization.md#proposed-locale-context) defines locale inputs and message resolution. A localized message binding preserves its ID and typed arguments in the common representation; changing provider values changes presentation without replacing component keys or user editing state. Literal text and message references need distinct validated forms before a serialized schema is extended.

## Implemented property metadata

[property_metadata.hpp](../../include/tessera/ui/property_metadata.hpp) describes the authored semantic property vocabulary above without a reflection framework or editor dependency. `property_descriptors()` returns one `PropertyDescriptor` per property, ordered by name; `find_property_descriptor` performs exact, case-sensitive lookup. Descriptors have static storage duration and remain valid for the rest of the program.

| Field | Meaning |
| --- | --- |
| `name` | Stable identifier and JSON v1 member name under node `properties`; not a display label. `property_names` holds the same constants for runtime consumers. |
| `type` | `PropertyType` mirroring the `Property` alternative; `property_type` maps a value to it. No coercion. |
| `accepted` / `required` | `NodeKinds` bit sets. Other kinds reject the property as `unknown_property`; absence on a required kind is `missing_property`. |
| `absent_value` | Meaning of absence on an accepted, non-required kind, or none. It is never materialized into documents or output. |
| `stages` | `PropertyStages` bit set whose meaning is owned by [styling](styling.md#property-effects). |
| `category` | Editor grouping (`content`, `interaction`, `accessibility`); it never affects validation or defaults. |

| Name | Type | Accepted / required | Absent value | Stages | Category |
| --- | --- | --- | --- | --- | --- |
| `disabled` | boolean | Box/Text / none | `false` | input, semantics | interaction |
| `focusable` | boolean | Box/Text / none | `false` | input, semantics | interaction |
| `labelled_by` | reference | Box/Text / none | none | semantics | accessibility |
| `text` | string | Text / Text | none | layout, paint, semantics | content |

`validate` derives property name, node-kind, type, and required-property checks from these descriptors; string UTF-8, finite-number, and reference-existence checks remain value rules. JSON v1 encodes a property under its descriptor name using its `Property` alternative. `effective_property` returns the authored value or the descriptor's absent value, borrowing from the node or the static table; pointer and focus targeting read `disabled` and focus dispatch reads `focusable` through it, and layout/paint read `text` through `property_names`. Descriptors cover authored properties only; resolved style, layout, and other derived values are not listed. The current vocabulary has no numeric range or enumeration, so descriptors carry no range/enum fields.

[Property metadata checks](../../tests/ui/property_metadata_tests.cpp) validate every descriptor, node kind, and value type against validation, absence handling, and canonical encoded names, and [pointer checks](../../tests/input/pointer_tests.cpp) compare absent and explicit `disabled`.

## Proposed property reflection

Extend the implemented descriptors as the schema evolves, without a general reflection framework or editor SDK dependency. Add valid range/enum metadata when a numeric or enumerated property is introduced, and distinguish derived or read-only values if they are exposed. A property can affect multiple stages; do not force style/layout/paint/semantics into a mutually exclusive enum.

Use the same descriptors for Inspector generation and invalidation. Do not maintain a second editor-owned list of types/defaults. This proposal does not add fields to JSON v1. Path-finder consumes this metadata under its [bridge contract](path-finder-integration.md).

Separate static schema descriptors from observations of one generation. The schema supplies stable property ID, display name, semantic type, default/absence rules, editability, validation rules, enum/range metadata where applicable, and affected stages. Observations join current, authored, default, inherited, and resolved values as applicable, source origin, component owner, and generation. Missing or inapplicable values are explicit rather than guessed from a rendered result; derived observations are read-only unless they expose a declared edit operation.

The affected-stage set follows [property effects](styling.md#property-effects); resource-related effects need an explicit extension when resource properties are introduced. Metadata can support semantic, style, layout, paint, resource, and interaction work without requiring incremental evaluation. Inspector edits validate a typed candidate, enter the ordinary command/transaction or declared runtime edit boundary, and publish one accepted generation. A generic Inspector must discover editors from this schema without hardcoding Box/Text properties, and observe the resulting property/source metadata after an edit.

## Proposed overlays and portals

An overlay root provides a presentation layer for popups, tooltips, context menus, and modals outside ordinary content clipping. A portal changes presentation ancestry while retaining declared component/state ownership and stable identity. Define logical versus presentation parentage explicitly before adding it to the document schema.

`OverlayRoot` and `Portal` are the shared primitives for composed Tooltip, Dropdown, and Modal behavior. Presentation relocation does not transfer the portal child's local state, subscriptions, source origin, or command ownership to the overlay root. The [SemanticTree](semantics.md) must express the declared logical relationships rather than deriving meaning solely from the relocated paint hierarchy; concrete relationship encoding is a schema decision.

The model owns mount/unmount, keyed identity, and cleanup. [Layout](layout.md#scrolling-and-overlay-geometry) owns anchor/viewport placement; [rendering](rendering.md#proposed-overlay-paint) owns presentation order/clips; [input](input.md#proposed-overlay-interaction) owns modal focus and hit eligibility. These consumers must use the same layer identity rather than inventing independent z-order schemes.

Virtualized views rely on keyed item identity and reconciliation cleanup. A realized item keeps its key across recycling and generations; selection and focus refer to item keys, so they persist while the item is unrealized, and focus recovery follows [input](input.md#implemented-prototype-focus-dispatch) when the keyed item disappears. Geometry and realization are owned by [layout](layout.md#proposed-virtualization-foundation).
