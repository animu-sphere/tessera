# Input, focus, and navigation

## Core invariants

- The host normalizes platform devices at the boundary; core does not poll OS input APIs.
- Targeting uses coherent logical geometry and shared eligibility. Keyboard/gamepad navigation and semantic operations follow ordinary action/command boundaries.
- Host actions execute after traversal; generation/lifetime checks reject stale targets rather than invoking expired owners.

## Implemented Modal interaction

[modal.hpp](../../include/tessera/input/modal.hpp) supplies `ModalDispatcher(id)` for the controlled root-sibling [Modal/Dialog](ui-model.md#implemented-c-form-authoring). One displayed, locally visible, enabled Modal establishes shared eligibility: only its subtree can receive pointer hits, focus/navigation, wheel routing or semantic actions. Background nodes remain painted and exposed as disabled semantic entries without actions. Binding lookup cannot escape to root/background owners. Tab/Shift-Tab wrap among eligible descendants; directional navigation retains its ordinary non-wrapping geometry rule inside that set. Programmatic background focus fails as `modal_target`.

The dispatcher retains stable author IDs, never live nodes. Refresh every accepted view, including closed ones, with current-snapshot focus so the eventual opener is remembered. Opening requests the first eligible dialog control once and `reset_pointer`; compatible replacements preserve eligible focus. An empty scope clears ordinary focus. Closing/unmount/hidden or disabled owner requests pointer reset and recovers only to a surviving eligible opener; ordinary focus recovery remains the fallback. Unavailable open owners additionally request controlled dismissal.

Dispatch before ordinary input. Logical Cancel or unmodified Escape sets `dismiss`, `consumed` and `reset_pointer`; the host closes, publishes and refreshes before restoring background focus. The open view remains modal until that publication. Backdrop clicks do not dismiss or confirm. Reset/cancel ordinary pointer presses on the returned flag to prevent deferred activation across transitions, including when compatible pointer replacement is enabled. Calls validate coherent snapshots, stable Modal IDs, current focus and normalized ordered events; rejection preserves policy state.

If dispatch itself first observes an open/close transition, that event is consumed rather than activating a newly recovered control or the background. Normal hosts refresh before routing so ordinary inside events pass through unchanged.

`active` exposes host arbitration state, not OS capture or a global command filter. Hosts must gate world input, owner-free shortcuts and other transient UI themselves, and route panel scroll/focus reveal through the ordinary APIs. The [guide](../guides/modal-dialog.md), [owner fixture](../../tests/input/modal_tests.cpp) and [settings-reset consumer](../../examples/modal-dialog/main.cpp) define usage and checks. Nested/stacked modal lifetimes and Portal relocation remain unsupported/proposed.

## Implemented Popup and Tooltip interaction

[popup.hpp](../../include/tessera/input/popup.hpp) supplies host-owned policy for the controlled [Popup/Tooltip compositions](ui-model.md#implemented-c-form-authoring). No dispatcher writes application state or runs actions. All calls validate a coherent snapshot; dispatch additionally validates normalized events and monotonic timestamps. Rejected calls preserve state. Stable author IDs, not borrowed nodes, survive replacement.

`PopupDispatcher(id)` requires a popup ID. `refresh` runs on every accepted view, including closed ones. Opening requests focus on the first ordinary eligible focusable descendant once; compatible replacement does not steal focus again. Closing requests focus on the surviving eligible anchor. Unavailable geometry, hidden/disabled anchors or owner removal requests dismissal without restoring expired or ineligible handles. Apply returned `focus` through `FocusDispatcher`; ordinary focus recovery remains the fallback.

Dispatch runs before pointer/focus routing. Any pointer press outside the popup, logical Cancel or unmodified Escape requests controlled dismissal, marks the event consumed and requests anchor focus. Inside events pass to ordinary pointer dispatch, navigation and command execution. On consumed dismissal, cancel/reset any ordinary pointer press so its later release cannot click through. Selection commands close in the host, followed by refresh. There is no focus trap, modal input capture, navigation override or implicit native pointer capture.

`TooltipDispatcher(anchor)` returns immediate visibility while its eligible anchor (or a descendant) is hovered or focused. It retains one normalized pointer position/identity, recomputes stationary hover on refresh, and clears matching hover on PointerCancel. Cancel/Escape or a press suppresses help until both hover and focus leave. Pass current-snapshot focus after ordinary focus routing; stale handles fail explicitly. The host can hide help while a Popup is open and owns scheduling, optional delays and window-focus normalization. The dispatcher does not consume events.

`pointer_events: false` excludes a node and its descendants from pointer hits independently of disabled state. It does not suppress painting, semantic text, focus eligibility or semantic actions; Tooltip composition contains only nonfocusable Text. Thus help never intercepts the anchor or a control beneath it. Ordinary popup option buttons remain ordinary semantic buttons; no tooltip role, accessibility description relationship or native accessibility adapter is introduced.

The [owner checks](../../tests/input/popup_tests.cpp) and [dedicated example](../../examples/popup-tooltip/main.cpp) verify lifetime, dismissal, hover/focus suppression, transparent hit routing and pointer/keyboard/gamepad command parity. The [guide](../guides/popup-tooltip.md) owns the host procedure.

## Implemented Menu and ContextMenu interaction

`MenuDispatcher(id)` in [popup.hpp](../../include/tessera/input/popup.hpp) layers single-level command policy over `PopupDispatcher`, preserving its snapshot, event-order, dismissal and focus-recovery contract. The [menu guide](../guides/menu-context.md) owns the complete host procedure and limits; [owner tests](../../tests/input/menu_tests.cpp) cover the boundary.

ContextMenu's paired point properties enable secondary-press opening on the eligible topmost target/descendant hit, and nonrepeating Shift+F10 when eligible focus is inside that target. `open_at` is a consumed request for host-controlled publication, not an action on the underlying target. Keyboard opening uses the target's visible lower-left point. Disabled, modal-blocked, missing or fully clipped targets cannot open. Reopening requests the first eligible item again.

Inside hover requests eligible item focus. Ordinary `FocusDispatcher` handles menu Up/Down in item order, skipping disabled items and wrapping; Home/End reach endpoints and Left/Right stay put. Activation remains the ordinary pointer/focus/semantic action followed by host command execution and accepted-choice closure. Menus expose no selected/expanded state.

Outside presses, Cancel and unmodified Escape consume dismissal; reset ordinary presses to prevent click-through. Sequential traversal instead requests unconsumed dismissal: close/publish/refresh, then route the one logical FocusNext/FocusPrevious in the closed view. Hosts translate raw Tab once, route wheel/reveal through ordinary scroll helpers, and arbitrate external focus/window loss/other overlays. There is no menu-modal scope, general focus trap, submenu or implicit native input capture.

## Implemented SplitPane adjustment

[split_pane.hpp](../../include/tessera/input/split_pane.hpp) connects the public [SplitPane composition](ui-model.md#implemented-c-form-authoring) to normalized input without callbacks or platform types. `split_pane_geometry(input, id)` resolves the generated three-child structure against a coherent hit-test snapshot, joining the actual first-pane/handle boxes, parent content size, orientation and wrapper minima. It returns separator eligibility through shared semantics. Absent or hidden generated parts return an absent geometry; malformed structure and invalid snapshots return actionable diagnostics.

`SplitPaneDispatcher(id, keyboard_step)` is host-owned single-handle capture. Its finite positive step defaults to 8 logical units. A primary press on the ordinary clipped/topmost handle hit returns focus and starts capture without moving the split. Matching pointer moves and primary release subtract the current first-pane logical origin and the press's offset inside the handle; both clamp to the feasible range. The dispatcher emits an owned size and the handle's ordinary `ActionRequest` only for changed values. Execute it through the command registry/host and recompose; it never writes application state.

Capture retains pointer identity, grab offset, orientation, handle size and action name, not live tree handles. `refresh` at every accepted replacement returns the resolved first size and preserves a compatible drag. Handle removal/hiding/disabling, action/orientation/handle-size changes end capture. `PointerCancel` for the captured pointer, logical Cancel or unmodified Escape end capture while retaining the last accepted size; later release requests no deferred action. Foreign pointers, secondary buttons and additional presses cannot change capture. Other non-pointer events end the drag before their ordinary routing. Invalid input leaves capture unchanged.

When the supplied eligible focus is the handle, Left/Right adjust a horizontal split and Up/Down adjust a vertical split, including repeated keys and corresponding logical gamepad Navigate events. Home/End select limits; Activate proposes one positive step. Modified or orthogonal keys pass through. Bounds suppress redundant commands. Parent-size changes use Flex's resolved clamp; the host stores `refresh.size` before the next composition. Minima that cannot fit remain clipped and lock adjustment.

Host OS capture, capture-loss cancellation and resize cursors remain explicit adapters. The [Settings host](../guides/settings-starter.md#resize-the-sidebar) wires them with the same resolved geometry. [Owner checks](../../tests/input/split_pane_tests.cpp) cover both axes, nested Flex, scrolled/padded coordinates and clip/hit/paint agreement, drag replacement/lifecycle, cancellation, keyboard/gamepad and resize clamping.

## Implemented controlled scrollbars

[scrollbar.hpp](../../include/tessera/input/scrollbar.hpp) supplies `scrollbar_geometry(input, id, scroll_id)` and host-owned `ScrollbarDispatcher(id, scroll_id, keyboard_step = 16)` for the public controlled composition. Geometry joins the accepted ScrollView viewport/extent/offset with its sibling track and generated thumb, reports `ScrollbarAxis` from the generated track direction (Column: vertical, Row: horizontal), diagnoses stale authored metrics, and shares ordinary clipping, disabled/modal eligibility, hit testing and semantic actions. Missing/hidden controls are absent; no overflow or zero travel is inert.

A primary thumb press returns focus and captures the pointer/grab offset without moving content. Matching moves and primary release request a clamped main-axis offset and the thumb's ordinary action only for changed values, preserving the cross-axis offset. The host executes the command and stages both content and thumb before accepting; handled input must not also run ordinary pointer activation. Track clicks do not page. Focused main-axis arrows (Up/Down vertically, Left/Right horizontally), corresponding Navigate, Home/End and Activate share this path; the finite positive step defaults to 16. Modified and cross-axis keys pass through.

Refresh every accepted replacement, including removal. Its update observes the canonical layout-clamped host offset without an action. Capture holds only owned pointer/grab/binding/axis/geometry values, never borrowed handles. Compatible offset-only replacements retain capture; removal, hiding, disabling, full clipping, changed action, viewport, thumb size or range cancel it. Matching PointerCancel, logical Cancel and unmodified Escape retain the last accepted offset and suppress deferred release commands. Other non-pointer events end capture before ordinary routing, except wheel input. Foreign pointers/secondary releases cannot steal capture; failed calls preserve state.

Wheel routing and focus reveal continue to own the same host offset through `route_scroll` and `scroll_into_view`; they do not maintain a scrollbar-specific value. Hosts remeasure/recompose and store the accepted clamp after resize or content change. The [guide](../guides/scrollbar.md), [owner tests](../../tests/input/scrollbar_tests.cpp) and [Settings consumer](../guides/settings-starter.md#scroll-the-sidebar-and-form) own the complete procedure and validation limits. Track paging, a coordinated two-axis corner and native accessibility are not introduced.

## Host boundary

The host polls platform devices and translates their data into normalized Tessera events. Tessera does not poll OS input APIs.

The [Win32 example host](rendering.md#implemented-win32-vulkan-example-host) is the first native normalization. The mouse is `PointerId` 1; client pixels map to logical positions by its pixel-center rule, and timestamps come from the monotonic performance counter. Left/right/middle messages become primary/secondary/middle down/up with shift/control/alt/super modifiers. The host captures the mouse while any button is held and releases capture after dispatching the last up. It sends `PointerCancel` on capture loss it did not initiate (`WM_CAPTURECHANGED`), `WM_CANCELMODE`, `WM_KILLFOCUS`, and `WM_MOUSELEAVE` with no button held (clearing hover). Input before the first layout snapshot is ignored. Returned action requests run after dispatch; the example maps `start-game` to a title change and `quit-game` to orderly shutdown.

The same host translates `WM_KEYDOWN` into [focus dispatch](#implemented-prototype-focus-dispatch) commands, following the baseline below: a handled key press becomes one logical command and never also a `KeyDown`. Tab is `FocusNext` (Shift+Tab `FocusPrevious`), arrow keys are `Navigate` with `repeat` taken from the message's previous-key-state bit, Enter and Space are `Activate`, and Escape is `Cancel`. The OS auto-repeat drives traversal and navigation; repeated Enter/Space/Escape messages are dropped, so one press activates once. Keys pressed with Ctrl or Alt and unmapped keys go to the system. Host press policy: a primary `PointerDown` whose dispatch records a press owner also calls `focus` on that owner, so keyboard navigation continues from the button last pressed; the dispatcher's own rule that pointer dispatch never moves focus is unchanged. The focus dispatcher is refreshed with the pointer dispatcher at each update point. The host shows focus through a `:focus` rule in its [prototype style sheet](styling.md#implemented-prototype-style-resolution).

Gamepad input reaches the same commands; the host owns polling, dead zones, and repeat. By default it prefers the first connected XInput controller and otherwise reads a standard DualSense through the [DirectInput adapter](../../examples/vulkan-menu/directinput.hpp). Polling occurs only while its window is in the foreground; empty devices are rescanned at most once per second. DirectInput uses foreground nonexclusive acquisition and single-attempt reacquisition after focus loss. It releases disconnected devices and selects exact vendor/product descriptors rather than guessing other HID mappings. Switching input sources resets held-input suppression. A missing sample, as on disconnection or focus loss, resets the policy. The device-independent [gamepad policy](../../examples/vulkan-menu/gamepad.hpp) maps each sample. The D-pad takes precedence over the left stick, whose radial dead zone engages a direction above half deflection and releases it at XInput's recommended left-stick dead zone (7849/32767). The dominant stick axis selects the direction, vertical on ties, as is diagonal D-pad input. Each change of held direction is one `Navigate`; holding it repeats with `repeat` set after 400 ms and then every 120 ms, at most once per sample. XInput A/B and DualSense Cross/Circle press edges are `Activate`/`Cancel`, emitted after navigation. DualSense accepts Sony VID `054c`, PID `0ce6`, sets left-axis range [-32768, 32767], maps DirectInput button indices 1/2, inverts left Y from down to up, and maps the first POV hat (clockwise hundredths of a degree, with low-word `ffff` neutral) to the same D-pad bits. USB/Bluetooth enumeration follows the device descriptor; supported configuration evidence is owned by [support](../reference/support-matrix.md). Input already held when samples begin is ignored until released, so connecting a controller or refocusing the window never acts.

The host's explicit `--joycons` mode instead combines the first original Joy-Con (L) and (R) descriptors, Nintendo VID `057e` and PIDs `2006`/`2007`, held vertically. Both sides must provide a sample; losing either side suppresses commands until a complete pair returns through the same held-input policy. In the ordinary Bluetooth simple report, L button indices 0/1/2/3 become left/down/up/right; the L POV is rotated 90 degrees to map 27000 to up, and becomes an eight-way stick direction with no analog magnitude. Unused axis fields and the R stick are ignored. R buttons 0/2 (A/B) become activate/cancel. The host sends no report-mode, sensor, rumble, or calibration commands. This profile does not accept Pro Controllers, Joy-Con 2, USB adapters, or a single sideways Joy-Con. The [native smoke](../../examples/vulkan-menu/main.cpp) checks both descriptor mappings and the shared policy with scripted samples.

`WM_MOUSEWHEEL` and `WM_MOUSEHWHEEL` become one `Scroll` each at the message's screen position converted to client pixels and then to logical coordinates. One `WHEEL_DELTA` is 40 logical units and partial deltas scale proportionally; a forward vertical wheel reveals content above (negative Y), and a rightward tilt content to the right. The host passes the event to [scroll routing](#implemented-scroll-routing), stores the returned offsets, recomputes layout, and refreshes both dispatchers at that update point. Host reveal policy: when a logical command moves focus to another node, the host calls `scroll_into_view` for it and applies the result the same way. At a resize or DPI update point, focus whose `scroll_into_view` requested no change before the new layout is revealed the same way if the new layout hides it; focus the user scrolled away from stays out of view. Pointer press-to-focus does not reveal, so a click never moves the pressed button out from under the cursor.

## Implemented event contract

[event.hpp](../../include/tessera/input/event.hpp) defines `InputEvent`: a host monotonic timestamp in microseconds (non-negative, non-decreasing within one stream) and one of these values:

| Event | Contents and rules |
| --- | --- |
| `PointerMove`, `PointerDown`, `PointerUp` | `PointerId`, position in [layout](layout.md) logical coordinates, `primary`/`secondary`/`middle` button for down/up, `Modifiers` |
| `PointerCancel` | The host abandoned the pointer (lost window focus, capture loss, device removal) |
| `Scroll` | Position and delta in logical units; positive values reveal content further right/down |
| `KeyDown`, `KeyUp` | Logical (layout-mapped) `Key`: navigation/editing keys, `a`-`z`, digits, F1-F12; `repeat` on key down; modifiers |
| `TextInput` | Nonempty committed UTF-8 text; never carries composition/IME state |
| `Navigate` | `up`/`down`/`left`/`right` after the host applied dead zones and repeat policy; `repeat` flag |
| `FocusNext`, `FocusPrevious`, `Activate`, `Cancel` | Logical commands without payload |

A `PointerId` is host-assigned and stable from press until release or cancel. `Modifiers` holds shift, control, alt, and super flags. Characters never arrive as `Key` values. The host owns gamepad mapping, dead zones, and repeat timing. `validate(InputEvent)` reports non-finite positions/deltas (`invalid_number`), negative timestamps (`out_of_range`), undeclared enumeration values (`unknown_value`), and empty or invalid text (`empty_text`, `invalid_utf8`). Ordering across events is not validated.

Proposed baseline: a host delivers a given key press either as a logical command or as `KeyDown`/`KeyUp`, not both.

Key events and text input are separate operations. The presence of `TextInput` does not imply a text editor or IME support. Composition is a host-routed [string editing operation](#implemented-ime-composition-state), not an `InputEvent`; clipboard and editable-text semantics remain host or proposed contracts.

The host can route normalized `KeyDown` through the [keyboard shortcut boundary](commands.md#implemented-keyboard-shortcut-boundary) before translating unconsumed input into logical focus commands. Pass editing/IME consumption explicitly, stop routing on resolution errors, and execute returned invocations after dispatch. Chord scopes, conflict rules and command resolution are owned by that boundary; platform key normalization and input stream ordering stay with the host.

For gamepad shortcut routing, the host sends a normalized pressed button and exact other-held-button mask through the separate [gamepad shortcut request](commands.md#implemented-gamepad-shortcut-boundary). It handles device selection, physical button positions, trigger thresholds, press edges, repeats and held-input reset/suppression. An unconsumed request can then become an ordinary logical focus command. `InputEvent` and its logical navigation/activation events are separate from this in-process shortcut request; one physical press must produce at most one command invocation.

## Hit testing and propagation

### Implemented rectangular hit testing

[pointer.hpp](../../include/tessera/input/pointer.hpp) defines `HitTestInput`, borrowing a coherent `UiTree`, its resolved-style span, and its `LayoutResult` for one query. `hit_test(input, position)` returns a `HitTestResult` with an optional target; a successful query outside all eligible boxes has no target, whereas invalid input has no result value.

- Scan boxes in the reverse of the [paint order](rendering.md#implemented-paint-generation): tree preorder with siblings in the [`z_index` stacking order](layout.md#implemented-stacking-order). Every eligible Box/Text can be a hit target, including a label without a binding and a transparent or zero-opacity box.
- Use border-box rectangles, including their border area. Left/top edges are inclusive; right/bottom edges are exclusive. Zero-area boxes never hit. Corner radius does not cut away the rectangular hit region.
- Display-none subtrees are absent. Visibility is local: a hidden box is excluded, but a visible descendant remains eligible. A node's boolean `disabled` property defaults to false and excludes its entire subtree when true; disabled subtrees are skipped, so an eligible box behind them can receive the hit.
- A box with a recorded [layout clip](layout.md#implemented-prototype-algorithm) hits only inside that half-open rectangle, the one paint pushes; its clipped-out part falls through to eligible boxes below. Unclipped overflow can hit outside the parent or viewport. There is no implicit viewport clip or transform, no pointer-events property, and no dependence on draw commands or renderer state. [Scroll offsets](layout.md#implemented-prototype-algorithm) are already applied to recorded geometry and clips, so hit testing needs no separate scroll mapping. Transforms must add shared coordinate semantics before they arrive.

`validate(HitTestInput)` uses the same tree/style/layout snapshot checks as [paint input](rendering.md#implemented-paint-generation), without a shaper requirement. Missing inputs, style count/values, displayed topology, foreign handles, parent indices, recorded edges/visibility, and numeric geometry are rejected with the same located codes. `hit_test` also validates the point under `/position`. Callers must recompute layout after geometry/text changes; validation does not detect every stale dimension or text metric.

### Implemented pointer dispatch

`PointerDispatcher` is a host-owned, single-stream object. `dispatch(snapshot, event)` accepts only `PointerMove`, `PointerDown`, `PointerUp`, and `PointerCancel`; other normalized events return `unsupported_event` at `/event`. It validates the event and snapshot before changing state. Timestamps must be non-decreasing across accepted events (`event_order` at `/timestamp` for backwards time), including after a tree replacement; equal times are allowed. Invalid calls leave the stream clock and pointer states unchanged. `reset()` clears both.

The owned `PointerDispatchResult` contains the current event's hit target, action requests, and pointer states sorted by `PointerId`. Each `PointerState` exposes position, the deepest/topmost `hovered` target, the `pressed` activation owner, `active`, and `primary_down`. Only values/handles are retained, never borrowed tree/style/layout pointers or callbacks.

- **Binding lookup.** From the hit target, walk toward the root and select the first eligible node with an `activate` binding. Hidden ancestors are skipped. This lets a Text label activate its containing button and lets release on the same button's padding match the press. At most one binding is selected; full event propagation, cancellation/default prevention, capture phases, and arbitrary callbacks are not implemented.
- **Press/release.** Primary down records that binding owner, without requesting an action. Primary up requests one activation only when a primary press exists and the release's binding owner is still the recorded owner, then clears press/active state. An outside down, a release without down, or release over another binding cannot activate. Repeated primary down while held does not replace the original press.
- **Move.** Moving out retains the press but clears `active`; returning to the same binding restores `active`, allowing a drag-out/back release to activate. Secondary/middle events update position/hover but neither start nor release the primary press.
- **Cancel.** `PointerCancel` erases only that pointer, produces no action, and makes a later release harmless. The host must send cancellation on focus/capture/device loss. Multiple pointers retain independent presses; there is no OS capture or device polling in the dispatcher.
- **Snapshot changes.** Each accepted dispatch refreshes all remembered positions against the supplied layout. `refresh(snapshot)` does the same without an event, timestamp change, or action, so stationary pointers can recover after geometry/style changes. An absent, hidden, or disabled press owner is cancelled and cannot revive before another press. By default (`PointerSnapshotPolicy::tree_identity`), a different tree identity clears all pointers before accepting new events; author IDs do not restore a press.

Continuously publishing hosts can opt in with `PointerDispatcher pointer{PointerSnapshotPolicy::compatible_author_ids};`. On replacement, remembered logical positions and held-button state survive and stationary hover is hit-tested against the accepted layout, even without a press or a stable hover ID. A press migrates only to the same unique author ID, node kind and `activate` action name. The dispatcher owns copies of that identity/binding, never a borrowed snapshot, and resolves fresh handles before evaluating the new view. Anonymous buttons still work within one tree but cannot migrate; duplicate IDs are rejected by `UiTree::create`.

In this mode, removal, missing ID/binding, changed kind/action, display-none, local hiding, inherited disabling, modal exclusion, inherited `pointer_events: false`, zero-area or fully clipped owner geometry cancels the press permanently. Partial clipping and layout changes are compatible while the owner remains pointer-eligible; an outside pointer retains the press but cannot activate until release hits its owner again. No coordinate or preorder-index fallback is used. A cancelled held press cannot revive on restoration or repeated Down; release followed by a fresh Down is required. `PointerCancel` and `reset()` still discard capture. Invalid policies report `unknown_value` at `/policy`; invalid snapshots/events leave all retained state unchanged.

Refresh every accepted presentation, including intermediate removals or changed bindings, and execute returned actions against their producing snapshot before replacement. Rejected staging must not refresh dispatchers. Refresh never emits an action; release emits at most one action targeting the current snapshot. This is logical activation continuity, not OS pointer capture, arbitrary drag routing or a reason to ignore focus/capture-loss cancellation. Host-owned logical coordinates must remain consistent; reset/cancel when that mapping changes discontinuously.

Hover is stored only on the hit target, and active only on its selected binding owner. Ancestor pseudo-state matching belongs to [style resolution](styling.md#implemented-prototype-style-resolution); stylesheet invalidation is not defined. Logical `Activate`/`Cancel` and `cancel` bindings belong to [focus dispatch](#implemented-prototype-focus-dispatch).

### Implemented scroll routing

[scroll.hpp](../../include/tessera/input/scroll.hpp) defines two stateless operations over the same `HitTestInput` snapshot and validation as [hit testing](#implemented-rectangular-hit-testing). Both return `ScrollUpdate` values (scroll box handle and new requested offset), innermost box first and only for boxes whose offset changes. Tessera keeps no scroll state: the host stores each offset in its [`LayoutInput::scroll_offsets`](layout.md#implemented-foundation-contract) span and recomputes layout at its next update point, then refreshes pointer and focus dispatch as for any snapshot change. Neither operation requests an action.

- **Routing.** `route_scroll(snapshot, scroll)` hit-tests the event position with the ordinary rules and returns that target, the updates, and the `remaining` delta. Starting at the target and walking toward the root, each eligible scroll box (locally visible and not disabled; hidden scroll boxes are skipped as hidden binding owners are) moves each axis by the remaining delta within `[0, scroll_limit()]` and passes what it could not consume to the next. Axes chain independently. A position that hits nothing, including one over a disabled subtree with nothing eligible behind it, scrolls nothing. Non-finite positions or deltas are `invalid_number` at `/position` or `/delta`.
- **Reveal.** `scroll_into_view(snapshot, target)` moves each scroll box on the target's ancestry, innermost first, as little as possible so the target's border box lies within its viewport, carrying the adjusted position outward. A box larger than a viewport aligns its leading edge. Visibility, disabled state, and focusability do not matter; a handle from another tree is `stale_target` and a display-none node `hidden_target`, at `/target`. Results are float arithmetic, so a revealed trailing edge can land within rounding of the scroll limit rather than exactly on it. A misalignment of at most four `float` epsilons relative to the larger of the span's and viewport's edge magnitudes, plus the box's offset, counts as none, so revealing an already revealed target in the laid-out result requests no change and an empty result can mean "in view".

Scroll anchoring, smooth or animated scrolling, keyboard page/home/end scrolling, and latching an in-progress wheel gesture to one scroll box are not defined.

### Action registration and lifetime

Host action registration is explicit. The foundation stores `activate`/`cancel` and tree-branch `expand`/`collapse` action names and rejects names absent from the caller's `ValidationContext.actions`; see [UI model](ui-model.md).

Implemented contract: Tessera never stores host callbacks. Pointer and focus dispatch produce `ActionRequest` values (binding name, owned action name, target binding-owner `NodeHandle`) and returns them to the host. The host runs its own action implementations after dispatch returns, and applies resulting mutations at its next update point, so no callback runs during traversal and callback lifetime is entirely host-owned. A request's target handle is valid only while the producing tree snapshot is alive; after replacement, `UiTree::get` rejects stale targets. Pointer replacement follows the explicit policy above; it never retargets previously returned action requests.

## Event-to-action boundary

Normalized device events describe interaction; application-facing actions describe intent. Pointer, keyboard, gamepad, touch, accessibility, and external automation should reach the same declared action path after eligibility checks. Components do not directly call host functions; an action request resolves to an application command under [commands](commands.md#proposed-invocation-path). The implemented `ActionRequest` contract above is the baseline. Prototype [focus activation](#implemented-prototype-focus-dispatch) and [semantic activation](semantics.md#implemented-prototype-projection) return the same request as pointer activation under the same disabled/hidden eligibility; value-setting/open/back payloads and generation-aware external invocation are proposals requiring validation and lifetime rules before extending it.

[Semantics](semantics.md) owns exposed roles/names/action availability. It consumes input state and refers to actions here, rather than duplicating focus or dispatch policy.

[Inspection operations](inspection.md#proposed-target-resolution-and-operations) resolve targets before entering this path. Semantic activate/set-value and raw pointer/key injection are distinct operations with the same eligibility constraints. Automation must not turn unsupported text editing or value actions into direct property mutation.

### Implemented edit gesture host boundary

The [command gesture adapter](commands.md#implemented-edit-gesture-boundary) consumes normalized completion/cancellation input after ordinary traversal and before host publication. Hosts route its consumed result or error before requesting shortcut/navigation/activation actions, translate capture loss to `PointerCancel`, and call its update-point refresh or explicit owner-change cancellation before reload/disposal. Gesture identity, transaction ownership, exact terminal matching and closure diagnostics are owned by commands. This adapter does not add value-editing actions to document nodes.

## Interaction state

Input owns interaction behavior. Pointer hover/active, inherited disabled filtering, and prototype focus are implemented in this page. The host passes the resulting states to the [prototype style resolver](styling.md#implemented-prototype-style-resolution) for `:hover`, `:active`, `:focus`, and `:disabled` rules. Host updates must resolve styles/layout and call `refresh` or dispatch with the new snapshot. Disabled focus policy and automatic style/layout/paint invalidation remain to be defined.

## Focus and navigation

Keyboard and gamepad operation are architectural requirements even though pointer interaction is delivered first. Model focusable nodes, traversal order, directional navigation, activation, and cancel/back from the beginning.

### Implemented prototype focus dispatch

[focus.hpp](../../include/tessera/input/focus.hpp) defines `FocusDispatcher`, a host-owned, single-stream prototype over the same `HitTestInput` snapshot and validation as [hit testing](#implemented-rectangular-hit-testing). It stores only the focused handle, the author IDs of that node and of the other focusable nodes before and after it in preorder, the tree identity, and the stream clock. It does not extend JSON v1.

- **Eligibility.** A node can take focus when it is displayed, locally visible, and not disabled by itself or an ancestor (the hit-testing rules), and its `focusable` property is true; absence means false. Opacity, zero area, and clipping do not affect eligibility, so a fully clipped node stays focusable until scrolling can reveal it.
- **Commands.** `dispatch` accepts `FocusNext`, `FocusPrevious`, `Navigate`, `Activate`, `Cancel` and unmodified Home/End `KeyDown`; other events are `unsupported_event` at `/event`. Hosts translate other keys and gamepad buttons into logical commands. Home/End move to the first/last eligible collection item when focused on an item, otherwise doing nothing. Event validation and the non-decreasing timestamp rule (`event_order` at `/timestamp`) match pointer dispatch, and rejected calls leave state unchanged. The owned `FocusDispatchResult` holds the focused handle and action requests. `reset()` clears focus and the clock.
- **Sequential traversal.** Eligible nodes are ordered by tree preorder. `FocusNext` moves to the first eligible node after the focused one and wraps to the first; `FocusPrevious` mirrors it. Without focus, they select the first or last eligible node.
- **Directional movement.** `Navigate` compares border boxes in root logical coordinates. A candidate must lie entirely beyond the focused box's edge in that direction; touching is allowed, overlap is not. The lowest of (orthogonal projections do not overlap, edge distance, orthogonal gap, preorder) wins, so an aligned box beats a nearer unaligned one and equal candidates resolve to the earlier node. Without a candidate, focus stays; there is no wrapping. Without focus, every direction selects the first eligible node. `repeat` does not change selection.
- **Activation and cancel.** `Activate` walks from the focused node toward the root to the first eligible node with an `activate` binding, the [pointer binding lookup](#implemented-pointer-dispatch), so it requests exactly what a click on that node requests and a focused label activates its button. `Cancel` walks the same way for a `cancel` binding, starting at the root when nothing is focused. Neither moves focus; finding no binding requests nothing.
- **Recovery.** `refresh(snapshot)` and `dispatch` first reconcile the stored focus with the supplied snapshot. In the same tree, a focused node that became ineligible moves focus to the nearest following eligible node in preorder, else the nearest preceding one, else none. Under a different tree identity, focus is restored to the node with the same author ID, followed by the same rule. When the focused node had no author ID or its ID is absent from the new tree, focus recovers in its place: after the nearest preceding node that was focusable when focus was stored and whose author ID is present in the new tree, else before the nearest such following node, focus takes the first eligible node in preorder, else the last eligible node. Without a surviving neighbor, focus clears. Removing a focused menu item therefore focuses the item now in its place, or its predecessor when it was last. When `dispatch` moves or clears focus this way, the command is consumed: the result reports the recovered focus without further movement or action, so input aimed at a stale view cannot activate another node.
- **Programmatic focus.** `focus(snapshot, target)` focuses an eligible node, for example under a host's pointer-press policy. At `/target` it rejects a handle from another tree (`stale_target`), display-none or hidden nodes (`hidden_target`), disabled nodes (`disabled_target`), and non-focusable nodes (`not_focusable`). Pointer dispatch never changes focus.

Explicit neighbor overrides and general focus scopes remain proposed; the bounded root Modal scope is [implemented above](#implemented-modal-interaction). Focus dispatch does not scroll; hosts reveal a newly focused node through [scroll routing](#implemented-scroll-routing). [Semantic projection](semantics.md#implemented-prototype-projection) reports the focus a host supplies from this dispatcher; it does not store or recover focus. [Replay](replay.md#implemented-prototype-playback) plays logical commands and target-resolved focus steps through this dispatcher and can apply the host press and reveal policies. Directional wrapping options remain open.

### Implemented collection navigation

For focused `list_item`/`tree_item` rows, `Navigate` takes precedence over geometric movement. Up/Down use eligible item preorder within the nearest collection and stop at either end; List Left/Right do nothing. Tree Right requests `expand` on a closed branch or focuses its first eligible direct logical child; Left requests `collapse` on an open branch or focuses its eligible logical parent. Movement never selects. `Activate` selects through the ordinary action. Tab/Shift-Tab retain ordinary per-row traversal; disclosure buttons are not focusable. The host may focus their row on press.

A focused `radio` instead moves through the eligible radios of its nearest `radio_group` in preorder: Up/Left to the previous and Down/Right to the next, wrapping at either end, with Home/End reaching the first/last. Movement to another radio also returns that radio's `activate` request, so selection follows focus through the host command; no request is returned when focus stays. Tab/Shift-Tab enter a group once, at its eligible checked radio or else its first eligible radio, and leave the group from any of its radios. The [RadioGroup guide](../guides/radio-group.md) and [owner tests](../../tests/input/radio_group_tests.cpp) own this boundary.

A focused `tab` follows the same roving rule within its nearest `tab_list`, but only Left/Right (wrapping) and Home/End move and request the newly focused tab's `activate`; Up/Down fall through to geometric movement and never select. Tab/Shift-Tab enter a list once, at its eligible selected tab or else its first eligible tab. A focused control inside a `toolbar` moves among that toolbar's eligible controls in preorder with Left/Right (wrapping) and Home/End, without any request; Up/Down stay geometric. Tab/Shift-Tab enter each toolbar once at its first eligible control, regardless of checked toggles, and leave it from any control. Collection navigation takes precedence over toolbar navigation, and documents keep collections out of toolbars. The [Tabs and Toolbar guide](../guides/tabs-toolbar.md) with the [tabs](../../tests/input/tabs_tests.cpp) and [toolbar](../../tests/input/toolbar_tests.cpp) owner tests own this boundary.

A focused `option` uses the list rule within its nearest `listbox`: Up/Down move through eligible options in preorder and stop at either end, unmodified Home/End reach the first/last, Left/Right do nothing and movement never selects; `Activate` requests the focused option's action. `ComboBoxDispatcher`, constructed with the trigger ID, routes the `<id>-list` popup before ordinary input: opening requests the selected eligible option's focus, else the first eligible one; non-repeating Alt+Down on the focused closed trigger returns `open`; Escape, `Cancel`, Alt+Up and outside presses (including the trigger) return consumed dismissal with trigger focus; sequential focus commands return unconsumed dismissal; and hover requests an option's focus. Refresh dismisses a list whose trigger disappears or becomes ineligible. The [ComboBox guide](../guides/combobox.md) and [owner tests](../../tests/input/combobox_tests.cpp) own this boundary.

`ColorPickerDispatcher`, constructed with the trigger ID, routes the `<id>-panel` popup before ordinary input with the host's accepted `HsvColor`. Opening requests the area's focus; Alt+Down on the focused closed trigger returns `open`. A primary press on the area or hue strip focuses it and captures that pointer until release or `PointerCancel`; the press, captured moves and release request the clamped color under the pointer over the control's content box. The focused area maps Left/Right to saturation and Up/Down to value, and the strip maps Left/Down and Right/Up to hue with Home/End selecting its ends, all by configured steps. Each changed color is returned with the control's activate request for the host to execute; unchanged values are consumed without one. Tab moves between the two controls and past either end returns unconsumed dismissal; Enter, `Activate`, Escape, `Cancel`, Alt+Up and outside presses return consumed dismissal with trigger focus. The [ColorPicker guide](../guides/color-picker.md) and [owner tests](../../tests/input/color_picker_tests.cpp) own this boundary.

`tree_parent` preserves logical ancestry for flat layout rows. Disabled logical ancestors participate in shared input eligibility and `:disabled` styling. If a surviving focused tree item becomes hidden/disabled, reconciliation first tries its nearest eligible logical ancestor, then ordinary neighbor recovery. This also handles author-ID replacement after controlled collapse. Removed keys use ordinary neighbor recovery. The [public guide](../guides/tree-list.md) owns controlled state, scrolling and command wiring; [owner tests](../../tests/input/collection_tests.cpp) cover navigation, state, rejection and codec boundaries.

Map gamepad input into logical navigation/activation/cancel actions at the host boundary. Dead zones and repeat policy must have an explicit owner, as in the [Win32 host](#host-boundary). Do not put device-specific polling in buttons.

Delivery scope is owned by [current](../roadmap/current.md) and [backlog](../roadmap/backlog.md).

## Proposed overlay interaction

## Implemented logical string editing

[text_edit.hpp](../../include/tessera/input/text_edit.hpp) defines owned `TextEditState`, revision-addressed `TextEditRequest`, selection/insertion/erase/move operations and `TextEditPolicy`; [text_edit.cpp](../../src/input/text_edit.cpp) implements pure candidate transforms. The host owns accepted observations, publication, history and lifetime allocation. `make_text_edit_state` requires a nonzero host owner that the host never reuses, starts revision one, and places anchor and caret at the buffer end. `edit_text` returns a complete candidate without mutating its input or invoking application code; hosts publish it only through their ordinary eligibility and command/update boundary.

- **Text and indices.** Buffers and inserted values are valid UTF-8, bounded to 4096 bytes, and reject CR/LF. No normalization changes stored bytes. Selection anchor and caret use byte offsets at Unicode scalar boundaries, including the buffer end. Reverse selection is valid. Insert replaces the half-open interval between anchor and caret, then collapses both to the inserted end. Erase deletes the selection, or one scalar backward/forward at a collapsed caret; buffer boundaries are safe no-ops. The replacement limit accounts for removed bytes before insertion.
- **Movement.** Left/right move one scalar, or collapse a non-extended selection to its respective edge. Home/end address buffer start/end. Extension preserves the anchor; other movement collapses it to the new caret. Scalar movement is distinct from grapheme, BiDi and visual caret services under [text](text.md). No platform index conversion or editable Text widget is implied.
- **Identity and rejection.** Every accepted operation increments revision, including selection changes and no-ops. Requests must match owner and revision. Invalid observations, stale identities, split/out-of-bounds selections, malformed UTF-8, oversized/multiline values, unknown operation enums and revision exhaustion return located `/edit` diagnostics without a candidate. Revisions never wrap. Host cancellation restores bytes/selection with a newer revision; owner removal/recreation requires a fresh owner.
- **Eligibility.** Disabled policy rejects all operations except composition cancel. Read-only policy permits movement/selection and rejects insertion/deletion and composition start/update/commit. Hosts derive policy from their coherent UI/command state and suppress shortcut/focus routing for consumed editing input. The transform performs no tree traversal or implicit eligibility query.

The [editor consumer](../integrations/path-finder.md#implemented-in-process-panel-fixture) maps committed `TextInput` and supported normalized editing keys into these requests after ordinary focus/eligibility checks, then uses host-owned gesture transactions for value changes. The [Settings consumer](../integrations/settings-app.md#implemented-form-skeleton-boundary) uses the [composed form field](ui-model.md#implemented-c-form-authoring) to observe the same logical state through ordinary Text and stages host-owned command candidates before publication. [Logical editing checks](../../tests/input/text_edit_tests.cpp) cover Unicode scalar boundaries, supplementary characters, reverse selection, replacement limits, stale requests and policy failures; [source consumers](../../tests/cmake/consumer/main.cpp) exercise the public boundary. Asynchronous clipboard, core caret geometry and serialized logical edit events follow the proposed boundary below.

### Implemented IME composition state

`TextEditState::composition` holds one optional uncommitted preedit. `TextCompositionStart` captures the current selection as the replacement range with an empty preedit; its ID is the revision the start produces, so IDs are unique per owner and never reused. `TextCompositionUpdate` replaces the whole preedit and its caret, a UTF-8 byte offset at a scalar boundary within the preedit. `TextCompositionCommit` replaces the captured range once with the platform's result text, which may differ from the last preedit, and collapses the caret after it. `TextCompositionCancel` discards preedit and keeps committed bytes and selection. Every accepted step increments the revision like other edits.

- **Isolation.** While a composition is open, committed bytes and the selection stay fixed: selection, insertion, erasure, movement and a second start fail with `composition_active`. Update, commit and cancel must name the open ID; a closed or replaced ID fails with `no_composition` or `stale_composition`. Preedit uses the same UTF-8, single-line and 4096-byte checks as committed text, applied to the composed result. Commit cannot also arrive as `TextInput`; the host routes each platform result once.
- **Observation.** `validate(const TextEditState&)` checks a complete observation, including that the composition names a revision no later than the state and the retained selection. `display_text_edit` returns the presented string with preedit spliced over its range, the preedit byte range and a caret collapsed to the preedit caret; without composition it returns committed text and selection. Lowering uses it, so the [TextInput composition](ui-model.md#implemented-c-form-authoring) presents preedit through ordinary Text.
- **Ending.** Focus loss, owner removal, disabled/read-only transitions and reload are host update points that cancel; cancel is accepted under any policy so a host can always close a session, and it never commits preedit. A rejected commit leaves the composition open; hosts cancel it to close the platform session.

[Owner checks](../../tests/input/text_edit_tests.cpp) cover Japanese preedit replacement of a selection, commit/cancel, interior and supplementary-scalar carets, unique IDs, duplicate/late steps, isolation from ordinary edits, buffer limits, policy and malformed observations. Decoration ranges, reconversion, core caret geometry and serialized composition events remain proposed.

### Implemented Inspector IME host

The [Inspector application](../guides/inspector-hierarchy.md#japanese-ime-composition) routes Windows IME sessions to its focused eligible name editor through the existing staged name command. The optional [Win32 host](../../examples/settings-starter/native_win32.hpp) attaches the default input context only while the application reports editing and hides the default composition window. It reads `GCS_COMPSTR`, `GCS_CURSORPOS` and `GCS_RESULTSTR`, converts strict UTF-16 to UTF-8 and the UTF-16 cursor to a byte offset that never splits a surrogate pair, and delivers start/update/commit/cancel; consumed results produce no `WM_CHAR`. Keys and characters during a session stay with the IME. Malformed results and `WM_IME_ENDCOMPOSITION` without a result cancel. A pointer press first asks the IME to complete, so its result commits before the press moves focus; window focus loss, or any application focus change, cancels the platform session. Without a composition callback, as in the Settings starter, Windows keeps its default IME UI and committed `WM_CHAR` routing.

The application cancels any open preedit before input that can move focus, selection or menus, and addresses each step to the item and owner that started it, so a late step cannot redirect to another item. A rejected commit closes the composition and keeps committed bytes with recoverable feedback. It derives a logical caret rectangle from the accepted layout and its text service; the host maps it with the input/rendering scale for `ImmSetCompositionWindow` and `ImmSetCandidateWindow`. Native smoke injects composition strings in place of an IME; physical IME sessions remain unvalidated.

### Implemented Inspector copy/paste host

The [Inspector application](../guides/inspector-hierarchy.md#host-and-observation-boundary) wires exact, initial Control+C/V to synchronous host clipboard services for its focused eligible name editor. Copy extracts the selected committed UTF-8 bytes without changing edit state. Paste captures the item, owner, revision and selection before reading owned text, rechecks the same observation and focus/eligibility afterward, and submits an ordinary `TextEditInsert` through the existing staged name command. Empty selections on copy and empty text on paste are no-ops. Service, Unicode, embedded-NUL, single-line, size and presentation failures retain accepted UI/edit state and report located diagnostics. The Windows application adapter supplies bounded `CF_UNICODETEXT` access and strict UTF-16 conversion; core APIs acquire no platform types or implicit clipboard calls. Cut, asynchronous results, generalized editing-owner declarations and clipboard replay remain proposed.

## Proposed editing, IME, and clipboard boundary

An editable TextInput component supplies the minimum string property editor: a Unicode UTF-8 logical buffer, caret, selection, insertion/deletion, and left/right/home/end navigation. Runtime editing state belongs to the editing owner independently of source text; authored property source origins identify edit targets, not caret offsets. Multiline behavior is a separate consumer-driven extension; rich-text editing is outside this contract. Caret movement/deletion follows the declared [text index and segmentation services](text.md), and consumed editing keys must not also navigate or activate surrounding UI.

[Semantics](semantics.md) already exposes the presented value of [TextInput and NumberInput](../guides/text-number-input.md); expose selection state there and caret/selection/scroll geometry from the settled revision. Deterministic replay records normalized logical edit/composition and clipboard-result events with owner/revision identity, rather than relying on live clipboard contents or platform completion timing. The concrete replay encoding is a [replay](replay.md) contract decision. A Tessera Inspector string editor verifies this boundary through ordinary focus and command/transaction paths.

Committed `TextInput` stays separate from the [implemented composition steps](#implemented-ime-composition-state). A text-editing contract still needs explicit replacement ranges, caret geometry and copy/cut/paste requests. Declare index units and validate ranges against the document revision; UTF-8 bytes, graphemes, and glyph indices are distinct under [text](text.md).

The host normalizes platform IME events, owns clipboard access, and receives caret/selection geometry for candidate-window placement. Core stores editing state without platform types or implicit clipboard calls. Composition cancellation, focus loss, asynchronous paste, read-only/disabled policy, and stale replacement ranges need explicit fixtures. Japanese composition is a first-class requirement; boundary design can precede platform adapters and editable TextInput implementation.

### Proposed editing request rules

An editing owner exposes an immutable UTF-8 buffer revision, a half-open selection range, and a caret affinity. Replacement ranges and selection offsets use UTF-8 byte offsets at scalar boundaries of that revision; grapheme navigation is a separate [text](text.md) service. Hosts convert UTF-16 platform indices before submitting an event and reject invalid/split surrogate conversions. Every request names the live editing owner and buffer revision; stale owner/revision or out-of-bounds/split-scalar ranges fail before changing text. A `Text` display node does not acquire editability through this proposal.

Composition start, update, commit and cancel follow the [implemented state rules](#implemented-ime-composition-state). Updates may later carry decoration ranges within the preedit, such as converted clauses. Committed `TextInput` outside composition requests one selection replacement. No normalizing or reshaping operation silently changes stored bytes.

Navigation commands must not activate menu bindings while the host marks them as consumed by composition. Core should publish caret/selection geometry in logical coordinates from the settled revision; until then the [Inspector host](#implemented-inspector-ime-host) derives it from its own layout and text service, and the host converts it for platform candidate-window placement using the same viewport/scale as input/rendering.

Copy requests the selected committed bytes and leaves state unchanged. Cut requests clipboard write followed by selection deletion only after the host acknowledges a successful write for the same owner/revision/selection; failure leaves the buffer intact. Paste returns owned UTF-8 text through an asynchronous request carrying the captured owner/revision/range. A changed selection or buffer cancels it; no paste completion redirects to the newly focused editor. Clipboard unavailable, invalid UTF-8, denied access, or size-limit failure returns a located host diagnostic. Read-only owners allow selection/copy but reject cut/paste/commit; disabled owners reject editing and clipboard requests. The host performs no clipboard call inside traversal.

Open decisions: concrete editing event/result types, editable-owner declaration, clipboard byte limits, newline policy, composition decoration and reconversion, and grapheme/caret navigation service. Remaining fixtures include reload during composition and delayed paste after selection/focus changes. Platform adapters verify their own IME behavior against the composition fixtures.

The [Web editing adapter](../proposals/web-host.md#proposed-text-editing-adapter) may use browser-native input facilities alongside GPU visuals. It translates index units, revisions, focus, and composition into this same contract without exposing browser-specific controls in the UI model.

## Proposed typed drag and drop

Drag-and-drop payloads are typed values, not bytes or strings. A payload declares a MIME-like type ID (for example a file path, asset reference, node reference, color, material or image reference, or an application type), an optional schema for its value, a preview, the allowed operations (copy, move, link), and the source identity. A drop target declares accepted types and operations; eligibility is evaluated during the drag so hover feedback, semantic state, and the final drop agree. Dropping requests a [command](commands.md) inside a [transaction](commands.md#proposed-transaction-boundary); Tessera never applies the payload to application data. External OS or browser drags enter through the host, which converts them into typed payloads; clipboard data uses the same type vocabulary. Cancellation, a disappearing source or target, and keyboard-operated drag need explicit fixtures.
