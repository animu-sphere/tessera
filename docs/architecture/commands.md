# Commands and transactions

## Core invariants

- Every input source shares command eligibility and typed argument validation; discovery does not bypass execution-time generation/owner checks.
- Applications own command implementations, data mutations, transaction history and rollback outcomes.
- Reactive update batches and application edit transactions are distinct; a non-editing action does not create an undo token.

> [!NOTE]
> Implemented sections describe source-backed contracts. Proposed sections are Direction, and open decisions are Exploration. Neither schedules implementation; see [documentation authority](../README.md#contract-labels) and the [agent policy](../agent-policy.md).

## Implemented in-process command boundary

[commands.hpp](../../include/tessera/commands/commands.hpp) defines immutable owned `CommandRegistry`, `CommandSnapshot`, and `CommandInvocation` values. Registry copies share descriptor storage and a process-unique revision; replacement registries receive a distinct revision, even for equal descriptors. There is no global registry or callback. The host reserves command namespaces and passes the registry explicitly; subtree context follows the [context proposal](ui-model.md#proposed-context).

`CommandRegistry::create` validates a candidate atomically. IDs have at least two dot-separated `[a-z][a-z0-9_]*` segments and at most 128 bytes. Parameter names use one such segment. A descriptor owns its ID, nonempty label, description, category, availability (`both`, `development`, or `production`), and parameter schema. Explicit action-to-command mappings resolve exact registered IDs; a label or an unmapped action cannot implicitly resolve a command. Legacy actions keep their [input contract](input.md#action-registration-and-lifetime).

Parameters accept distinct boolean, binary64 number, UTF-8 string, string enumeration, and `CommandObjectId` alternatives. Numbers must be finite and meet optional inclusive bounds. Strings and object IDs meet a descriptor byte bound; object IDs are nonempty and belong to the host's permitted set for the settled generation. Enumeration choices are unique. Defaults are type/range checked on registration and materialized on resolution; object defaults additionally require the current permitted set. A default satisfies an omitted required parameter. Optional parameters without defaults remain absent. Unknown fields, missing required arguments, mismatched types, invalid references, and invalid defaults fail with located diagnostics and no partial value; no coercion occurs.

Bounds are 1,024 descriptors and action mappings, 64 parameters/arguments per command, 64 choices per enumeration, 4,096 bytes per presentation string or parameter string, and 10,000 permitted host object IDs. Descriptor string bounds can be smaller; an object-ID bound is nonzero. Registry revision exhaustion throws, as do allocation failures.

The host publishes `CommandSnapshot` at an update point with a nonzero logical generation, execution mode, owned query observations, and permitted object IDs. Generations and request sequences are host-issued and never reused within a session; they are independent of tree identities and Replay generation indices. Missing observations disable commands. A `query_error` disables the command and clears checked state, even if the supplied flags are true. Unknown observation IDs and invalid modes or metadata reject publication. `discover` returns owned metadata/observations ordered by ID; `lookup` uses exact IDs. Unavailable descriptors cannot be discovered or resolved; their lookup produces the same diagnostic as an unknown command.

`lookup_action` reads an exact explicit action mapping and returns the same metadata/observation as `lookup`. An absent mapping is `unmapped_action`; an unavailable mapped descriptor is `unknown_command`, as for direct lookup. It invokes no eligibility callback.

`apply_eligibility` validates and copies the authored document before tree/style/layout/semantic construction. It composes unavailable or disabled command state into the `disabled` property of explicitly mapped `activate` owners, preserving authored disabled state and ordinary ancestor eligibility. Always lower from the authored document to restore eligibility on a later update. Input targeting, pseudo-state resolution, focus, and semantic projection then read the same disabled property. Unmapped actions retain their existing behavior. This boundary supports activation bindings; [keyboard shortcuts](#implemented-keyboard-shortcut-boundary) reuse this eligibility, and cancellation bindings follow the invocation proposal below.

`resolve` checks generation, nonzero request sequence, invocation source, availability, eligibility, and arguments for a node-free request. `resolve_action` additionally borrows a coherent `SemanticInput` and verifies the live activation owner and exact binding through ordinary semantic action eligibility. All sources (pointer, keyboard, gamepad, accessibility, agent, and replay) use these checks. The resulting invocation owns normalized arguments, source/sequence, generation/revision, and an optional action owner handle; it retains its command observation without borrowing descriptor or tree memory. It exposes a const record and cannot be constructed by the requester.

Immediately before executing after dispatch returns, the host calls `recheck` against its current command snapshot and, for node invocations, current coherent UI snapshot, or uses the [execution adapter](#implemented-host-execution-and-result-boundary) that performs this check. A changed registry revision or observation identity rejects the invocation, including accidental reuse of a generation number. A removed/replaced, hidden, disabled, or differently bound node fails ordinary owner validation. A copied snapshot shares its identity. The host is responsible for pairing UI and command observations from one update and publishing later changes as a new generation. `recheck` performs no execution or sequence deduplication. Invocation handles are values, and a destroyed tree is never dereferenced; an author ID reused in a replacement tree does not retain ownership.

`permits_object` reads exact object-ID permission from the settled snapshot without callbacks. This API does not encode command schemas in UI JSON or Replay JSON. [Command checks](../../tests/commands/commands_tests.cpp) declare descriptors, queries, arguments, and object IDs as host fixture inputs, then replay the ordinary UI recording and resolve its action observations through that fixture. [The tool-panel example](../../examples/tool-panel/main.cpp) demonstrates disabled/enabled generations and host execution of a non-editing inspection command. Edit tokens use the [transaction boundary](#implemented-synchronous-transaction-boundary); serialized invocation/results and palette composition follow the proposals below.

## Implemented host execution and result boundary

[execution.hpp](../../include/tessera/commands/execution.hpp) defines `CommandHost`, `CommandExecutor`, `CommandOutcome`, and `CommandExecution`. The application supplies a synchronous `CommandHost::execute` implementation explicitly at each call; the registry, document and executor store no host callback. Invoke the adapter after input/core traversal returns. Its inputs, including a node invocation's coherent `SemanticInput`, remain alive until return. The adapter copies invocation identity and retains its immutable command snapshot before entering the host, so result validation uses the dispatched descriptor even if the host publishes a later snapshot.

The host owns one noncopyable, nonmovable executor per session, confines it to its creating UI thread, and issues increasing nonzero request sequences shared by all commands and input sources. Wrong-thread and recursive execution, and a sequence less than or equal to the highest entered execution, reject before the host runs. Registry/generation/owner recheck failures also reject before entry. Rejection returns `Result<CommandExecution>` without a value and does not consume a new sequence. Sequence gaps are allowed; accepting a higher sequence rejects every lower sequence thereafter. This constant-space rule rejects out-of-order delivery as well as duplicates, across generations and registry replacements. Sessions and sequence assignment remain host responsibilities; creating a second executor does not share deduplication state.

Once the host is entered, the sequence is consumed for success, cancellation, structured failure, malformed output, and exceptions. The outer result contains an owned `CommandExecution` pairing the complete invocation record with one outcome. Inspect `outcome.status` to distinguish success, cancellation and error; an outer value alone does not establish success. Standard host exceptions become `host_exception` at `/result/host`, preserving nonempty valid UTF-8 exception text within 4,096 bytes, otherwise using a bounded generic message. Nonstandard exceptions receive the generic diagnostic. Allocation failures propagate; a failure after entry keeps the sequence consumed and releases the recursive-execution guard. A host error does not establish rollback or restoration of application state, and the adapter does not automatically retry.

`CommandDescriptor::results` declares a named success object using the same `CommandParameter` scalar types, identifiers, bounds, required/optional fields and defaults as arguments. Registration validates argument and result schemas independently, each with at most 64 fields. An empty result schema means void success. Success permits only declared fields: omitted defaults are materialized, optional fields without defaults remain absent, and unknown, missing, type, range, enumeration and UTF-8 errors replace the whole result with located diagnostics under `/result/values`. Validation precedes copying caller-controlled values; oversized unknown field names are located with the fixed `<oversized>` token. No coercion occurs. Result object IDs are bounded nonempty opaque host identities and may identify newly created objects; unlike input arguments, they do not require membership in the earlier settled permitted-ID set. Later commands require publication of their permitted IDs through the ordinary input boundary.

A cancellation carries no values or diagnostics. An error carries no values and between 1 and 64 host diagnostics, including at least one error. Each diagnostic has a valid severity, nonempty UTF-8 code within 128 bytes, nonempty UTF-8 message within 4,096 bytes, and a UTF-8 JSON-pointer path within 4,096 bytes (empty root is allowed). The adapter prefixes valid host paths with `/result/host` and preserves byte offsets. Malformed statuses, payload combinations, diagnostics and success fields yield an error outcome with adapter diagnostics and no partial values. These are in-process owned values; serialization and asynchronous execution follow the proposals below.

[Command checks](../../tests/commands/commands_tests.cpp) exercise ordinary input and serialized UI replay requests through this adapter, with host-declared schemas and observations. The [tool panel](../../examples/tool-panel/main.cpp) uses it to inspect the selected item and validate the returned object identity before consuming the result.

## Implemented synchronous transaction boundary

[transactions.hpp](../../include/tessera/commands/transactions.hpp) defines a host-owned `CommandTransactions` session, weak `TransactionToken`, owned `TransactionRecord`, and synchronous `TransactionHost`. The application owns mutation, undo history and merge policy. The session owns a single open edit and a command executor; it is noncopyable, nonmovable and confined to its creating UI thread. Wrong-thread and recursive entry reject before any host callback. All host calls occur explicitly after dispatch returns; no application callbacks run during core traversal.

`begin` rechecks a resolved command and its coherent UI owner, validates metadata before copying, then calls the supplied host. Metadata has a nonempty UTF-8 label and optional merge hint, each within 4,096 bytes, at most 64 bounded nonempty UTF-8 affected object IDs permitted by the settled command snapshot, and an optional signed host timestamp. The owned record pairs metadata with the opening invocation, its logical request sequence, and a process-unique session identity. It has no wall-clock or history dependency. Session identity exhaustion and allocation failures throw.

A successful begin issues a weak token. Nested begin, malformed metadata, stale invocation and consumed opening sequences reject without host entry. Entering begin consumes its opening sequence for future begin requests even on failure; the executor reserves that sequence for the explicitly joined edit. A failed, cancelled, malformed or throwing begin issues no token: the host's begin contract requires atomicity, leaving no open application edit on any such outcome. Tokens do not retain the session or host. The same host instance must remain alive through closure; using a different host or foreign session rejects without consuming the active edit.

`execute_edit` explicitly joins a token. It accepts only the opening command and live action owner in the same registry revision, with a sequence at or after the opening request; using the opening sequence requires the identical invocation record. Later updates resolve fresh invocations with new sequences. Before editing, the session resolves the opening command and owner against the current settled generation, including original argument and affected-object permissions, then delegates invocation/result recheck and once-only execution to the [command executor](#implemented-host-execution-and-result-boundary). Continuous edits can span reactive batches and command generations while retaining one token. A node-owned edit retains its original tree handle; replacement trees, including ones reusing author IDs, invalidate it. Node-free edits have command/registry ownership only.

Ordinary pre-execution rejection with a valid local token, cancellation, host error, malformed command result and non-allocation exceptions request rollback once. An invalid or foreign token rejects without touching another edit. On a rejected invocation, rollback failures accompany the rejection diagnostics; on an entered command, they convert cancellation to an error or append to the existing error outcome, with no partial result values. Combined adapter diagnostics can exceed the host's individual 64-diagnostic bound. A failed rollback is an observed host error and does not establish restoration of application state. Allocation failures propagate; a token remains open if allocation fails before closure, so the host must explicitly recover or roll back. An entered command sequence stays consumed.

`execute` runs non-editing commands through the same executor without opening, joining or closing a transaction, including while an edit is active. Editing classification is an explicit host choice; descriptors carry no edit policy. Undo and redo can use this token-free path. Command and begin sequences share a host-issued increasing request stream; a begin reserves its opening sequence, and non-editing calls require a later sequence. A second session has independent execution deduplication state.

For a discrete edit, the host calls begin, executes one edit and commits after success. A continuous gesture begins on its first accepted edit, explicitly joins each later update and commits on completion. `commit` rechecks command/owner/object eligibility against the current generation and requires at least one successful edit. Invalidation or an empty edit requests rollback instead of commit and returns an error outcome. `recheck` performs the same eligibility refresh without editing or committing: valid state returns `true`; invalidation rolls back with `owner_changed` and returns no value, preserving the original diagnostics and appending rollback failures. Entry/token/host rejection changes no active edit. The host explicitly calls `rollback` for user cancellation, capture loss or owner removal/reload before publishing the replacement generation. The session subscribes to no input or owner lifecycle; the [gesture adapter](#implemented-edit-gesture-boundary) provides normalized input routing and explicit update-point checks.

Commit and rollback consume the token before host entry, even on failure, malformed output or allocation exceptions; no closure is retried and failed commit does not implicitly invoke a second boundary. Both return a `Result<CommandOutcome>`: outer rejection enters no host; an outer value requires checking its status. Boundary success is void; cancellation becomes `transaction_cancelled`, and structured errors/exceptions use the command outcome validation with locations under `/transaction/begin`, `/transaction/commit` or `/transaction/rollback`. Valid host diagnostic paths are relative to that phase's `/host` location. A closed or expired token cannot edit, commit or roll back. Session destruction releases records without callbacks; the host must finish an active edit before destroying either session or host. Closure settles synchronously before the host publishes its next UI generation.

[Transaction checks](../../tests/commands/transactions_tests.cpp) use host-owned inventory state/history with coherent reactive publication and ordinary serialized UI replay actions. The [tool panel](../../examples/tool-panel/main.cpp) lowers an amount caption into the full-tree style/layout/semantic/paint path across three edit batches, commits one history entry on normalized pointer release, then restores an Escape-cancelled edit through the gesture adapter. Asynchronous execution and serialization extend this boundary under the transaction proposal below.

## Implemented edit gesture boundary

[gestures.hpp](../../include/tessera/commands/gestures.hpp) defines `EditGesture`, `GestureInputResult` and `CommandGestures`; [gestures.cpp](../../src/commands/gestures.cpp) owns routing. The adapter borrows a `CommandTransactions` session that outlives it, retains one weak transaction token and an owned gesture declaration, and invokes no callbacks from destruction. Operations run on the adapter's creating UI thread after ordinary input traversal and before presentation publication; recursive or wrong-thread entry rejects with `/gesture` diagnostics. Hosts use the borrowed session for non-editing commands and its shared request sequence stream, but must not directly open or close its edit while the adapter has an active gesture. Finish or cancel before destroying the adapter, session or host.

A declaration has a nonzero host-issued `id`, optional normalized `PointerId`, declared `PointerButton`, and the transaction boundary's bounded metadata. `edit` begins and executes the first update; subsequent updates with the same declaration join the token and retain the opening command/owner under ordinary transaction checks. IDs increase and never repeat within an adapter. Delegating a begin attempt reserves its ID even when begin rejects; zero IDs or unknown buttons reject before reservation. An active gesture rejects another ID with `nested_gesture`; changing pointer, button or metadata rejects with `gesture_mismatch`, preserving the edit. Closed IDs reject with `stale_gesture`. The host classifies editing explicitly and calls no gesture operation for a non-editing command. `active` observes the open ID on the UI thread.

`complete(id, snapshot, host, ui)` commits through ordinary eligibility and nonempty-edit checks. `cancel(id, reason, host)` rolls back explicitly, including `owner_changed` before reload/disposal and `capture_lost` for host lifecycle notifications. A mismatched or closed terminal ID cannot close another edit. `refresh(snapshot, host, ui)` returns `false` for no active edit or delegates to transaction `recheck`, returning `true` for a valid open edit. The host calls it at every update point, including changes without input. Replacement trees invalidate node-owned edits even when author IDs survive; disabled/hidden owners, replaced registries, missing coherent UI and revoked object permissions close by rollback before publication. Node-free edits retain command/registry ownership; the host explicitly cancels them when their application scope is disposed.

`handle_input` validates the normalized event and a non-decreasing timestamp stream before refreshing eligibility. Rejected input advances no clock or gesture state. For a valid active gesture, `PointerUp` matching both pointer and button completes even outside the original box; matching `PointerCancel` cancels for capture loss; `KeyDown` Escape, including repeats/modifiers, or logical `Cancel` cancels for the user. Other events and unrelated pointers/buttons return an unconsumed result without closure. Pointer-free gestures use explicit completion and the same Escape/logical cancellation path. The host owns pointer capture, device mapping, gesture recognition, ordered terminal delivery and suppression of events from an earlier pointer lifetime; the adapter hit-tests nothing and translates no movement into values.

A handled terminal returns `consumed=true` and an owned closure outcome, whose status must be checked even when the outer result succeeds. The host suppresses subsequent shortcut/navigation/activation routing for consumed input; an error also ends routing. Duplicate terminal input after closure enters no host boundary. Command failure/cancellation and rejected edit invocations follow ordinary once-only rollback; closed tokens and reserved IDs prevent late edits from reopening the gesture. Rollback failure remains a located host error and proves no restoration. Allocation failures propagate; an edit left open retains its identity for explicit cancellation, while an already entered closure stays consumed. No subscription, automatic reactive publication, serialized gesture/token, platform capture or asynchronous execution is introduced.

[Gesture checks](../../tests/commands/gestures_tests.cpp) verify multi-generation edits against settled reactive values and full-tree layout/semantic/paint, one application history entry on release, pointer/keyboard/gamepad cancellation, lifecycle invalidation without an input event, declaration/clock rejection, shared non-editing execution, host failures and serialized ordinary pointer replay. The [tool panel](../../examples/tool-panel/main.cpp) uses normalized release and Escape after presenting each accepted edit.

## Implemented keyboard shortcut boundary

[shortcuts.hpp](../../include/tessera/commands/shortcuts.hpp) defines immutable owned `CommandShortcuts`, `ShortcutScope` and `ShortcutBinding` values, with data-only `ShortcutRequest` and `ShortcutDispatch`. The map retains a registry revision, tree identity, parent indices and copied declarations, never borrowed UI pointers or host callbacks. Copies share the immutable map. Rebuild it when replacing the tree or registry; publishing new command observations for the same registry/tree uses the same map with a fresh request generation.

`create` borrows a command snapshot, immutable tree and scope span. It validates the complete candidate before copying. Bounds are 64 scopes, 1,024 bindings across keyboard and [gamepad](#implemented-gamepad-shortcut-boundary) declarations in total and 128 bytes per command ID. Every command must be available in the supplied snapshot's mode, but disabled commands can be registered. Each root, including the absent global root, is unique. A chord is one declared logical `Key` and an exact match of all four `Modifiers` flags; duplicate chords within one scope reject with `shortcut_conflict` at the later chord and a message locating the earlier chord. Equal chords in distinct scopes are deliberate overrides, independent of declaration order or eligibility.

A subtree scope has a live root handle and each binding requires an ordinary `activate` owner within that subtree, including the root itself. A global scope has no root and may bind a node-free command or an activation owner. An owner must name the live node's exact activation binding and its explicit action mapping must target the binding's exact command ID. Foreign roots/owners, owners outside their scope, mismatched actions and mappings reject the candidate. Registration uses tree identity and declarations; style/command eligibility is checked during resolution and execution.

`dispatch` borrows coherent command/UI observations. It validates the normalized event, UI snapshot and focused handle, nonzero host request sequence, current request generation, map registry/tree identities and the 64-argument count before routing. It has no stream clock: host input routing owns non-decreasing timestamp delivery. A host-consumed event (for example editing or IME composition) returns consumed with no invocation. Events other than `KeyDown`, and unmatched key/modifier combinations, return unconsumed with no invocation.

Eligible focus uses the ordinary displayed, locally visible, focusable and ancestor-disabled rules. Subtree scopes are active on that focus's ancestry; absent or ineligible focus activates only the global scope. Hidden containers can contain locally visible eligible focus, as in ordinary input. The nearest active scope containing the chord wins; a nearer scope without that chord permits an outer match. The global match follows all subtree matches. A selected binding shadows outer/global bindings even when disabled, unavailable, hidden or repeat-suppressed. `repeat` defaults false: a repeated key for that binding is consumed without invocation; explicit repeat opt-in resolves another host-sequenced request. Resolution errors have no dispatch value and stop further routing; they never fall through to another command.

The host supplies settled arguments in each request. Node-owned bindings call ordinary `resolve_action`; global node-free bindings call `resolve`. Both use current query/object permission and schema/default checks and yield an owned `CommandInvocation` with keyboard source, request sequence and observation identity. Subtree activation ownership preserves ordinary stale-tree, hidden and disabled rejection through the [execution adapter](#implemented-host-execution-and-result-boundary), which the host calls after dispatch returns. Dispatch executes no application code, consumes no execution sequence and opens no transaction. Node-free global commands have command/registry ownership, as for other node-free invocations.

The [tool panel](../../examples/tool-panel/main.cpp) declares a panel-scoped logical Control+I activation of its inspection command. The [shortcut checks](../../tests/commands/shortcuts_tests.cpp) compare it with pointer, logical focus/gamepad, semantic and serialized UI replay observations through the same command/execution boundaries. Declarations and raw key events are host fixtures, not a command or shortcut recording schema. Platform key conventions, multi-key sequences, editable focus scopes and palette presentation extend this boundary through the proposals below.

## Implemented gamepad shortcut boundary

[shortcuts.hpp](../../include/tessera/commands/shortcuts.hpp) defines `GamepadButton`, `GamepadShortcutChord`, `GamepadShortcutBinding` and `GamepadShortcutRequest`. A `ShortcutScope` holds keyboard `bindings` and `gamepad_bindings` under one root. Both use the [keyboard boundary's](#implemented-keyboard-shortcut-boundary) immutable map, total declaration bounds, activation-owner validation, focus ancestry, nearest-match precedence, repeat suppression and command/execution checks. Keyboard and gamepad conflicts are independent; identical gamepad chords within one scope produce `shortcut_conflict` at the later `/scopes/<index>/gamepad_bindings/<index>/chord`, naming the earlier location.

Logical button positions are `south`, `east`, `west`, `north`, `dpad_up`, `dpad_down`, `dpad_left`, `dpad_right`, `left_shoulder`, `right_shoulder`, `left_trigger`, `right_trigger`, `left_stick`, `right_stick`, `select` and `start`, in that bit order. `gamepad_button_bit` returns the corresponding 32-bit mask, or zero for an undeclared enum. A chord names the newly pressed or repeated `button` and the exact `held` mask of other buttons from the same device/sample. The pressed button is excluded from `held`; no bits above bit 15 are accepted. Registration and dispatch reject undeclared buttons/bits with `unknown_value` and a mask containing the pressed button with `invalid_chord`, at `/chord/button` or `/chord/held` (prefixed by the declaration path during registration). An empty mask expresses a single-button chord; extra or missing held buttons never match.

The gamepad `dispatch` overload accepts this normalized chord with host generation, sequence, settled arguments, `consumed` and `repeat` flags. It validates the chord and shared request/UI boundaries even for consumed requests. A consumed request returns consumed without invocation; an unmatched chord returns unconsumed. A selected binding consumes repeat without invocation unless explicitly opted in, and its failure never activates an outer binding. Successful resolution records `CommandSource::gamepad`; the host executes the returned invocation after dispatch using its ordinary shared sequence stream. Dispatch retains no pressed-button state, device identity, timestamp or clock. Requests are in-process data, separate from `InputEvent` and the serialized replay event vocabulary.

Hosts own device selection, physical-label mapping, trigger thresholds, press-edge detection, held-state reset on focus/device loss, repeat timing and request ordering. Buttons held on connection/refocus must be suppressed until released. Route a normalized press through shortcuts before translating an unconsumed press to ordinary navigation/activation/cancellation; a consumed press or resolution error ends that routing. The [input host boundary](input.md#host-boundary) owns normalization and the [tool panel](../../examples/tool-panel/main.cpp) demonstrates synthetic left-shoulder + west inspection with the same owner/arguments as Control+I. The [shortcut checks](../../tests/commands/shortcuts_tests.cpp) verify matching, conflicts, bounds, eligibility, stale identity and shared execution sequences. Physical-device adapters and shortcut serialization follow the proposals below.

## Proposed command registry

Commands are the semantic operations an application exposes, such as `file.open`, `edit.undo`, `view.frame_selection`, or `node.delete`. They decouple widgets from application functions: a menu item, toolbar button, shortcut, gamepad binding, accessibility client, agent, or replay step requests a command instead of calling the application directly. This proposal extends the in-process boundary above; it does not change [JSON v1](../../formats/tessera-ui/README.md) or the implemented [action request](input.md#action-registration-and-lifetime) contract.

A command descriptor carries:

| Field | Meaning |
| --- | --- |
| ID | Stable, namespaced identifier; never a display string |
| Label, description | Localizable presentation text supplied by the application |
| Category | Semantic grouping for palettes, menus, and discovery |
| Shortcut | Optional declared key or gamepad chord; conflicts are diagnosed, not silently resolved |
| Enabled, checked | Query results the application derives from its own state, with an optional disabled reason |
| Argument schema | Typed parameters validated before invocation; no coercion |
| Result/error contract | Typed result or structured error returned to the requester |
| Availability | Whether the command exists in development builds, production builds, or both |

The application owns the registry contents and every implementation. Tessera stores descriptors and evaluates eligibility; it holds no callbacks inside core traversal, consistent with [action lifetime](input.md#action-registration-and-lifetime). The registry reaches a subtree through explicit [context](ui-model.md#proposed-context) rather than a global locator.

## Proposed invocation path

### Descriptor and eligibility rules

- Command IDs use dot-separated segments matching `[a-z][a-z0-9_]*`, with at least two segments. The application reserves its leading namespace and registers library namespaces explicitly; duplicate IDs fail before publishing the registry. Display labels never resolve commands.
- A descriptor is an owned immutable value in one registry revision. Availability is checked before discovery or resolution; production requests cannot discover or invoke a development-only descriptor. The host publishes eligibility queries together with settled UI state, without callbacks during traversal. A query yields enabled, checked, and an optional disabled reason, and errors fail closed.
- Arguments are a named object of declared required/optional booleans, finite numbers with inclusive bounds, UTF-8 strings with byte bounds, string enumerations, or host object IDs. Defaults are descriptor values validated on registration. Unknown fields, missing required values, type mismatches, and invalid references fail at the argument field; there is no coercion. Reuse the scalar vocabulary of [property metadata](ui-model.md#implemented-property-metadata), with command schemas owned here rather than added to UI JSON.
- An action binding resolves by exact command ID only when the host explicitly registers that action-to-command mapping. Existing action names retain the [input action](input.md#action-registration-and-lifetime) contract. The mapping, descriptor revision, and eligibility observation belong to one generation. A request carries that generation, command ID, arguments, invocation source, and logical request sequence; stale generations fail before any host implementation runs.
- Effective enabled state is the conjunction of ordinary node/ancestor eligibility and command eligibility. The host applies the same eligibility observation to pointer/focus dispatch, style, and semantic projection when settling the generation. It does not merely hide an action in the semantic adapter. Requests without a node use the same command query and argument validation.
- Dispatch returns an owned validated invocation. Immediately before executing it, the host rechecks generation, registry revision, and eligibility; changes reject the invocation instead of activating a replacement. Execution happens after traversal. Results are success with a declared serializable value, cancellation, or a structured error with command/request identity and located diagnostics. Host exceptions are converted at the execution adapter, never inside core.

```text
pointer / keyboard / gamepad / accessibility / agent / replay
        -> normalized event or semantic operation (input, semantics, inspection)
        -> ActionRequest after eligibility checks
        -> command resolution and argument validation (this page)
        -> application implementation after dispatch returns
```

A document binding keeps naming an action. A host may declare that action name as a command ID, so bound widgets, shortcuts, and external requests converge on one descriptor without new document fields. Command enabled state composes with node eligibility: a disabled node cannot request a command, and a disabled command makes its bound nodes report the disabled state through [semantics](semantics.md) in the same generation. Each invocation records its source (pointer, keyboard, gamepad, accessibility, agent, or replay) for diagnostics, transactions, and [replay](replay.md).

Commands evaluated or invoked from outside the UI tree, such as a palette or an agent, use the same eligibility query and argument validation. No source receives a private path or bypasses a disabled state. External discovery is exposed through the [agent capability manifest](../proposals/agent-capability-manifest.md#proposed-agent-capability-manifest).

## Proposed command palette

A palette composes ordinary components and uses the same registry, argument validation and eligibility as other command requesters. Search ranking and history stay application-owned.

Possible mechanisms: [command palette](../proposals/command-palette.md#proposed-command-palette). This direction is not an implementation task; only the active roadmap can require a bounded part.

## Proposed transaction boundary

This proposal extends the [synchronous boundary](#implemented-synchronous-transaction-boundary) and [normalized gesture adapter](#implemented-edit-gesture-boundary) with native capture/lifecycle integration, asynchronous request identities and richer host transaction policies. It defines no serialized token schema.

Reactive [update batches](reactive-runtime.md#proposed-update-batches-and-scheduler) coalesce view evaluation and effect delivery. This page owns application edit tokens and undo/rollback boundaries. A non-editing event can use a batch without a token; a continuous editing gesture can retain one token across several batches. Nested batch scopes joining an outer batch do not relax the single-level edit transaction rule below.

### Transaction rules

An application adapter owns a transaction token and every mutation. A discrete editing command requests one explicit begin/commit pair; non-editing commands request none. Continuous gestures begin once on the first accepted edit and commit on completion. Escape, capture loss, owner removal/reload, or command failure requests rollback once, even after multiple updates. Undo/redo implementations consume application history and do not implicitly open another transaction. A commit/rollback result settles before the next published UI generation.

Transactions are single-level: nested begin requests fail with a located diagnostic. A command invoked within a gesture may join its explicitly supplied token but cannot implicitly begin or commit it. Each token belongs to one host session, command/gesture owner, and logical request sequence; a closed or foreign token rejects later edits and a late asynchronous completion cannot reopen it. Merge hints never merge in core; the application decides history coalescing after a successful commit. Rollback failure is reported as a host error, without claiming application state was restored.

Long-running commands either perform no mutation until ready and then request a discrete transaction, or explicitly keep one gesture-owned token whose cancellation requests rollback. They use [async request identities](../proposals/async-resources.md#proposed-async-state) and publish transitions only at update points. Pending execution grants no exemption from command eligibility, stale-owner rejection, or the transaction token rules.

Tessera does not own application data history. It provides a common boundary so that UI-driven edits group consistently:

```text
begin_transaction(metadata) -> application mutations -> commit_transaction()
                                                     -> rollback_transaction()
```

Transaction metadata includes an ID, a label, a logical sequence (and host timestamp when supplied), the source (pointer, keyboard, agent, or replay), a merge/coalesce hint, and affected object IDs. A continuous gesture such as a drag, a transform handle, or slider scrubbing forms one transaction, so a 100-frame drag is one history entry. Cancellation of a gesture rolls back. Inspectors, property editors, node editors, drag and drop, transform UI, text editing, and multi-selection edits share this boundary.

The application applies mutations, keeps the undo stack, and decides merge policy. Tessera reports boundaries at defined update points and never mutates application data itself. Undo and redo are ordinary commands (`edit.undo`, `edit.redo`) whose enabled state comes from the application's history.

## Ownership

[Input](input.md#event-to-action-boundary) owns event-to-action translation and eligibility, and [semantics](semantics.md) owns which actions a node exposes. This page owns action-to-command resolution, descriptors, command eligibility, invocation records, and transaction boundaries. [Inspection](inspection.md) exposes commands to tooling. Applications own implementations, data, and history.

## Open decisions

- Asynchronous host execution/cancellation adapters and serialized invocation/result schemas, including transport size limits.
- Domain-specific host object-ID validation beyond the settled permitted-ID set.
- Platform key and device-button conventions, native shortcut routing and multi-key sequences beyond the [keyboard](#implemented-keyboard-shortcut-boundary) and [gamepad](#implemented-gamepad-shortcut-boundary) boundaries.

## Verification

First implementation fixtures: one menu command requested by pointer, keyboard, scripted gamepad, semantic identity, and replay with identical validated arguments; eligibility changing between dispatch and execution; a removed/replaced owner with a reused author ID; malformed and unknown arguments; a development-only command in production discovery; and a multi-update edit with one commit, cancellation with one rollback, nested begin rejection, and a late completion after token closure. Record descriptor revisions and eligibility as fixture inputs before extending [Replay](replay.md); no callback-only check establishes generation or semantic agreement.

Check that every input source produces the same command invocation and declared result under the same eligibility, that disabled commands and nodes agree in semantics, that invalid arguments fail with located diagnostics, and that stale targets fail after replacement. Verify execution rejection never enters the host, entered requests cannot run twice even on error/cancellation, recursive and wrong-thread calls reject, and malformed outcomes expose no partial values. Transaction fixtures must establish that a continuous gesture produces exactly one committed or rolled-back transaction. Use replayed fixtures rather than callback mocks; follow the [testing strategy](../guides/testing.md).
