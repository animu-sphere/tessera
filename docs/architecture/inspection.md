# Inspection, snapshots, and automation tooling

## Core invariants

- Owned observations identify one accepted generation; completed pixels cannot be combined with a different generation's semantic/layout records.
- Source information and unavailable observations are explicit; tooling cannot invent origins or inspect private application memory.
- Operations use ordinary target eligibility, lifetime and command/transaction boundaries under adapter permissions.

## Proposed shared inspection boundary

Tessera should be operable by humans, test runners, and external agents through the same runtime. This proposal defines inspection and tooling boundaries, not a stable public API, wire format, CLI, or build option; the [implemented prototype](#implemented-prototype-capture-and-target-resolution) covers a small in-process subset. Capability and configuration evidence belongs in [support](../reference/support-matrix.md).

DevTools, Path-finder, regression tools, and agent adapters consume a shared inspection layer. The layer depends on runtime contracts; the core never depends on an agent SDK, RPC server, MCP, or AI model. [Semantics](semantics.md) owns roles, names, state, and supported actions; [UI model](ui-model.md) owns identity and property metadata. Inspection joins these with layout and source information rather than maintaining another widget or accessibility tree.

Publish owned observations from one settled [update generation](overview.md#update-and-snapshot-rules). External consumers must not retain borrowed node pointers or access mutable runtime internals. A response identifies its generation; an action against an expired generation fails even if an author ID has been reused.

## Proposed inspection records and source mapping

An element record should expose scoped author identity, component/type information when available, semantic role/name/value, ordered hierarchy, logical bounds, visibility and interaction state, supported actions, and links to property/style/layout observations. Keep runtime hierarchy and semantic hierarchy distinguishable: semantic flattening need not preserve every layout container.

Source mappings associate authored nodes/properties with file identity and spans through frontend lowering and reload. Generated components may need both definition and instance origins. Report unavailable source information explicitly; never guess a source line from a preorder index. Source maps are tooling metadata, not runtime behavior or implicit new JSON v1 fields.

Extend provenance to component prop/signal/local-state declarations and authored defaults, keeping declaration/default origins distinct from invocation and supplied expression origins. Observations identify whether a value came from an explicit argument, a default, inheritance, or resolution using [property reflection](../proposals/property-reflection.md#proposed-property-reflection). Dedicated origin fields and precedence need bounded validation before use; a default must not acquire a fabricated argument span. Reload carries the accepted source map with its generation and preserves source-located rejection diagnostics for the discarded candidate.

Expose only host-declared serializable state slots. An application adapter validates typed values, owns capture/restore and any schema migration, and applies changes at update boundaries. No arbitrary memory access or enumeration of private application state is allowed. Fixture state can include host inputs that affect UI, but UI tooling does not become the owner of application state.

## Proposed target resolution and operations

Prefer targets in this order:

1. Explicit ID within a declared document/component scope.
2. Semantic role and accessible name.
3. Stable component/item key within its declared scope.
4. Explicit structural path.
5. Logical coordinates.

Style classes are presentation details and should not be stable automation identities. Selector grammar remains a decision; do not reuse CSS specificity as target resolution policy. A singular operation requires exactly one match and diagnoses missing, ambiguous, stale, hidden, disabled, or unsupported targets. Tree paths and coordinates are intentionally less stable across edits.

Distinguish semantic operations such as activate, focus, set value, toggle, or select from normalized pointer/key/text/scroll injection. Both follow [input eligibility and action dispatch](input.md#event-to-action-boundary); neither writes component fields or calls host callbacks directly. A pointer click scenario still exercises hit testing and press/release rules. Text entry must respect the editing/IME contract, and set-value requires a declared typed action. Logical coordinates are the default; physical or element-local inputs require explicit conversion.

Waiting observes an explicit predicate over settled generations with a bounded timeout or controlled frame/time limit. It must not add hidden sleeps or advance the runtime's clock implicitly.

## Implemented prototype capture and target resolution

[inspection.hpp](../../include/tessera/inspection/inspection.hpp) implements an in-process subset of the proposals above. It is a prototype, not a wire format or stable API, and it does not extend JSON v1.

- **Input and generation.** `InspectionInput` borrows the same coherent tree/resolved-style/layout snapshot as [semantic projection](semantics.md#implemented-prototype-projection), plus an optional source map and the optional host focus that the projection reports, and is rejected with the same located snapshot and focus codes. `capture_inspection` returns an owned `InspectionSnapshot` that borrows nothing. Its `generation` is the tree identity, so a handle built from it is a `NodeHandle` of that generation. No renderer, shaper, or host state is involved.
- **Element records.** Element *i* corresponds to tree preorder index *i* and records the runtime parent/children (including display-none nodes), kind, author ID, classes, event bindings, and the resolved style. `PropertyObservation`s list every descriptor accepted by the kind in [descriptor order](ui-model.md#implemented-property-metadata), with the effective value and whether it was authored. Displayed elements carry border/padding/content boxes, local visibility, the recorded layout clip, and scroll geometry for scroll boxes; display-none elements have no geometry. An element links to its entry in the snapshot's `SemanticTree` when it has one, keeping runtime and semantic hierarchy distinct. Projection warnings such as `missing_name` are kept as snapshot diagnostics.
- **Sources.** [serialization.hpp](../../include/tessera/ui/serialization.hpp) defines `DocumentSourceMap` and `NodeSource`; [source_map.cpp](../../src/ui/source_map.cpp) owns `validate_sources`. `load_document_with_sources(json, file, actions)` preserves `load_document`'s document validation, enriches failures under the [source diagnostic contract](#implemented-source-diagnostic-boundary), and returns node pointers and spans in preorder with authored property value spans. Byte ranges are half-open UTF-8 offsets. The metadata is outside document serialization. [Component lowering](ui-model.md#implemented-component-source-mapping) also returns maps for composed candidates. Inspection owns a copy; it does not read or authenticate any source content.
- **Source-map validation.** Maps contain exactly one record per document node within the document's 10,000-node/64-level bounds. Each `pointer` equals that node's resulting `/root/...` path. Every present semantic property appears exactly once in either `properties` (template value span) or `unmapped_properties` (explicit unavailable template value origin). Node spans are ordered; property spans are ordered and contained in their authored node span. `mapped=false` records have zero template spans, no template file override or property spans, and explicitly unmapped properties; independent instance origins are permitted. A record's optional `file` overrides the map's default when present, including a present empty identity; absence uses the default for mapped records. Each identity has at most `max_source_file_bytes` (4,096) valid UTF-8 bytes. Shape/pointer/property disagreement is `source_map_mismatch` at `/sources/nodes` or `/sources/nodes/<index>`; invalid ranges or unmapped template records are `source_map_span`, and invalid identities are `source_map_file`, at the offending field. `validate_sources` performs bounded traversal without copying and does not replace ordinary document semantic validation. Inspection uses it against its immutable document before capture.
- **Instance origins.** `SourceLocation` owns an opaque file identity and an ordered half-open byte range, validated by `validate_source_location` using the same 4,096-byte UTF-8 file bound. `NodeSource` optionally records `invocation`, `property_arguments`, `event_arguments` and `style_argument` independently of its template span/file. Property argument origins name present properties in `unmapped_properties`; event argument origins name present event bindings. These maps cannot exceed the corresponding node property/event counts; name or count disagreement uses `source_map_mismatch`. Style provenance describes one complete instance override, without inferring individual fields or validating an override array. Location ranges need not lie within template or invocation ranges, because the files can differ. [Component lowering](ui-model.md#implemented-component-source-mapping) owns argument association and default rules.
- **Source availability.** Without a map, snapshots report `SourceStatus::not_supplied` and elements have no source. A supplied validated map reports `SourceStatus::mapped`, including partial maps. A node with neither a template span nor instance provenance has no element source. Other nodes retain explicit missing template property origins and independent instance origins in `InspectionElement.source`; only mapped nodes have a resolved template file identity. `InspectionSnapshot.source_file` is the supplied map's default, which need not identify every element after composition. Warnings at `/nodes/<index>` gain an offset only for a mapped template node; consumers resolve its file through that element's source. [Invariant observations](#implemented-in-process-ui-invariant-boundary) copy the same per-element origins and use only mapped template spans for diagnostic offsets. Neither layer guesses unavailable positions.
- **Target resolution.** `resolve_target` resolves exactly one element of a snapshot: by author ID (document scope; display-none elements included), by semantic role plus exact name, by an explicit child-index path from the root, or by a logical point. A point selects the topmost visible displayed element, in the [`z_index` paint order](layout.md#implemented-stacking-order) over the observed hierarchy and resolved styles, whose half-open border box and recorded clip contain it. This includes disabled elements and is an inspection query, not pointer targeting. No match fails as `target_not_found` at `/target` (or `/target/children/<step>` for an out-of-range path step). Several role/name matches fail as `ambiguous_target`, listing the candidates. Non-finite points are `invalid_number`. An optional scope handle restricts every query to that authored subtree, including its root. Scoped paths start at the scope; points stay in root logical coordinates. A foreign or out-of-bounds scope fails as `stale_target` at `/scope`. Without a scope the whole document is searched; component keys have no target form.
- **Operations.** Resolution performs no action. A resolved handle is invoked through [`request_semantic_action`](semantics.md#implemented-prototype-projection), which applies ordinary hidden/disabled eligibility and rejects a handle from an earlier generation as `stale_target`, even after a reload that reuses every author ID. [Replay](replay.md#implemented-prototype-playback) focus and semantic action steps resolve their targets this way in each step's current generation, and a [replay session](replay.md#implemented-prototype-playback) is a controlled host fixture without a window: it captures its current generation for a consumer and records the consumer's handle operations as replayable steps.

## Proposed localization observations

Join [localization](localization.md) resolution results with text, layout and source observations from one settled generation. A locale Inspector or agent report can expose requested and resolved locale, effective UI/paragraph direction, catalog identity/revision and resource source, message ID, fallback chain/hit, missing-message or formatting diagnostic, and selected plural/select branch. Text observations supply script runs, concrete font faces and missing-glyph/fallback information; layout supplies logical bounds, clip and overflow observations. Optional screenshot regions refer to the same generation's completed capture.

Keep message IDs distinct from node/component/command identity. Translated accessible names are observable values; cross-locale scenarios should target stable scoped author IDs or keys rather than assuming a name remains equal. Preserve the shared diagnostic envelope and source mapping. Catalog/argument contents and paths follow host export/redaction policy; report unavailable information explicitly.

Static message-ID extraction, missing/unused-key and argument checks, glossary checks, and translation coverage are tooling candidates over the catalog schema and supported frontend syntax. Dynamic IDs must be reported as unresolved or declared explicitly, rather than counted as complete coverage. Reports distinguish fallback use, missing translation, missing glyph and layout overflow; numeric overflow follows the [invariant policy](#proposed-ui-invariants). These observations add no CLI or transport contract.

## Proposed runner and snapshot bundle

A capture joins owned observations and optional completed pixels from one accepted generation. Replay inputs and snapshot observations remain distinct; missing artifacts are explicit.

Possible mechanisms: [snapshot bundles and cli](../proposals/snapshot-bundles.md#proposed-runner-and-snapshot-bundle). This direction is not an implementation task; only the active roadmap can require a bounded part.

## Implemented prototype offscreen runner

[offscreen_runner.hpp](../../include/tessera/inspection/offscreen_runner.hpp) defines `run_offscreen(OffscreenInput)` in core. It is a window-free, in-process prototype, not a CLI, snapshot bundle, or stable API. Frames come only from a host adapter of the [capture boundary](rendering.md#implemented-capture-boundary); core chooses, constructs, and substitutes no backend.

- **Inputs.** `OffscreenInput` borrows a `ReplayRecording`, the text service its [environment](replay.md#implemented-prototype-playback) declares, an optional declared `CaptureBackend`, and an optional `FrameCapture` adapter. A missing recording or text service is `missing_input` at `/recording` or `/text`. A declaration requires an adapter (`missing_input` at `/frames`), an adapter requires a declaration (`missing_input` at `/capture`), and the adapter's `backend()` must equal the declaration (`capture_mismatch` at `/capture`); declaration diagnostics are relocated under `/capture`. These checks run before playback, so an unavailable or different backend fails without capturing anything. The host verifies a font-profile declaration, for example with `verify_replay_fonts`, before running; core neither embeds nor checks the profile.
- **Playback and frames.** The recording plays exactly as `play_replay`; its diagnostics and warnings are relocated under `/recording` (for example `/recording/steps/2/viewport/width` or `/recording/nodes/3`). All replay observations settle before any capture. Then `OffscreenRun::frames` holds one `OffscreenFrame` per output generation, in order, with the generation index, the producing generation's owned logical viewport, device scale, animation-clock value, and its `capture_extent`. A generation whose extent is invalid fails as `out_of_range` under `/generations/<g>/capture`, even without a declared backend.
- **Capture.** Without a declaration the run is core-only: every frame has status `not_declared` and no image, and the manifest has no backend. With one, each generation's owned paint list is passed to the adapter in generation order with its viewport, scale, extent, and explicit animation time; the adapter returns only a completed frame. The image must have the requested extent, the declared format, and `width * height * 4` bytes (`capture_mismatch` at `/generations/<g>/capture`). Adapter diagnostics are relocated under that path; a failure without an error diagnostic is `capture_failed`. Images are bounded to `max_capture_bytes` (256 MiB) per run, checked before each request (`out_of_range`). Any failure returns no partial run; already completed adapter frames are the host's to discard.
- **Manifest and determinism.** `OffscreenManifest` records the replay version, the recording's whole environment (scale, locale, and placeholder or font-profile identity), and the declared backend. A run owns its manifest, replay output, frame conditions, and pixels, and borrows nothing; repeated runs with equal inputs and a deterministic adapter compare equal, image bytes included. Frame numbering, target reuse, resource preparation such as glyph atlas pages, and retirement stay inside the adapter.

The runner captures every output generation, including the declared boolean state and readiness transitions of the [controlled host update boundary](replay.md#implemented-controlled-host-updates). The manifest owns initial slot declarations; each replay generation owns its settled observations alongside its paint. The runner evaluates no animation, executes no host provider or application state binding, and encodes no image.

## Implemented snapshot bundle tooling

[snapshot_bundle.hpp](../../tools/snapshot/include/tessera/snapshot/snapshot_bundle.hpp) is development tooling above core, built with `TESSERA_BUILD_TOOLS` as `tessera::snapshot`. Core does not depend on it and gains no filesystem access or image encoder. It writes one [offscreen run](#implemented-prototype-offscreen-runner) as a directory that a person, a CI job or an agent can read directly. Bundle v1 has its own version, separate from the UI document, Replay and Semantic versions. It is a capture format, not an exchange or transport contract.

- **Building.** `build_snapshot_bundle(recording, run, options)` takes the recording that the run played and returns owned members sorted by path. Equal inputs give byte-identical members. The host supplies its `producer`, an optional `scenario`, and two identities when they apply: the text service it actually used (`text_service`, by default the recording's `placeholder` or `font-profile:<id>` declaration) and the glyph coverage behind captured frames (`glyphs`, required when a frame was captured). Identities are 1–256 UTF-8 bytes without ASCII controls; any other value is `invalid_bundle_option`. Selected generations must exist and strictly increase (`out_of_range` at `/options/generations/<i>`); by default only the last generation is written.
- **Members.** `manifest.json` records the bundle format and version, producer, scenario, Replay version, environment, declared text service, capture backend and glyph identity (or `null` for a core-only run), and the generation count. For each selected generation it also records the producing step, viewport, scale, animation time, node count, focused node and member list. `recording.json` is the input as Replay JSON. `actions.json` lists the run's requested actions and `diagnostics.json` the host's run warnings. Each `g<g>/` directory holds the generation's last settled observation as Semantic JSON v1 (`semantics.json`). `layout.json` lists every preorder node of that generation's document with its parent, kind and ID; displayed nodes add border box, border, padding, visibility, clip and scroll geometry, and display-none nodes are marked `displayed: false`. `paint.json` counts the commands by kind plus the glyphs and time dependence. `frame.png` is present only when the run captured that generation.
- **Derived tree.** `g<g>/tree.txt` shows one node per line, indented by depth: the semantic role or node kind, `#id`, the name (or text content), the border box and the focused, disabled, selected, expanded, value, multiselectable, item position, hidden, display-none and scroll states. The manifest marks it `derived`. It is a compact text view for reading and searching; tools compare the JSON members instead.
- **Missing observations.** A generation without a captured frame records `{"unavailable": "not_declared"}`, and one without a semantic observation records `no_semantic_observation`. A consumer must not mistake a missing member for an empty one.
- **Images.** `encode_png` writes 8-bit RGBA with an `sRGB` chunk. Every row uses filter None, and the image data is one fixed-Huffman deflate block from a bounded greedy matcher, so the bytes depend only on the pixels. A pixel buffer that does not match its extent is `capture_mismatch` at `/pixels`.
- **Writing.** `write_snapshot_bundle` accepts an absent or empty directory, or one that holds only the files and `g<n>/` directories of an earlier bundle, which it replaces. Any other entry is `bundle_directory_not_empty`, and nothing is changed. Filesystem failures are `bundle_io`.
- **Reading.** `read_snapshot_bundle` reads the regular files of a bundle directory and of its immediate subdirectories without interpreting them. It refuses more than 2,048 entries, a file above 64 MiB or more than 1 GiB in all with `bundle_limit`, and an unreadable directory or file with `bundle_io`. Deeper directories and entries that are not regular files are `unlisted_member`.
- **Verification.** `load_snapshot_bundle` checks every member against bundle v1 and reports every problem, returning the loaded bundle only when there is none. A manifest that is not a bundle manifest, or whose version is not 1, stops validation (`unsupported_version` at `/manifest.json/version`). Other member versions other than 1, and Replay versions other than 1 and 2, are also `unsupported_version` at their version field. A listed member that is absent is `missing_member` and a member the manifest does not list is `unlisted_member`, both at `/<path>`. JSON members are parsed strictly: UTF-8 without a BOM, no duplicate or unknown fields, at most 64 levels and per-member byte bounds (`bundle_limit`). A failure is `invalid_member` at `/<path>` with its byte offset. The same code reports a schema violation at `/<path>/<pointer>`, or a member that disagrees with the manifest or another member: a generation, node count, viewport, scale, focused ID, action or diagnostic count, frame extent, or the recording's environment. Each layout lists the generation's preorder nodes with parents before children and unique author IDs, and its paint kinds add up to its command count. `recording.json` must load with `load_replay` and each `semantics.json` with `load_semantics`. Their diagnostics keep their codes, relocated below the member path. Frames decode with `decode_png`, which reads non-interlaced 8-bit RGBA with any filter and stored, fixed or dynamic deflate blocks. It checks chunk CRCs and the Adler-32 and bounds an image to 16,384 pixels per side and 256 MiB of pixels; anything else is `invalid_png`. `tree.txt` is only checked for presence and UTF-8. `verify_snapshot_bundle` reads and loads a directory and reports the diagnostics of both.
- **Comparison.** `diff_snapshot_bundles(before, after, options)` in [snapshot_diff.hpp](../../tools/snapshot/include/tessera/snapshot/snapshot_diff.hpp) compares two loaded bundles. It pairs every listed generation when both bundles list the same ones, and otherwise their last generations. Conditions come first: bundle version, environment (scale, locale and text declaration), text service, capture backend (backend, device and format), glyphs, and each pair's viewport and scale. Any mismatch makes the status `incompatible` and leaves the judged levels empty. Otherwise it reports levels in order. **Semantic** lists added, removed and changed semantic entries. **Layout** lists added, removed and changed layout nodes, and numbers within `geometry_tolerance` logical units are equal. **Actions** compares the run's requested actions by position. **Paint** compares command, glyph and per-kind counts and time dependence. **Pixels** gives one record per pair: compared and differing pixel counts, the largest channel delta and the bounds of the differing pixels. A pixel differs when a channel changes by more than `pixel_threshold`, and frames differ when more than `pixel_count` pixels differ or one bundle lacks the frame. Nodes are matched by author ID. An unnamed node is matched by its preorder ordinal among the unnamed nodes whose nearest identified ancestor is the same, so inserting an entry does not shift the others. References such as `parent` and `labelled_by` are reported as these keys rather than as indices. A changed record names only its changed fields, with before and after values; absent fields read as null. `first_difference` names the most semantic level that differs, and the status is `equal` or `different`. A negative or non-finite tolerance is `invalid_diff_option`. `save_snapshot_diff` spells the report as `tessera-snapshot-diff` JSON v1, with the judged levels `null` when the status is incompatible. Perceptual comparison, layout-only or semantic-only selection, and per-node tolerances are not implemented.

`tessera_snapshot capture <recording.json> --out <dir> [--generation last|all|<g>[,<g>...]] [--core-only]` loads a Replay JSON v1/v2 recording within its 64 MiB bound, plays it with the placeholder text service and captures frames with the scalar CPU renderer and synthetic glyph marks (`synthetic-fixture`). It refuses a font-profile recording with `text_service_unavailable`, because it cannot provide that service, and substitutes nothing. Exit status is 0 when the bundle is written, 1 when input or capture is rejected and 2 for a usage error. A host whose text or glyph services are its own writes bundles in-process through the same library; the [Inspector](../guides/inspector-hierarchy.md#snapshot-bundles) does this with named scenarios.

`tessera_snapshot verify <dir>` prints each problem and exits 0 for a valid bundle, 1 for an invalid one and 2 for a usage error. `tessera_snapshot diff <before> <after> [--geometry-tolerance <units>] [--pixel-threshold <0-255>] [--pixel-count <n>] [--out <report.json>]` verifies both bundles and writes the report to stdout, or to `--out`, with a one-line summary. It exits 0 when they are equal, 1 when they differ, 2 for an invalid bundle or a usage error and 3 for incompatible conditions. Neither command needs the text or glyph services that produced the bundles, so they compare host-written bundles too. Invariant declarations, source maps and inspection property records are not implemented.

## Proposed diagnostics and comparisons

Tooling diagnostics extend the [source diagnostic boundary](#implemented-source-diagnostic-boundary) with category and typed contextual data. Categories include document/style/layout/render/resource/input/state/accessibility/performance. Hints may be deterministic rules; no model is needed. Preserve existing validation codes, severities, and locations when adapting them. Categories, context and hints are separate contract decisions. Numeric overflow observations need policy because intentional scrolling/overlays can extend beyond a parent.

Snapshot comparisons should report semantic additions/removals/state/action changes, logical geometry changes, render-counter changes, and optional visual differences in machine-readable form. Match scoped stable identities, not process handles or allocation order. Incompatible versions or fixture conditions must be reported before judging a regression. Exact/threshold pixel comparisons come first; perceptual methods are later choices. An image change is evidence to explain alongside semantic/layout changes, not a complete behavior assertion.

The [semantic diff](#implemented-semantic-diff) compares two semantic snapshots in core and names each change by kind, without a bundle. Comparisons are diagnosable in a fixed order, so a report explains a failure at the most semantic level that changed: semantic diff, layout diff, action diff, paint diff, visual diff, then performance counter diff. Pixel differences alone never establish or rule out a behavior change.

## Implemented source diagnostic boundary

[document.hpp](../../include/tessera/ui/document.hpp) defines the owned `Diagnostic.source` envelope: a `DiagnosticSource` contains a `SourceLocation` and `DiagnosticOrigin`. The optional field is unavailable unless a source-aware entry point resolves it. Origins distinguish a complete parsed/template property `value`, a zero-width parser failure `point`, a template `node` declaration, a supplied expression `argument`, and an `invocation` fallback. These labels identify what the range describes; a node or invocation is not the exact offending field. Codes, severities, JSON-pointer paths, messages and `byte_offset` retain their existing meanings. Expression files/ranges are independent of the diagnostic pointer and template file, so enrichment never rewrites the original offset to an unrelated expression offset. Metadata is outside document serialization; diagnostic equality includes the owned envelope.

`load_document_with_sources` validates the opaque file identity before parsing. For valid identities it preserves ordinary loader rejection and enriches each failure with that file. Schema/semantic failures use the complete nearest parsed value at the diagnostic's existing offset, including a containing object when a required field is absent. Parser/input failures use the existing offset as a zero-width point when no complete matching value exists. No partial document or source map is returned on failure. The ordinary loader returns diagnostics without source envelopes.

`locate_diagnostics(document, map, diagnostics)` in [serialization.hpp](../../include/tessera/ui/serialization.hpp) enriches caller-owned document-local diagnostics in place. It accepts at most `max_source_diagnostics` (4,096) records and a shared 4 MiB diagnostic-pointer byte budget, reporting `diagnostic_limit` at `/diagnostics`. It validates the complete map using `validate_sources`, without requiring the candidate's document semantics to pass. Bounds or map errors leave every input record untouched. Successful lookup stages owned envelopes before replacing all prior origins, preserving diagnostic order and other fields; an unavailable origin clears obsolete metadata. Allocation failure is a standard C++ exception.

Lookup selects the exact `/root/children/<index>/...` node, with canonical JSON-pointer token spelling; a missing child cannot inherit an ancestor's source. Property/event fields first use their supplied argument origin, and `/style` fields use the complete style argument. Authored properties otherwise use their value span. For instance fields without an exact origin, an invocation is preferred to a template node; other node fields prefer the template declaration. Generated nodes can use an invocation fallback, and nodes without relevant provenance remain unavailable. Document-level fields have no node-map origin. Explicit empty file identities stay empty. The adapter opens no source file, authenticates no source contents, evaluates no reactive value and publishes nothing.

[Component lowering](ui-model.md#implemented-component-source-mapping) applies this boundary before relocating template and composed-child validation paths and after constructing a complete candidate map for final document validation. Its own prop/action/style argument errors use validated expression origins or the invocation fallback. Invalid metadata supplies no trusted origin; enrichment preserves the underlying rejection rather than substituting map errors. Child validation cannot inherit the parent's invocation. Nested lowering preserves envelopes when prefixing paths with `/invocations/<index>`, and local topology/schema failures may use the addressed invocation's validated origin. Whole-graph `/reactive` errors remain graph-located without an instance envelope. Source-map metadata errors have no envelope derived from that invalid metadata. Dedicated schema/default declaration spans, categories/context/hints, diagnostic encoding and editor transport are outside this boundary.

[Source diagnostic checks](../../tests/ui/source_diagnostic_tests.cpp) verify UTF-8 ranges, syntax points, rejected candidates, argument and template precedence, independent child files, stale reactive arguments, unavailable origins, atomic metadata rejection and bounds. [Independent source consumers](../../tests/cmake/consumer/main.cpp) use the same public envelope and adapter.

## Proposed reactive observations

Development inspection can join [reactive graph](reactive-runtime.md) and owner-tree observations with presentation/source records from one settled generation. Record lifetime-aware computation/owner IDs, dependencies/dependents, accepted value revisions, potential dirtiness, evaluation counts, and the cause of invalidation. A bounded causal trace connects a changed source through derivation, measurement/layout, and paint work so an Inspector or agent can explain why a node updated. Durations are optional measured observations rather than deterministic graph state.

Snapshots own their records, identify unavailable fields, and carry explicit record/edge/trace limits with truncation reporting. Graph exports use the same observations; JSON/DOT encoding, transport operations, and UI panels are separate API decisions. They expose no addresses, mutable storage, executable closures, or private application values. Source names/values are host-declared exports under the [production boundary](#proposed-tooling-and-production-boundary). Observation never flushes pending work or creates dependency edges.

## Proposed performance metrics

A GPU-native renderer is not itself a performance guarantee; CPU and GPU work are both measured.

| Side | Metrics |
| --- | --- |
| CPU | Document update, reconciliation, style resolution, layout, semantic projection, paint generation, text shaping, glyph cache |
| Reactive | Invalidated/evaluated computations, replaced dependency edges, layout nodes touched, paint items rebuilt, allocations per update, owner creation/disposal, queue depth, and update latency |
| GPU | Draw and instance counts, upload bytes, atlas pages, render passes, GPU timing when the backend supplies it |
| Iteration | Edit-to-visible-result latency, broken down into parse, update, layout, paint, submit, completion/readback, and export |

Iteration latency, not frame rate alone, is the first-class metric for live reload, Path-finder, and agent loops. Performance comparisons identify workload, changed-node count, build/backend/device, warmup, sample count, and measurement method. Separate deterministic counters from noisy durations; absent GPU timing is unavailable, never zero. Consumer-specific budgets require representative baselines and explicit tolerance policy. These are instrumentation goals, not promised millisecond or framework-speedup targets.

Measure work proportionality by varying total UI/graph size and the changed region independently. Use chains, fan-out, diamonds, dynamic branches, owner churn, keyed reorder, one changing label among static content, theme changes, viewport resize, and streaming/virtualized consumers. Compare evaluated/touched counts and upload bytes with a full-update baseline; avoid adopting illustrative million-node or widget-count targets as guarantees.

## Proposed UI invariants

UI invariants are machine-readable assertions evaluated against one captured generation, shared by unit and integration tests, the offscreen runner, CI, Path-finder, coding agents, and replay. Illustrative predicates:

```text
visible("#save")          enabled("#save")          focusable("#search")
semantic_name("#save") == "Save"
no_overlap(".toolbar > *")                          inside_viewport("#dialog")
layout_time < budget      draw_calls <= budget      glyph_atlas_pages <= budget
```

Selectors use [target resolution](#proposed-target-resolution-and-operations), so an ambiguous or missing target is a diagnosed failure, not a vacuous pass. Structural predicates read semantic, layout, and focus observations; performance predicates read the metrics above under declared measurement conditions and stay separate from deterministic predicates. A failure reports the predicate, the resolved targets, the generation, and the observed values in the diagnostics envelope. Invariants are evaluated by tooling and never change runtime behavior. Predicate spelling and the scenario format are open decisions.

## Implemented in-process UI invariant boundary

[invariants.hpp](../../include/tessera/inspection/invariants.hpp) defines host-built `UiInvariant` declarations and `evaluate_invariants(InvariantInput)`; [invariants.cpp](../../src/inspection/invariants.cpp) evaluates them against one owned [inspection snapshot](#implemented-prototype-capture-and-target-resolution). This is read-only tooling with no callback, reactive evaluation, input dispatch, renderer, transport, or serialized scenario schema.

An input borrows the snapshot and at most 256 ordered declarations. Each declaration has a unique report name of 1–256 UTF-8 bytes without ASCII controls, a typed predicate, and an optional ordinary inspection subtree scope. Author-ID targets use the same name bound; semantic target names and expected names allow empty UTF-8 strings of at most 4,096 bytes. Paths have at most 63 child steps. Point coordinates and geometric tolerances must be finite; tolerances are nonnegative logical units. A supplied viewport has positive finite dimensions and origin `(0,0)`; the host declares the viewport of this generation rather than deriving it from the root box. A viewport is required for containment predicates.

Malformed declarations and malformed snapshot structure return no report. Snapshot checks enforce a nonzero generation, document node/depth bounds, complete canonical preorder with matching parents, valid observed border/clip rectangles, reciprocal semantic links/handles from this generation, and the [semantic snapshot schema](semantics.md#implemented-semantic-snapshot-contract)'s identity/state rules. These checks protect observation reads; they cannot prove that caller-modified values came from a real capture or that the declared viewport matches the host. The host supplies an unmodified coherent capture and its conditions.

Supported predicates:

| Declaration | Observation and rule |
| --- | --- |
| `VisibleInvariant` | Compare the observed Boolean with `expected`. A target is visible when it has locally visible geometry and its border box has positive area after intersection with the recorded ancestor clip. Display-none, hidden, zero-area, and fully clipped targets observe false. No viewport clipping or paint-transform inference is added. |
| `EnabledInvariant` | Compare the exposed semantic entry's inherited `enabled` with `expected`. |
| `FocusableInvariant` | Compare the exposed semantic entry's ordinary focus eligibility with `expected`. |
| `SemanticNameInvariant` | Compare the exposed semantic name exactly with the UTF-8 `expected` string. |
| `InsideViewportInvariant` | Every full border-box edge must lie within the declared viewport, allowing `tolerance` outward on each edge. |
| `NoOverlapInvariant` | Two distinct targets pass when either full border-box intersection axis is at most `tolerance`. Touching edges and zero-area boxes pass. |

Semantic predicates require an exposed entry: a presentational Text descendant or flattened Box has no inferred semantic value. Geometry predicates require displayed geometry; hidden boxes retain geometry and can be compared. Containment and overlap compare full logical border boxes without applying clips, viewport intersection, paint transforms, margins, or resource pixels. This explicit policy exposes intentional scrolling/overflow as a condition the caller chooses to test. Edge sums/intersections use binary64 arithmetic on observed binary32 coordinates. The API supplies no class/group selector, pairwise set predicate, or performance/timing predicate.

Each target resolves through `resolve_target` with the declaration's scope, preserving ID/role-name/path/point semantics. Missing/ambiguous targets and stale scopes produce `InvariantStatus::error`, including for a negated visible predicate; unavailable semantic/geometry observations use `invariant_unavailable`, and comparing the same target uses `invariant_same_target`. Resolution codes are preserved and relocated under `/invariants/<index>/target`, `/other`, or `/scope`. A resolved mismatch has status `failed` and `invariant_failed` at `/invariants/<index>`. Evaluation continues in declaration order after either failure or error.

A valid evaluation returns an owned `InvariantReport` even when assertions fail. `Result` success means evaluation was valid; `report.passed()` means every result passed. The report owns the captured generation, declared viewport, declaration copies, resolved handles, observed state/name/bounds/clip, optional source records/file, and located diagnostics. Available source spans supply diagnostic byte offsets; missing sources stay absent. An empty declaration list produces an explicit zero-result report. The report survives destruction of all input data and confers no action authority.

[Invariant checks](../../tests/inspection/invariants_tests.cpp) cover deterministic owned reports, semantic eligibility/name agreement, explicit visibility/geometry policies and tolerances, shared target resolution, source absence, stale scopes, and declaration/snapshot rejection. The [tool panel](../../examples/tool-panel/main.cpp) verifies its inspection button's visibility, selection-dependent enabled/focusable state, name, and viewport containment before publishing each full-tree selection generation.

## Implemented capability manifest

[capabilities.hpp](../../include/tessera/inspection/capabilities.hpp) defines `capture_capabilities(CapabilityInput)` and `save_capabilities` in core. A manifest tells an agent, for one host generation, which operations an adapter offers, which commands exist with their state and schemas, and which semantic entries it can focus or act on. It is a projection of the [command snapshot](commands.md#implemented-in-process-command-boundary), the [semantic snapshot](semantics.md#implemented-semantic-snapshot-contract) and the adapter's own declarations. It is not a runtime API, transport or invocation path, and it grants no authority: requests still go through ordinary semantic and command eligibility, generation checks and transactions. `tessera-capabilities` JSON v1 has its own version, separate from the UI document, Replay, Semantic and bundle versions.

- **Input.** `CapabilityInput` borrows a `CommandSnapshot`, a `SemanticSnapshot` and a span of `CapabilityDeclaration`s, and names its `producer`. A missing snapshot is `missing_input` at `/commands` or `/semantics`. The semantic snapshot is validated as Semantic JSON v1 with its diagnostics relocated under `/semantics`. Both snapshots must carry the same host generation (`capability_mismatch` at `/semantics/generation`), so the host captures semantics with the command generation of the view it projects. The producer and each declaration's `entry_point`, `request` and `result` are opaque identities of 1–256 UTF-8 bytes without ASCII controls (`invalid_identifier`). An operation declared twice is `duplicate_operation`, a repeated precondition `duplicate_precondition`, and an undeclared enum value `unknown_value`, each at its `/operations/<i>/...` field. Every problem is reported and no manifest is returned.
- **Operations.** The vocabulary is fixed: `inspect_tree`, `inspect_properties`, `semantic_action`, `invoke_command`, `replay_input`, `capture_frame`, `evaluate_invariants`, `edit_source`, `reload` and `compare_snapshots`. The manifest reports every operation once, in that order. A declaration names the operation, its [command availability](commands.md#implemented-in-process-command-boundary) (`both`, `development` or `production`), the adapter's entry point, the request and result schema identities, and the preconditions `generation` (a request names this generation and fails once it is replaced) and `target` (a request names a target resolved in it). A declaration available in the command snapshot's mode is `supported` and keeps those fields, with sorted preconditions. One declared only for the other mode is `unavailable` and keeps none of them, so a production manifest does not show development entry points. An operation without a declaration is `not_declared`.
- **Commands.** The manifest copies `CommandSnapshot::discover`: the commands available in the snapshot's mode, ordered by ID, with label, description, category, availability, enabled, checked and disabled reason, and every parameter and result field with its type, required flag, default, number bounds, string or object-ID byte bound and enumeration choices. A failed query is disabled with the reason discovery reports. `objects` lists the snapshot's permitted object IDs, which the new `CommandSnapshot::permitted_objects` returns. `CommandSnapshot::mode` gives the manifest's mode.
- **Targets.** A target is a semantic entry that is focusable or exposes an eligible action. It records the entry's preorder `node`, author ID, role, name and focusability, and for each action its binding, its host action and the explicitly mapped command, or `null` when the action has no mapping or maps to a command unavailable in this mode. Disabled entries have no actions and are not focusable, so they are not targets. Their commands still appear under `commands` with their disabled reason.
- **Ownership and encoding.** `CapabilityManifest` is owned, borrows nothing and has no public constructor; only `capture_capabilities` makes one, so a saved manifest always satisfies these rules. Equal inputs give equal manifests. `save_capabilities` writes canonical JSON with sorted keys and a trailing newline. The top-level fields are `format` (`"tessera-capabilities"`), `version` (1), `producer`, `mode`, `generation` as a canonical decimal string, `operations`, `commands`, `objects` and `targets`. An operation record has `operation` and `status`, plus `entry_point`, `request`, `result` and `preconditions` when supported. Output above 16 MiB is `size_limit`. A reader is not implemented, and the manifest is not a bundle member.

The [Inspector](../guides/inspector-hierarchy.md#capability-manifest) writes a manifest for the final generation of a snapshot scenario with `--capabilities <scenario> <file>`. Its window-free adapter declares `inspect_tree` and `capture_frame` through `--snapshot` (request `inspector-scenario`, result `tessera-snapshot-bundle/1`) and `compare_snapshots` through `tessera_snapshot diff` (result `tessera-snapshot-diff/1`). It reports the other operations as not declared, because it neither invokes commands nor injects input. Property records, invariant reports, source editing, reload and a live request transport stay out of scope.

## Implemented semantic diff

[semantic_diff.hpp](../../include/tessera/inspection/semantic_diff.hpp) defines `diff_semantics(before, after, options)` and `save_semantic_diff` in core. Where a [semantic snapshot](semantics.md#implemented-semantic-snapshot-contract) says what the UI currently means, a semantic diff says how that meaning changed between two snapshots, usually two generations of one host: focus, entries added, removed or moved, and changes to role, name, state, value or available actions. An agent can check the result of an action or command from the diff instead of rereading the whole tree, and a test can check that an action changed what it should and nothing else. The comparison is read-only and deterministic. It does not depend on fonts, colors, resolution, layout or a rendering backend. It reports what changed, not why: the cause comes from the command or action that produced the generation. `tessera-semantic-diff` JSON v1 has its own version, separate from the Semantic and snapshot-diff versions.

- **Input.** Both snapshots are validated as Semantic JSON v1, with their diagnostics relocated under `/before` and `/after`. Their generations are recorded as `from_generation` and `to_generation` and are not otherwise constrained. `SemanticDiffOptions::scope` names an author ID. Only that entry's subtree is compared, in each snapshot that has the entry. A scope absent from both snapshots is `target_not_found`, and an empty or control-character scope is `invalid_identifier`, both at `/options/scope`. `kinds` keeps only the listed change kinds; an undeclared one is `unknown_value` at `/options/kinds/<i>`. The diff records its kinds sorted and unique, and listing every kind is the same as listing none.
- **Identity.** Entries are matched by author ID. An entry without one is matched by its role and its ordinal among the entries without an ID of that role whose nearest identified semantic ancestor is the same (`SemanticNodeKey`). Inserting an entry of another role or under another identified ancestor therefore does not shift the others. Preorder indices and parent entry indices are not identities: each change also reports `before_node` and `after_node`, the preorder indices in either snapshot, so an agent can build a `SemanticIdentity` for the after generation. `labelled_by` is a preorder reference that has no identity across generations, so it is not compared; its effect appears as a name or name-source change.
- **Changes.** `focus_changed` is one change for the whole snapshot, between the focused entries' keys, either of which can be empty. `node_added` and `node_removed` carry the entry's record and its placement (its parent's key and its index among the parent's semantic children). `node_moved` carries the before and after placements. An entry moved when its parent's key changed. It also moved when it kept its parent but is not on the longest sequence of siblings that kept both their parent and their relative order, so moving one row reports one move rather than shifting every sibling. Its index can stay the same when siblings were also added or removed. The field changes are `role_changed`, `name_changed`, `name_source_changed`, `enabled_changed`, `focusable_changed`, `selection_changed`, `checked_changed` (the `selected` state of a checkbox or switch, never reported as selection), `expanded_changed`, `value_changed`, `item_count_changed`, `item_position_changed` and `multiselectable_changed`. Absent optional values read as empty. `action_added` and `action_removed` name a binding and host action, so a tree branch that expands reports `expanded_changed`, `collapse` added and `expand` removed.
- **Order.** `focus_changed` comes first. Then come the after snapshot's entries in preorder, each with its changes in kind order: added or moved, then fields, then actions. Removed entries follow in the before snapshot's preorder. With a scope, an entry is reported when it is in the scope on either side, so an entry that moves into or out of the scope is a move rather than an addition or removal. Focus is reported when either focused entry is in the scope.
- **Ownership and encoding.** `SemanticDiff` is owned, borrows nothing and has no public constructor. `find(id, kind)` returns the first change of a kind for an author ID. `save_semantic_diff` writes canonical JSON with sorted keys and a trailing newline. The top-level fields are `format` (`"tessera-semantic-diff"`), `version` (1), `from_generation` and `to_generation` as canonical decimal strings, `scope` (or `null`), `kinds` (or `null` for every kind) and `changes`. A change has `kind`, `target` (`{"id": ...}`, or `{"within", "role", "ordinal"}` for an entry without an ID, `null` for focus), `before_node`, `after_node`, `before` and `after`. Values use Semantic JSON v1 spellings. Placements are `{"parent", "index"}`, and actions are `{"binding", "action"}`. Added and removed entries have the Semantic JSON v1 record fields without `node`, `parent` and `labelled_by`, plus `placement`. Output above 32 MiB is `size_limit`. A reader is not implemented.

`tessera_snapshot semantic-diff <before.json> <after.json> [--scope <id>] [--kind <kind>[,<kind>...]] [--out <report.json>]` loads two Semantic JSON v1 files within the 16 MiB bound, such as two bundles' `g<g>/semantics.json` members, and writes the report to stdout or to `--out`, with a one-line summary. It exits 0 when nothing changed, 1 when something did and 2 for invalid input or a usage error. The [Inspector](../guides/inspector-hierarchy.md#semantic-diff) writes the diff between its launch state and the final generation of a snapshot scenario with `--semantic-diff <scenario> <file>`. Subscriptions, retained semantic history, assertions over expected change sets and a transport are not implemented.

## Proposed tooling and production boundary

Prove the in-process inspection/action API first, then a small CLI with machine-readable results, then bounded stdin/stdout JSON-RPC. Add local RPC, subscriptions, and optional MCP adapters only for a consumer. External automation handles inspect, invoke, replay, capture, diff, and assert consistently through these layers. The intended agent loop is short: edit, reload, capture a screenshot with layout/semantic dumps, compare, assert invariants, and edit again. Remote mutation is limited to declared commands, actions, and state slots; there is no unrestricted mutation API. The [snapshot CLI](#implemented-snapshot-bundle-tooling) is the first CLI step, with capture, verification, comparison and [semantic diff](#implemented-semantic-diff) commands; transport schema and production build switches remain undecided. A thin versioned JSON/YAML scenario layer may compose the same operations; it must not introduce another UI language or runtime.

State injection, source paths, detailed diagnostics, and mutation transports are explicitly enabled development/test facilities that can be excluded from production builds. Do not start a listener or expose private state by default. A local server needs an explicit access policy, request bounds, and lifetime/cancellation rules. Human Inspector and agent tooling share observations, while each adapter controls which operations it exposes.
