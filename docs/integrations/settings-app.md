# Settings reference application

The Proposed sections define application direction; the Implemented sections describe source-backed consumer boundaries. [Current work](../roadmap/current.md) owns the active subset; broader requirements need explicit promotion under the [agent policy](../agent-policy.md). ## Implemented form skeleton boundary

The [Settings fixture](../../examples/settings/main.cpp) composes Text, Checkbox, Row and Column through the [C++ form authoring contract](../architecture/ui-model.md#implemented-c-form-authoring). `SettingsRow` is an ordinary C++ function with typed label/identity props, a default gap and ordered child content. The Settings form composes it twice, without component mounting records or binding tables. A session owns a named enabled observation and a derived summary; a host command owns the application boolean and writes that observation after dispatch. The Checkbox's controlled marker and content-derived button name expose the same value alongside its label.

The host prepares command eligibility, full-tree styles/layout/semantics/paint and source inspection before graph publication. Logical focus/activation events exercise the keyboard/gamepad route; pointer press/release and semantic activation reach the same command descriptor and executor. Disabled command snapshots suppress activation, and old-tree owners fail resolution. An invalid style candidate returns a supplied source expression origin while the host retains its accepted snapshot.

The normalized sequence starts false: `FocusNext` then keyboard `Activate` toggles true; focus recovery by author ID and gamepad logical `Activate` toggles false; semantic activation toggles true; pointer press/release toggles false once on release. Each replacement exposes the checked marker, label, derived summary and source origins from one accepted presentation. Both authored-disabled and command-disabled candidates reject logical, pointer, semantic and direct command activation. A pending unexecuted invocation and old-tree action owner reject after replacement despite the same author ID. Physical key/button normalization belongs to the host.

The username variant adds an Account row through that same Settings function, with `TextInput("Username", observed, "settings.edit", props)`. One host-owned `TextEditState` and its session observation supply the committed value, UTF-8 byte anchor/caret and derived `User <value>; feature disabled` summary. The field's ordinary button name joins the label, value and visible `Selection <anchor>:<caret>` Text. The form contract owns this composition's public types and limits; there is no separate editable semantic schema.

The host focuses Checkbox then username with two logical `FocusNext` events. Committed normalized text inserts `日😀` after `Ada`, yielding `Ada日😀` at 10:10; Left moves to 6:6, Shift+Left selects 6:3, inserting `本` yields `Ada本😀` at 6:6, and Delete yields `Ada本` at 6:6. Home, Right, Backspace and End then yield `da本` at 5:5. Each edit or selection command advances one revision. Control/Alt/Super modified keys are outside this mapping; supported keys are consumed before focus navigation. Each synchronous edit host owns its immutable request payload and creates a pure candidate through `edit_text` after the ordinary executor rechecks the live activate owner. The application writes the observation, prepares all presentation stages and only then accepts host state, graph publication and snapshot replacement. On a returned preparation failure it restores the previous observation and keeps the accepted snapshot. Allocation failures propagate; this is not generalized exception rollback.

The fixture also selects all, injects measurement/paint rejection for a replacement and retries a replacement using a fresh execution sequence. Rejection retains host value, revision, selection and accepted inspection/document; host mapping translates stage preorder-node diagnostic paths to source document pointers before locating them. Command-disabled and authored-disabled fields suppress focus, normalized text routing, semantic and direct command requests. Old tree owners, pending invocations and stale edit owners/revisions reject. Malformed edit observations return source-located candidate diagnostics.

The combined workflow composes that username field, Checkbox, derived summary, an ordinary `Button("Apply", "settings.apply", props)` and a saved-result Text in one form. The host owns a draft `{username, feature}` and injects a synchronous `SaveObservation` whose call records own copies of those settings. Its record count supplies the save counter. The initial result is `Not saved`; an accepted Apply displays `Saved <count>: <username>; feature enabled/disabled`. Further editing/toggling changes the draft and summary without changing the saved copy or result until another Apply. This observation is an in-memory host operation; it supplies no persistence or fallible/asynchronous save protocol.

The combined sequence starts at `Ada` / false. Two logical `FocusNext` events focus username, committed text inserts `本`, and `FocusPrevious` plus `Activate` toggles the feature true. Two `FocusNext` events reach Apply. Keyboard and gamepad logical `Activate`, pointer release and semantic activation then request the same `settings.apply` descriptor/executor, each saving a copy of `Ada本` / true once. A pointer press alone requests no action. Moving back to username inserts `!`, moving back to Checkbox toggles false, and a later semantic Apply saves `Ada本!` / false. Physical key/gamepad mapping remains host-owned.

For each combined command, the host copies its accepted draft, stages observations and full-tree presentation, then calls the injected save operation only for an accepted Apply candidate before publishing the replacement. Returned measurement/paint errors restore observations and retain draft, saved copies/count/result and accepted document/inspection/command generation, with the supplied expression origin. Failed and successful execution sequences are consumed once. Authored-disabled and command-disabled Apply owners deny logical focus/activation, pointer, semantic and direct resolution. Pending invocations and old-tree owners reject after replacement, including an equal-command-generation foreign tree. Malformed field candidates also preserve the accepted workflow. Allocation failures propagate; this is no general exception transaction or external-save rollback contract.

The scripted consumer uses a fixed logical viewport, explicit scale/locale/clock, placeholder text metrics and synthetic glyph coverage. It records normalized actions plus the host's accepted document/style replacements, then compares replay geometry, semantics, paint and CPU images. Raw editing keys/text and edit payloads are host-translated and represented by accepted replacement views; replay reproduces recorded views without executing the application's C++ command host. Images and source replacements stay in memory; no caret geometry, composition/IME, clipboard, window, installed font, file save, native input device or GPU is implied.

## Implemented copyable edit/Apply starter boundary

The [standalone starter source](../../examples/settings-starter/main.cpp) and [CMake project](../../examples/settings-starter/CMakeLists.txt) expose the combined edit/toggle/Apply operation without extracting host code from the regression fixture. The [walkthrough](../guides/settings-starter.md) owns copy/build/run instructions. `Field` and `Settings` compose ordinary typed elements with explicit IDs and one session; application-owned form/control/status class declarations resolve through the shared cascade, with a typed Apply background override.

The starter's host retains accepted draft/edit state and owned save records. Focused committed text and the form skeleton's supported editing keys route through live ordinary command ownership before logical navigation. Its compact sequence inserts `本` after `Ada`, toggles true, applies by keyboard, inserts `!`, then applies by gamepad logical activation. Each Apply appends one owned settings copy; the first copy and saved-result Text remain unchanged by the intervening edit. Inspection exposes the draft, byte selection, Checkbox, derived summary and saved result. Full-tree replacement recovers focus by author ID.

Command execution proposes values; full-tree eligibility/style/layout/inspection/paint stages before host acceptance, save copying and session publication. Returned staging failure restores session observations and retains accepted host values, saves and presentation before exiting with diagnostics. Candidate command counters and consumed execution sequences are not restored. This bounded exit path provides no arbitrary exception or external save rollback. The regression fixture owns fault injection, retry and stale-owner coverage.

The starter uses a fixed 640×360 logical viewport, scale one, time zero, placeholder text and synthetic scalar glyphs. Repeated CPU captures observe accepted paint in memory. Input views borrow their presentation synchronously; preparation borrows the sheet, shaper and lowered source/style inputs, while the returned presentation owns its observations. Rasterizer/cache/capture lifetimes are nested in borrowing order. Local `add_subdirectory` and FetchContent imports consume only `tessera::core`; the starter supplies no native host, real-font capture, persistence or replay of C++ host execution.

## Implemented section-selection boundary

The [Settings fixture](../../examples/settings/main.cpp) also composes `SectionSettings` with ordinary C++ iteration and conditional branches through the same form API. The host owns a closed ordered list of `account`, `feature`, `about` IDs and its selected string, initially Account in that order. Each choice is an ordinary Button with stable `section-<id>` author identity and `settings.section.<id>` command. Its label has a `* ` prefix when selected; `selected-section` reports the selected ID. Selection is application data independent of runtime handles and username byte anchor/caret.

Only the selected branch is authored: Account contains the username row, Feature the Checkbox row, About a help Text. Summary, Apply and saved result are outside the branch. The single session's observations and the host's edit owner/revision/selection, draft and owned save copies outlive branch removal. The composition has no per-section local state requiring keyed component ownership. Rebuilding the C++ element tree uses explicit IDs and the ordinary full-tree preparation/publication boundary, without a new authoring convenience or lifecycle mechanism.

The normalized sequence starts with four `FocusNext` events to username and committed `本`, producing `Ada本` at 6:6. Two `FocusPrevious` events and keyboard `Activate` select Feature; two `FocusNext` events reach Checkbox, `Activate` toggles true, and `FocusNext`/`Activate` saves one owned `Ada本` / true copy. Two `FocusPrevious` events and gamepad logical `Activate` select About. Pointer press alone changes nothing; release selects Account. A semantic request selects Feature. These selection routes resolve ordinary Button activation through command eligibility and the common executor; each selection preserves the draft and saved result. Pointer dispatch does not move logical focus in this host policy.

Measurement and paint rejection for the About selection return expression-located diagnostics before accepting the branch. A fresh semantic request retries About, then selects Account; `FocusNext` reaches username. Reorder to `about, account, feature` retains username focus and the exact edit observation. Removing unselected About preserves them. Removing selected Account uses a host candidate selecting the first remaining section, Feature; focus recovers to Checkbox after the nearest surviving preceding choice. Restoring all three choices while Feature stays selected retains Checkbox focus; selecting Account recovers focus to username and projects its retained edit observation. This uses the [ordinary focus recovery contract](../architecture/input.md#implemented-prototype-focus-dispatch), not a component lifetime attached to list position.

The host rejects empty, duplicate or unknown section lists and a selected ID absent from the candidate, with an owned source diagnostic. Returned staging errors preserve accepted selection/order, edit observation, draft, save copies/result, document, inspection, command generation and paint. Disabled choices deny focus/logical activation, pointer release, semantic and direct command resolution. Pending invocations and replaced-tree owners reject even when author IDs recur; foreign trees with equal command counters and the removed username's old action owner also reject. Entered successful and failed command sequences are consumed once. These are synchronous host candidate rules with propagating allocation failures, not generalized application rollback.

The section consumer declares a fixed viewport, scale, locale and clock with the same placeholder metrics and synthetic glyph boundary as the combined form. Accepted list/branch replacements and host-translated text edits are recorded as replacement views. Replay observes accepted geometry, semantic names, paint and CPU bytes without executing section-selection or save hosts. Native input and dynamic component mounting require separate consumer scope.

## Implemented constrained-scrolling boundary

The [Settings fixture](../../examples/settings/main.cpp) also composes `SectionSettings` in a 720×160 logical viewport. Its root `settings` Column supplies ordinary `overflow: scroll`, 12-point padding and 12-point gaps; children retain their natural sizes. That root is the single scroll owner, initially at zero. Account's username extends beyond the viewport and Apply begins below it. The application composition declares overflow through `Props::style`; offset storage, input routing and candidate publication belong to the host, using the existing [layout scroll contract](../architecture/layout.md#implemented-prototype-algorithm) and [scroll input APIs](../architecture/input.md#implemented-scroll-routing).

The host stores an applied `Point` under the stable `settings` author identity and rebuilds the per-node offset span after lowering each candidate. Requested offsets are clamped by layout to the new extent. Scroll and command candidates prepare the entire document, styles, layout, inspection and paint before accepting the new snapshot and applied offset. Commands and navigation reveal recovered or newly moved focus using `scroll_into_view` on a copied focus dispatcher, then stage again if the offset changes; wheel input alone preserves logical focus without revealing it. Branch replacement retains the requested offset, clamps it to the new extent and reveals recovered focus before publication. Neither node indices nor runtime handles identify persistent scroll state.

The normalized sequence routes +48 vertical units at (16,16), then four `FocusNext` events reach and reveal username. Committed `本` produces `Ada本` at byte selection 6:6 through the ordinary editing command. `FocusNext` reveals Apply and gamepad logical activation saves one owned draft copy. Pointer press/release at the revealed Apply bounds requests its ordinary command once on release; the probe does not execute a second save. +4096 clamps at the bottom. Selecting shorter About while Apply holds focus clamps the retained bottom offset; restoring Account retains editing and saved observations. -4096 returns to zero without changing them, and `FocusPrevious` reveals username again. Feature selection recovers/reveals Checkbox, keyboard activation toggles true, and `FocusNext`/activation saves `Ada本` / true. About/Account replacement preserves the exact edit owner, revision, anchor/caret, draft, saved copies and result.

Every accepted observation joins descendant clips, inspection geometry, derived draft/section/save text, paint and CPU capture. Clipped Apply cannot be hit; revealing it makes pointer dispatch find its activation owner. Non-finite scrolls and stale reveal targets reject. Command-disabled Apply denies focus, pointer, semantic and direct requests, and pending invocations reject after replacement. Injected measurement and paint failures during scroll or Apply preserve accepted offsets, focus, host data, document, inspection, command generation and paint; command requests are consumed once. Restaging after rejection reproduces the accepted document, geometry and paint. These synchronous candidate rules do not provide general exception or external-operation rollback.

For replay comparison, each accepted document/style view starts at zero offset and explicitly reconstructs its host offset through a normalized Scroll at (16,16), followed by a fixed tick. Repeated replay must equal the accepted geometry, semantic records, paint and independently captured CPU bytes. This per-view replay does not serialize host offset retention or re-execute the application's navigation/edit/save sequence. The section and combined fixtures separately record their command sequences as replacement views. Scale 1.25, locale `en`, placeholder metrics and synthetic glyphs remain explicit fixture inputs; no native window/input, real-font capture, persistence or generalized ScrollView API is implied.

## Implemented reusable-style boundary

The [Settings fixture](../../examples/settings/main.cpp) composes a styled variant of the constrained form through existing `Props::classes`, `Props::style`, `StyleSheet` and `Theme`. An application-owned `SettingsAppearance` holds the two ordinary style inputs; it is not a public authoring API or a second style resolver. Repeated section Buttons, username, Checkbox, Apply and Appearance share a `control` class. Section choices also have `section`; heading and summary/result Text use `heading` and `status`. These classes belong to the application, including their names.

The comfortable theme supplies body size 16, root gap 12, control padding 4 on every edge, ink `(0.2, 0.2, 0.25, 1)` and surface `(0.95, 0.95, 0.98, 1)`. Compact supplies body size 14, root gap 8, control padding 2, ink `(0.1, 0.15, 0.2, 1)` and surface `(0.85, 0.9, 0.95, 1)`. Theme defaults bind these exact typed variables. The explicit control class adds a one-unit border with color `(0.35, 0.4, 0.5, 1)` and radius 4, replacing the theme's radius 1. Section text has weight 600; heading size is 20; status ink is `(0.25, 0.3, 0.4, 1)`. Apply's instance background `(0.15, 0.3, 0.55, 1)` replaces the theme surface. Generated control Text inherits its owner's typography and ink through the [shared cascade](../architecture/styling.md#implemented-prototype-style-resolution). Root padding/background and row spacing remain ordinary instance declarations.

An Appearance Button after the saved-result Text requests `settings.appearance`. Its ordinary command host alternates comfortable/compact, stages the candidate theme with all presentation stages and accepts it only after success. Pointer release, logical keyboard/gamepad activation and semantic requests use the same owner and execution boundary. Switching retains section, username owner/revision/byte selection, feature draft, saved copies/result and focused author identity. Applied offsets are clamped to new geometry; recovered focus is revealed before acceptance. Wheel-only changes preserve focus without reveal, as in the constrained scrolling boundary.

Inspection verifies exact resolved values, generated-label inheritance, clips and bounds. Switching while username holds focus changes the content extent and reveals the field; switching after Apply retains saved data and reveals the focused control. Wrong variable types, zero text size, a negative sheet radius and injected measurement/paint errors reject without changing accepted theme, offsets, focus, draft/save observations or presentation. Host-authored theme/sheet errors keep their field paths and the fixture's expression origin; executor diagnostics carry its ordinary `/result/host` prefix. Entered requests are consumed once, and fresh requests can retry. Command-disabled Apply/Appearance and stale pending invocations reject through ordinary eligibility.

Each accepted document/resolved-style view reconstructs its offset and must reproduce geometry, semantics, paint and CPU bytes through repeated replay under the constrained fixture's declared inputs. Replay consumes resolved styles; it does not re-execute theme selection or the C++ host. Interaction feedback follows the boundary below. Theme loading, subtree themes, native controls and generalized style conveniences are separate consumer operations.

## Implemented interaction-feedback boundary

The [Settings fixture](../../examples/settings/main.cpp) attaches ordinary state rules to the application's `control` class for section Buttons, username, Checkbox, Apply and Appearance. The hover border is `(0.2, 0.5, 0.8, 1)`, focus `(0.7, 0.35, 0.1, 1)`, active `(0.15, 0.25, 0.45, 1)` and disabled `(0.6, 0.6, 0.6, 1)`. Disabled ink is `(0.45, 0.45, 0.45, 1)`. Sheet order is hover, focus, active, disabled. The shared resolver suppresses other states for inherited disabled nodes. These rules change border color and ink without changing border widths, spacing or typography; theme defaults and Apply's instance background retain their ordinary cascade precedence. Generated Text inherits ink, while focus styling matches only its control owner.

The host derives `InteractionState` from copied pointer/focus dispatchers. Same-tree pointer feedback prepares full resolved styles, layout with retained offsets, source inspection and paint before accepting either visuals or pointer state. Normalized move/down/out/back/up/cancel over a generated label therefore updates its ancestor's hover/active rule without replacing the tree or migrating a press. Press alone emits no command; matching release requests its ordinary activation owner and passes through the shared command executor. Cancellation prevents release activation. Pointer input preserves logical focus. Logical navigation prepares owner focus feedback and reveals the target using the constrained-scrolling boundary.

Command, branch, scroll and theme candidates use full document replacement: focus refresh recovers by author identity before state resolution, and pointer refresh clears the old tree's pointer state. No hovered/pressed handle is remapped by author ID. The next pointer event uses accepted bounds and clips. Username owner/revision/byte selection, draft, selected section, saved copies/result, theme and applied offsets obey the preceding boundaries. Feedback-only updates preserve geometry, clips and command generation.

Returned measurement or paint rejection leaves accepted visuals, pointer/focus state, offsets and application observations intact, with source-located diagnostics; a fresh candidate can retry. This is a synchronous host staging boundary, with propagating allocation failures. Command-disabled Apply/Appearance use the same disabled styles and ordinary focus, pointer, semantic and command guards. An authored ancestor-disabled document also suppresses descendants' hover/active/focus values and projects disabled ink to generated labels, even when the resolver receives those handles explicitly.

Each accepted feedback view uses the constrained fixture's per-view replay reconstruction and repeated geometry/semantic/paint/CPU comparison. Replay receives resolved styles; it does not derive interaction styles or execute the C++ input and command hosts. The consumer supplies no public style facade, automatic invalidation, native pointer capture or additional editing operation.

## Proposed application workflow

Use a small Settings editor as the reference for ordinary UI authoring. A developer should build it from the [C++ authoring surface](../proposals/cpp-authoring.md) and reusable components without assembling graph nodes, mounting records or renderer internals.

The application presents settings sections, a username text field, an enable-feature checkbox, derived status text and an Apply command. A reusable settings-row component accepts typed props and child content. Conditional help/status and a small keyed list of settings sections exercise composition, repeated UI and stable selection. A bounded viewport requires scrolling to reach part of the form. The host owns the settings data and the save/apply operation; an injected save service or observable host result is sufficient before filesystem persistence is justified.

Begin with Text, Row, Column, Button, state and a derived summary. Add Checkbox, bounded TextInput and style conveniences from this same workflow. Each extension must name the application operation it enables and its stop condition. Additional controls, platform adapters and application shells are separate consumer choices.

## Proposed interaction and observation

- Edit the username through normalized input, move the caret, extend selection and replace selected text. Text editing and later clipboard/composition behavior follow [input](../architecture/input.md#proposed-editing-ime-and-clipboard-boundary), with typography behind the [text interface](../architecture/text.md).
- Toggle the feature, update its derived summary and conditional content, and retain compatible local state/focus while keyed settings sections reorder. Application selection is distinct from text selection and runtime handles.
- Scroll the constrained form and keep visible paint, hit geometry, semantic bounds and navigation consistent. Use existing [layout](../architecture/layout.md) before proposing a new algorithm.
- Invoke Apply through ordinary commands and observe the host's accepted settings/result. Pointer, keyboard/gamepad and semantic requests share eligibility and command execution; define the fixture's exact normalized mappings before implementation.
- Apply reusable styles and theme variables, including hover, focus, pressed and disabled states, through [styling](../architecture/styling.md), then inspect the same accepted presentation used for capture and replay.

## Verification requirements

Declare viewport/scale, initial state, normalized input, time, fonts/shaper, assets, save-service results and backend configuration. Verify state/derived-state agreement, text revision/selection, keyed identity, command results and save observations numerically or semantically. Repeated [replay](../architecture/replay.md) and CPU-reference captures must reproduce accepted observations; use selective images for paint behavior rather than per-widget screenshot suites.

Invalid props, bindings, styles or replacement candidates must report actionable source diagnostics and preserve the accepted presentation. Test lifetime cleanup and stale requests at affected boundaries under the [testing guide](../guides/testing.md). Native IME/clipboard, real-font and GPU claims require their own declared configuration evidence in [support](../reference/support-matrix.md).

## Authoring feedback and onboarding

Treat this example as a copyable starting point. Record friction from composing fields, changing state, binding commands, styling, reading diagnostics and verifying the result; use it to choose the smallest API/runtime change. Async-data, custom-component, styling, inspector, asset-browser and hosting examples should each answer one developer question when their consumer scope is selected. A broad example directory tree is not an implementation requirement.

Stop expanding the consumer when its promoted application operations and required invariants pass. A complete visual editor, generalized portal system, broad widget catalog and native platform integration suite are not implicit dependencies.
