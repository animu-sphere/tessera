# Renderer diagnostics UI

The Proposed sections define a consumer workload: express an interactive renderer diagnostics panel through Tessera's ordinary C++ authoring, commands, input, inspection and rendering boundaries. [Current work](../roadmap/current.md) owns scheduled operations and acceptance; this design does not activate its entire inventory. Implementation and validation evidence belongs only in [support](../reference/support-matrix.md).

## Proposed consumer workflow

Use the hydra-toon viewport's Telemetry overlay as a concrete authoring reference. A developer composes named timing rows, counters, a bounded frame-history plot, disclosure sections, choices, toggles and numeric controls without importing ImGui or assembling component/runtime internals in ordinary panel code. Matching information and operations matters more than reproducing ImGui's appearance or API.

The reference separates frame observations from requested controls in `OverlayFrame` and `OverlayControls`. Preserve that separation with application-owned snapshots and ordinary command requests; those external structs are source references, not new Tessera public types. The source-review provenance and inventory are recorded in [support](../reference/support-matrix.md#renderer-diagnostics-source-review--2026-10-17).

| Consumer group | UI expression | Host-owned information or operation |
| --- | --- | --- |
| Frame summary | Scene/device, extent, presentation mode, frame time/FPS/p99 and bounded history plot | Frame identity, sampling window, units and history samples |
| CPU/GPU/latency | Repeated labeled rows with mean/p95/max/stddev; unavailable states and explanatory text | Measurements, summaries, timestamp availability and latency meaning |
| Draws/uploads/session | Counter rows and small aligned tables; collapsible groups | Draw/triangle/pipeline counts, per-frame/session transfers and validation observations |
| Render controls | MSAA choice, outlines/self-shadow toggles, material-view choice, bounded scalar/vector controls and reset | Supported values, accepted settings and renderer-side execution |
| Animation | Play/pause, start/step, time, speed and loop with explicit eligibility | Time range, playback clock and deterministic-capture policy |
| Materials/morphs | Bounded repeated object groups, numeric values, override state and release actions | Stable object IDs, evaluated values, edits and override lifetime |
| Skeleton/avatar diagnostics | Repeated diagnostic rows, selection, errors and optional scene visualization | Joint/runtime identities, transforms, bindings and projected scene marks |

This mapping is a consumer inventory, not a requirement to implement a generic Table, TreeView, Combo, Plot, docking system or every editor. Small tables and expanded sections can be composed from ordinary Rows, Columns, Text and Buttons. Add the minimum reusable control only when a promoted operation demonstrates why existing composition cannot express it. Domain-specific editors and scene visualization need their own bounded operation before core work.

## Proposed data and command boundary

- The host owns renderer telemetry, sampling/aggregation, bounded history storage, scene data, accepted settings and frame scheduling. Capture immutable owned display data at an update point; borrowed renderer records must be copied or remain alive through synchronous preparation. The panel does not query a GPU or renderer while layout, paint or semantic projection traverses it.
- Pass backend-neutral values with stable row/object names, units, availability and sample identity. An unsupported GPU timer or an empty sample series displays an explicit unavailable marker, distinct from a measured zero. Do not label input-to-submit/presentation API measurements as measured display latency.
- Host observations may update at a readable cadence independently of renderer sampling. Publish timing rows, counters, history and settings from one accepted snapshot; retain disclosure, selection, focus and scroll state by stable identity across refreshes. A telemetry refresh must not execute render-setting commands.
- Commands request setting changes after dispatch. The host validates finite numbers, ranges, supported sample counts/enums, object identity and live eligibility before proposing accepted settings. Numeric editing must preserve the last accepted value on invalid input. Presentation failure retains the accepted panel/settings and produces actionable diagnostics; it does not undo an external GPU operation. A fallible or asynchronous renderer change needs an explicit host acknowledgement/error policy before integration.
- Pointer, keyboard/gamepad and semantic operations use the same commands and eligibility. Normalize platform input at the host boundary and arbitrate panel versus camera input there. Consumed panel input must not also operate the camera. Native capture, file dialogs and device polling remain host adapters.
- Use the ordinary [full-tree lifecycle](../architecture/overview.md#update-and-snapshot-rules), [authoring contract](../architecture/ui-model.md#implemented-c-form-authoring), [input](../architecture/input.md), [commands](../architecture/commands.md), [layout](../architecture/layout.md), [styling](../architecture/styling.md) and [rendering](../architecture/rendering.md). Core APIs and serialized UI definitions contain no Hydra, OpenUSD, Vulkan or ImGui types.

## Proposed bounded reference panel

Separate reusable panel composition and a small host-facing data/command interface from deterministic fixture machinery. An independent core-only consumer must be able to copy or import that composition, inject snapshots and observe requested operations without a live renderer, window or optional SDK. Exact public syntax is an implementation choice constrained by ordinary authoring and ownership.

Begin with a frame summary, CPU/GPU timing rows, a frame-history plot, draw/upload/session counters and collapsible sections in a constrained viewport. Keep history bounded and pair the chart with inspectable textual summary and sample identities; do not require a new scene renderer or general charting framework. Host offsets and focus reveal follow the same [scrolling boundary](settings-app.md#implemented-constrained-scrolling-boundary) as Settings.

Use representative controls to prove editing rather than only rendering a static mockup: samples 1/2/4/8 subject to host capabilities, outlines, scene-light selection, direct/ambient strength in [0,4], a key-direction vector with components in [-1,1], material-view choice and reset. Numeric operations need direct value entry and pointer/keyboard/gamepad adjustment; their minimal composition/control design must declare step, bounds, commit and cancellation rules before implementation. Enum choices may use repeated Buttons instead of requiring a popup mechanism.

Changing a control proposes a host request and displays the accepted result. External refreshes can change telemetry while the user expands a section or edits a value; retain the relevant interaction state and keep draft numeric text separate from accepted renderer settings. The synthetic host must expose request counts and accepted settings so read-only refresh, rejection and once-only operation are observable.

Playback, object override editors, skeleton/avatar rows and scene-space marks describe further use of this boundary. A representative panel is sufficient before porting the complete hydra-toon overlay. The host's scene renderer retains scene drawing; Tessera paints the panel through its own renderer contract. Translating ImGui draw lists or hydra-toon's overlay triangle format is not a substitute for Tessera-authored semantics and input.

## Proposed representative control boundary

This section defines consumer operations and host policy, not a public numeric widget or working source API. [Current work](../roadmap/current.md#current-slice) selects the bounded implementation; the other operations in this section do not become prerequisites for it. Compose ordinary Checkbox, TextInput and Button elements in Rows/Columns under one controls disclosure header. Keep telemetry snapshots separate from accepted settings, capabilities and numeric drafts. Stable author IDs derive from setting names and operations, never displayed values or row indices.

### Proposed settings and capability observations

Use the following owned synthetic settings and capabilities to make validation independent of renderer execution. Defaults describe fixture data, not hydra-toon renderer defaults. The host validates the entire accepted-settings candidate before preparing its presentation.

| Operation | Ordinary composition | Synthetic initial value and validation |
| --- | --- | --- |
| MSAA | Repeated Buttons with accepted-value text | See the [Implemented MSAA choice boundary](#implemented-msaa-choice-boundary) for values, capabilities and validation. |
| Outlines and scene lights | Two controlled Checkboxes | See the [Implemented outlines boundary](#implemented-outlines-control-boundary) and [Implemented scene-lights boundary](#implemented-scene-lights-control-boundary) for independent values, eligibility and Boolean requests. |
| Direct and ambient strength | Two instances of the numeric composition below | See the [Implemented direct-strength boundary](#implemented-direct-strength-control-boundary) and [Implemented ambient-strength boundary](#implemented-ambient-strength-control-boundary) for values and validation. |
| Key direction | Three named numeric compositions for x/y/z | Initial (0,0,-1); each component finite inclusive [-1,1], step 0.25. A component request changes only that component. The synthetic host neither normalizes the vector nor rejects a zero vector; renderer-specific direction requirements need a separate integration policy. |
| Material view | Repeated Buttons with an explicit selected marker | Synthetic strings `shaded`, `normals`, `base-color`, initial `shaded`; reject any other value and apply host eligibility. These strings are consumer choices, not renderer enums. |
| Reset controls | One Button and one ordinary command | Atomically propose the initial settings above and reset all numeric drafts. Enable only when every affected setting is eligible and every reset value meets capabilities; otherwise reject the whole operation. No partial reset or implicit renderer call. |

Publish capability/eligibility changes through a complete candidate presentation. Reject a capability set that excludes the accepted setting; changing capabilities does not silently choose a replacement or reset drafts. Telemetry-only refresh cannot change settings or issue a setting request. Keep draft editing and disclosure request counts distinct from accepted setting changes and setting-handler attempts, including failures.

### Proposed numeric entry and draft lifetime

Compose each numeric field from a labeled controlled TextInput, Decrease/Increase Buttons, Apply/Cancel Buttons, and separate Text for the accepted value and any validation diagnostic. Accessible names include the setting and operation. This uses ordinary button semantics and logical string editing; it does not claim slider, spinbutton or native editable-text semantics. The host owns one `TextEditState` per field and retains its nonzero lifetime owner while the panel exists, including across conditional removal. Presentation node handles are replaced at each acceptance; draft owners and author IDs are distinct identities. Closing the panel expires every draft; reopening allocates fresh owners.

Draft text accepts bounded single-line UTF-8 edits through revision-addressed `TextEditRequest` and `edit_text`, with a consumer limit of 32 bytes. Preserve incomplete or invalid numeric text as a draft without changing accepted settings. Apply parses the whole string with locale-independent ASCII grammar `-?(0|[1-9][0-9]*)(\.[0-9]+)?`, requires finite binary64 conversion and inclusive bounds, and rejects empty text, whitespace, a leading plus, exponents, trailing characters, NaN/infinity and overflow. Negative zero is accepted as zero. Direct entry need not be a multiple of the step. Rejection returns a field-located diagnostic and retains exact draft bytes/selection/revision, accepted values and presentation. The caller displays the returned error separately; it does not require a failed command to publish a new view.

Apply or unmodified, non-repeating Enter while the TextInput is focused proposes the parsed value through the same setting command. Focus traversal or blur does not commit. Merely activating the TextInput focuses it and consumes input without inventing an edit payload or accepting a number. Pointer primary press may focus the live field through `FocusDispatcher::focus`; it does not place a caret. Home/End, Left/Right with optional Shift, Backspace/Delete and normalized committed text follow the existing scalar editing rules before any navigation mapping. Unsupported modified keys remain unmapped. Gamepad users navigate to and activate the same Apply/Cancel and adjustment Buttons; direct text entry requires an injected text source and is not an on-screen keyboard claim.

Decrease/Increase act on the last accepted value, adding -0.25/+0.25 and clamping to the inclusive endpoint, with no wrapping, hold acceleration or slider gesture. Disable the direction already at its endpoint and disable both adjustments while draft bytes differ from the canonical accepted text; invalid pending text therefore cannot be silently overwritten. Canonical text is the locale-independent shortest fixed decimal that round-trips the accepted binary64 value, with zero written `0`. A successful Apply canonicalizes the draft, places selection at its end and advances the edit revision even if the numeric value is unchanged. A successful adjustment does the same. Cancel restores canonical accepted text and advances revision without changing settings. It is available for a differing draft; repeating it must not generate a setting change. Reset follows the all-settings policy above and advances all draft revisions. Revisions never rewind; exhaustion requires a fresh lifetime owner.

Keyboard/gamepad adjustment uses focus traversal or logical Navigate to reach Decrease/Increase and ordinary Activate; Left/Right inside the TextInput keep their editing meaning. Raw Enter/Escape map once to Apply/Cancel only for the focused numeric field, without modifiers or repeat. Logical Cancel from that field or its operation Buttons resolves the same live Cancel activation owner. The host supplies this routing after dispatch through ordinary commands; it does not require authoring a new cancel binding. Semantic callers use live activation owners and the same commands: revisioned edit payloads for entry, parameter-free adjustment/Apply/Cancel for the observed field. They cannot set an unrelated field through an owner. Node-free requests must validate field identity, eligibility, revision where applicable and typed numeric bounds and the canonical draft byte bound as well.

Telemetry refresh preserves each draft's bytes, selection, owner and revision, even when invalid. Collapse preserves all drafts and accepted settings without commit/cancel; its accepted presentation removes the controls and recovers focus to the controls header if focus was inside the removed group. Otherwise preserve eligible focus by author ID. Re-expansion restores the drafts and preserves header focus until navigation. Removing or disabling a live control rejects old presentation invocations; hiding a field does not destroy its retained draft. Re-enablement restores the draft. Only successful explicit editing/Apply/adjustment/Cancel/reset changes its text under this policy; telemetry has no independent settings-update path.

### Proposed command staging and input arbitration

Editing, numeric Apply, adjustment, Cancel, choices, toggles and reset use one host executor and increasing request sequence stream shared with disclosure. Distinguish draft commands from setting commands; editing and cancellation never request renderer execution. Stage owned candidate settings/drafts, disclosure, eligibility, focus, clamped/revealed offsets, commands, document/styles, layout, inspection and paint before replacing any accepted observations. Rejected measurement or paint preparation retains all accepted state, including exact draft revisions, accepted command generation and focus/offset. A command entered before failure consumes its sequence; retry resolves against the accepted presentation with a fresh sequence. Preserve the old view through executor result validation. The synthetic setting handler has no external side effects; real renderer submission needs its own acknowledgement policy rather than inferring rollback from this staging.

Arbitrate before passing events to a synthetic camera. Mark a panel-targeted pointer stream claimed from primary press through release/cancel, retaining that claim across accepted replacements even though the ordinary pointer dispatcher cancels its pending activation. Panel Scroll and recognized focused editing, navigation, activation and cancellation are consumed once, including a returned validation/staging error. A consumed raw key must not also generate a logical navigation/activation event. Stale or disabled panel targets cannot fall through into camera operation. Unsupported raw keys/text and pointer streams begun outside the panel may reach the camera once; they issue no panel command. Device adapters normalize these events outside core. The camera fixture counts delivered events only; it makes no physical-device or scene-motion claim.

Verify direct entry versus adjustment parity from a shared initial value, invalid/incomplete text retention, both bounds, revision/owner rejection, refresh/collapse retention, once-only commands and failed-stage retry. Compare accepted-view semantics, geometry, paint and repeated CPU/replay captures using the telemetry configuration. Replay reconstructs accepted replacement views; command execution and camera arbitration require separate scripted host assertions. Independent consumption must copy the exact reusable sources and updated small host through both local import modes using only `tessera::core`; extend the working guide only alongside implemented source. General numeric widgets, native text/IME, pointer dragging, wheel adjustment and continuous transactions require a separate consumer need.

## Implemented ambient-strength control boundary

[NumericControl](../../examples/renderer-diagnostics/panel.hpp) composes a second named numeric field beside [direct strength](#implemented-direct-strength-control-boundary), using the shared numeric policy and ordinary authoring. [Host](../../examples/renderer-diagnostics/host.hpp) exposes `ambient()` alongside the direct `numeric()` observation; `NumericField::direct` and `NumericField::ambient` explicitly select composition, parsing, revisioned edits and eligibility. The `NumericControl`, `parse_numeric`, `request_edit` and `numeric_eligibility` forms without an explicit `NumericField` retain direct-strength behavior. This is application composition, not a public numeric widget. Compose `Ambient strength` with stable `ambient-input`, `ambient-decrease`, `ambient-increase`, `ambient-apply`, `ambient-cancel`, `ambient-accepted` and `ambient-control` author IDs under controls disclosure. Use `ambient.edit`, `ambient.decrease`, `ambient.increase`, `ambient.apply` and `ambient.cancel` actions and a separate node-free `ambient.set` command. `NumericControl(value, field)` supplies the two identity/label variants while preserving direct identities and caller behavior.

The host owns accepted ambient strength, initially 0.5, an independent eligible flag initially true, and a `TextEditState` initialized to `0.5`. Its nonzero lifetime owner differs from direct strength and every closed panel's owners. Accept finite binary64 values in inclusive [0,4], with step 0.25 and the shared 32-byte decimal grammar/canonical text bound. Apply accepts arbitrary in-range decimal fractions; Decrease/Increase clamp the accepted value and are unavailable at their endpoint or while this field's draft differs from its canonical accepted text. Successful Apply, typed set and adjustment canonicalize only ambient text, move its selection to the end and advance its revision, including an equal-value Apply/set. Cancel restores only ambient canonical text and advances its revision without a setting attempt; it is enabled only for a differing draft. Blur and focus traversal do not commit. Exhausted revisions require a fresh lifetime.

Activation of each operation uses its fixed field with no arguments. Activating `ambient-input` focuses it without editing. Semantic edit requests explicitly select a field and carry its exact owner/revision plus the existing typed editing payload; reject a direct owner on an ambient request and the reverse, including equal revision counters. Node-free `ambient.set` requires exactly string field `ambient` and numeric `value`; reject missing/extra fields, coercion, non-finite/out-of-range values and canonical text beyond 32 bytes. Resolution and execution use the ordinary visibility, independent eligibility, accepted presentation/owner and sequence checks. Explicit field dispatch must reject unknown identities instead of falling through to direct strength. `request_edit(NumericField::ambient, request, source)` resolves the ambient activation owner and validates that field's draft identity during execution. `numeric_eligibility(NumericField::ambient, enabled, text)` stages only its eligibility. `request_value("ambient", value, source)` selects the ambient node-free command; unknown field strings reject. Neither current focus nor a matching revision alone authorizes editing another field.

Focused text/selection/edit keys and raw unmodified non-repeating Enter/Escape resolve against that field's draft and Apply/Cancel owners. Logical Cancel from a numeric input or its operation Buttons cancels that same field through its live activation owner. Moving between the fields or to another control preserves both drafts. Pointer press focuses without caret placement; pointer release, logical navigation/activation and semantic operation follow the shared command path. Gamepad text entry requires injected text. Keep the shared panel/camera claim and consumption rules, including recognized errors and replacement through terminal release/cancel.

Every ambient operation preserves direct accepted value, exact draft bytes, selection, owner/revision and eligibility, plus MSAA accepted samples/capabilities/eligibility, both Boolean values/eligibility, telemetry and disclosure. Direct operations preserve the ambient observations in the same way. Disabling either numeric field cannot disable the other. MSAA and Boolean commands must leave both numeric drafts untouched, including invalid text; dirty state and adjustment eligibility are per field. Refresh, controls collapse/re-expansion and eligibility publication preserve both drafts without parsing them. Collapse from either numeric field or operation recovers/reveals `disclosure-controls`; otherwise retain eligible author-ID focus and apply ordinary recovery/reveal.

Stage owned copies of both numeric observations with the existing complete candidate before acceptance. Returned measurement/paint errors retain both fields and every accepted setting/view observation; report bounded diagnostics located at the affected field or preparation source. Entered setting commands count one attempt even on parse/preparation failure and consume their sequence; retry needs a fresh request. Successful equal values count one attempt and no change; successful changed values count one attempt and one accepted setting change. Editing/Cancel count only draft requests; telemetry, eligibility and disclosure issue no setting request. Verify cross-field retention in both directions, independent eligibility, stale owners/presentations, rejected-stage retry, synthetic camera accounting and accepted-view CPU/replay parity in the [fixture](../../tests/integrations/renderer_diagnostics_tests.cpp). Renderer acknowledgement, vector controls, reset and generalized numeric/input frameworks require separate consumer selection.

## Implemented scene-lights control boundary

[SceneLights](../../examples/renderer-diagnostics/panel.hpp) and the [host](../../examples/renderer-diagnostics/host.cpp) define one synthetic scene-light selection. `Panel(snapshot, disclosure, numeric, msaa, outlines, scene_lights, ambient)` composes an ordinary controlled Checkbox labeled `Scene lights` after Outlines under controls disclosure, with stable author ID `scene-lights-toggle`. `Host::scene_lights()` exposes owned `SceneLights` observations: `accepted`, initially true, and independent `enabled`, initially true. `scene_lights_eligibility(enabled, text)` stages eligibility with the full presentation. These are independent of outlines, MSAA, numeric eligibility and telemetry. The marker observes the accepted value through the [form authoring contract](../architecture/ui-model.md#implemented-c-form-authoring); the button semantic name is `[x] Scene lights` or `[ ] Scene lights`. No new semantic role, property or serialized widget kind is required.

Use a parameter-free `scene_lights.toggle` command for activation. `request_scene_lights("scene_lights", value, source)` resolves a separate node-free `scene_lights.set` command requiring exact string field identity `scene_lights` and an exact Boolean `value`. These names define the consumer request boundary, not renderer enums. Activation requests the inverse accepted value and accepts no arguments. Set accepts either Boolean, including the accepted value; reject other fields, missing/extra arguments and number/string coercion through ordinary command schemas. Both commands require scene-lights eligibility and expanded controls. Disabled/collapsed requests, stale or foreign command observations/activation owners, and consumed sequences must reject before another handler entry. No request may mutate outlines or substitute another setting's owner.

Stage scene-lights settings and eligibility with the whole candidate through every refresh, disclosure, navigation, editing and setting path. A successful toggle or set enters the shared setting handler once; an equal-value set publishes a new accepted presentation with one attempt and no accepted setting value change. Compare all accepted settings when accounting for changes. Eligibility updates, telemetry, navigation, disclosure and draft operations issue no scene-lights setting request. Disabling scene lights affects neither outlines nor other control eligibility; disabling those other controls leaves eligible scene lights operable. Closing or reopening the synthetic host follows the existing panel/draft lifetime policy rather than renderer persistence.

Preserve exact direct-strength draft bytes, reverse selection, lifetime owner/revision and accepted numeric value, including incomplete or invalid text such as `2.`. Preserve MSAA accepted samples/capabilities/eligibility, outlines accepted value/eligibility and disclosure across scene-lights operations. A/B/C refresh cannot overwrite either toggle. Collapse retains all host settings/drafts and removes the activation owners; collapse from any controls owner, including `scene-lights-toggle`, recovers/reveals `disclosure-controls`. Re-expansion preserves header focus. Other accepted replacements preserve eligible author-ID focus and clamp/reveal through ordinary geometry; disable/re-enable preserves settings/drafts without an implicit toggle or commit.

Use the existing executor and increasing sequence stream shared with all other controls. Prepare owned candidate settings/eligibility, disclosure, focus/revealed offsets, command snapshot, document/styles, layout, inspection and paint, then publish only after successful executor result validation. Returned measurement/paint failures for toggle, set or either eligibility candidate retain every accepted observation and return bounded source-located diagnostics. An entered failed setting handler counts one attempt, no accepted change, and consumes its sequence; retry resolves a fresh request against the accepted presentation. Eligibility preparation failure enters no setting handler. Synthetic handlers have no external renderer side effects; native submission requires its own acknowledgement policy.

Pointer release, raw keyboard navigation/activation, logical gamepad Navigate/Activate and semantic activation use the same live owner and commands. Retain panel pointer claims through release/cancel across replacement, even when dispatcher activation is canceled. Disabled panel hits and recognized raw/pointer operations with preparation errors remain consumed and cannot reach the camera or produce a second logical activation. Unsupported keys/text and outside pointer streams follow the existing host arbitration policy. Verify the independent two-toggle states, exact unrelated-state retention, equal sets, typed/stale/disabled rejection and failed-stage retry in the [fixture](../../tests/integrations/renderer_diagnostics_tests.cpp). Accepted-view CPU/replay comparisons observe semantics, geometry and paint; separate host assertions verify commands and camera accounting. The [small copied main](../../examples/renderer-diagnostics/main.cpp) and [walkthrough](../guides/renderer-diagnostics.md#toggle-scene-lights) exercise the same host using both local core-only imports. Vector, material-view, reset and generic settings frameworks require their own consumer selection.

## Implemented outlines control boundary

[Outlines](../../examples/renderer-diagnostics/panel.hpp) and the [host](../../examples/renderer-diagnostics/host.cpp) connect one Boolean operation from the representative inventory. `Panel(snapshot, disclosure, numeric, msaa, outlines, scene_lights, ambient)` composes an ordinary controlled `Checkbox` labeled `Outlines` with stable author ID `outlines-toggle` under controls disclosure. `Host::outlines()` exposes owned `Outlines` observations: `accepted`, initially false, and independent `enabled`, initially true. `outlines_eligibility(enabled, text)` stages that eligibility with the full presentation. The checkbox observes the accepted Boolean; activation requests its inverse after dispatch. Use the [form authoring contract](../architecture/ui-model.md#implemented-c-form-authoring): the ordinary button semantic name contains `[x]` or `[ ]` and the label. This policy adds no checkbox semantic role, checked property or serialized widget kind.

Bind parameter-free activation to `outlines.toggle`. `request_outlines("outlines", value, source)` resolves a separate node-free `outlines.set` command requiring exact field identity `outlines` and an exact Boolean value, without numeric/string coercion. Activation cannot supply a value or name another setting. Both commands use the host's ordinary registry, executor and increasing sequence stream shared with numeric, MSAA and disclosure commands. Enable both only while outlines is enabled and controls are expanded. Eligibility changes stage a complete presentation without changing the accepted Boolean; numeric and MSAA eligibility neither enable nor disable outlines, and outlines eligibility does not change theirs.

One entered toggle or set handler adds one setting attempt, including a preparation failure. A successful Boolean change adds one accepted setting change. An equal-value set accepts a fresh presentation and records one attempt with zero changes; a toggle always requests the inverse accepted value. Schema, live eligibility, presentation/owner and sequence rejection before handler entry add no setting attempt. Refresh, eligibility changes, disclosure and draft commands add no outlines setting request. Count accepted changes alongside direct strength and MSAA without resetting or canonicalizing the numeric draft.

Carry the owned Boolean and eligibility through every candidate and accept them only after executor result validation and full-tree preparation. Outlines operations preserve accepted strength, exact draft bytes, selection, lifetime owner and revision, MSAA accepted samples/capabilities/eligibility and telemetry. Telemetry refresh preserves outlines without issuing a setting command. Collapse removes its activation owner while retaining settings/drafts; focus inside the removed controls recovers to `disclosure-controls`. Expansion retains header focus. Otherwise preserve eligible focus by author ID and use ordinary recovery/reveal and offset clamping after eligibility or geometry changes. Held invocations and pointer activations expire on accepted replacement; retained panel pointer claims still consume release/cancel.

Measurement or paint rejection preserves all accepted settings, eligibility, drafts, disclosure, command generation, focus/offset and view observations, with bounded located diagnostics. An entered failed setting command consumes its sequence; retry resolves against the accepted view with a fresh sequence. Pointer, normalized keyboard/gamepad and semantic routes use the same commands and panel/camera arbitration as the [direct-strength host](#implemented-direct-strength-control-boundary). Verify Boolean observations and exact unrelated-state retention, both eligibility directions, equal-value accounting, stale/foreign/hidden/disabled rejection, failure/retry and repeated accepted-view CPU/replay comparisons. Host execution and camera delivery require separate scripted assertions; accepted-view replay does not execute them. The [copied main](../../examples/renderer-diagnostics/main.cpp), [guide](../guides/renderer-diagnostics.md#toggle-outlines) and [fixture](../../tests/integrations/renderer_diagnostics_tests.cpp) exercise the same host through both local import modes and ordinary accepted-view capture. Other controls and a generalized toggle/settings framework require separate consumer selection.

## Implemented telemetry panel boundary

[panel.hpp](../../examples/renderer-diagnostics/panel.hpp) defines owned `Snapshot`, `Statistics`, `Timing`, `Counter`, `Sample` and `Disclosure` values. [panel.cpp](../../examples/renderer-diagnostics/panel.cpp) validates and composes them through ordinary authoring. [host.hpp](../../examples/renderer-diagnostics/host.hpp) and [host.cpp](../../examples/renderer-diagnostics/host.cpp) own the synchronous synthetic publication/input boundary. The [copy/run guide](../guides/renderer-diagnostics.md) explains embedding; [fixture assertions](../../tests/integrations/renderer_diagnostics_tests.cpp) are separate from reusable sources. This section defines the telemetry consumer contract; the direct-strength, ambient-strength, MSAA, outlines and scene-lights consumers are defined in their Implemented sections, and other representative controls use the Proposed sections above.

Reusable typed C++ functions compose labeled value rows, frame history and the panel. The panel iterates over the four disclosure groups and accepts an owned snapshot and host disclosure state as props; it lowers ordinary Text, Button, Row and Column elements in one host-owned authoring session. Conditional children are explicitly recomposed before lowering. A refresh supplies a candidate snapshot independently of command execution; disclosure commands change only candidate disclosure state. This is application source, not a new core telemetry schema or public widget API.

The snapshot owns scene/device/presentation strings, nonzero extent, frame summary, stable named timing/counter records and an ordered history of at most 32 frame-ID/value pairs. Each timing/counter group has at most 32 rows. Row IDs contain lowercase ASCII letters, digits or hyphens, are nonempty and at most 48 bytes, and are unique within their group. Frame IDs are unique, increasing and nonzero. Measurements are finite and nonnegative. Scene/device strings are at most 64 bytes, presentation/reason strings 48 bytes, labels 25 bytes and counter units 16 bytes; required text is nonempty single-line UTF-8. Available timings reject an unavailable reason; absent timing values require one. Diagnostics address the field and record identity before preparation. The host supplies timing aggregates and bounded history rather than asking the panel to sample renderer records; the panel derives history min/max/mean from those supplied samples. An unavailable timing is distinct from a measured zero. Snapshot storage must outlive synchronous preparation; the accepted snapshot and lowered observations own their data and retain no renderer pointers.

Declare three synthetic cases, using mean/p95/max/stddev order for timing tuples. All use scene `Fixture scene`, device `Synthetic device`, extent 1280×720 and presentation `Synthetic FIFO`. These labels make no native presentation claim.

| Observation | Snapshot A | Snapshot B | Snapshot C |
| --- | --- | --- | --- |
| Frame time / FPS / p99 | 16 ms / 62.5 / 24 ms | 20 ms / 50 / 40 ms | Same as B |
| CPU `update`, `submit` | (4,6,8,1) ms; (0,0,0,0) ms | (5,7,9,1) ms; (1,2,3,0.5) ms | Same as B |
| GPU `geometry`, `shading` | (7,9,10,1) ms; (3,4,5,0.5) ms | (9,11,12,1) ms; (4,5,6,0.5) ms | Both unavailable: `GPU timestamps unavailable` |
| Draws / triangles | 12 / 2400 | 18 / 3600 | Same as B |

## Implemented direct-strength control boundary

[Numeric and NumericControl](../../examples/renderer-diagnostics/panel.hpp) compose a controlled TextInput, Decrease/Increase, Apply/Cancel and accepted-value Text through ordinary authoring. [Host](../../examples/renderer-diagnostics/host.cpp) owns the numeric state independently of telemetry. The controls disclosure uses `disclosure-controls`; field/operation IDs are `direct-input`, `direct-decrease`, `direct-increase`, `direct-apply`, `direct-cancel` and `direct-accepted`. They identify one field, not vector positions or displayed values. No public numeric widget, serialized field or semantic role is added.

The accepted synthetic value starts at 1, uses inclusive [0,4] and a 0.25 clamped adjustment. `parse_numeric` accepts the whole ASCII grammar `-?(0|[1-9][0-9]*)(\.[0-9]+)?`, requires finite binary64 conversion and bounds, and normalizes negative zero. Direct entry need not align to the step. `canonical` emits the shortest round-tripping fixed decimal (zero is `0`), keeping accepted drafts compatible with the entry grammar. The draft limit is 32 UTF-8 bytes, including after insertion; a typed node-free value must also fit that canonical bound. Malformed numeric Apply returns a field-located diagnostic without publishing it into the accepted view. The caller can display returned errors separately.

A process-unique nonzero `TextEditState` owner survives telemetry replacement, collapse and eligibility changes for the host lifetime. `request_edit` addresses its exact owner/revision and resolves the live TextInput activation owner; commands carry decimal owner/revision strings without binary64 identity loss. `edit_text` validates selection/scalar operations. Draft byte differences disable both adjustments; endpoints disable their outward direction. Apply, adjustment and Cancel canonicalize the draft, put selection at its end and advance revision, including equal-value Apply. Cancel requires differing bytes and makes no setting request. Revision exhaustion rejects and requires reopening with a fresh lifetime.

`request` on `direct-input` produces a focus-only command; activation creates no edit payload or setting change. `request_value("direct", value, source)` resolves a typed node-free setting command with exact field identity, finite bounds, visibility and eligibility. `invoke`, `request`/`execute` and revisioned semantic editing share one executor and sequence stream with disclosure. `setting_attempts()` counts entries into setting handlers including parse/staging failures; `setting_changes()` counts accepted setting value changes across direct strength, ambient strength, MSAA, outlines and scene lights, and `draft_requests()`/`disclosure_requests()` distinguish non-setting operations. Empty or invalid drafts, stale revisions/owners/presentations, hidden/disabled fields and consumed sequences preserve accepted settings and observations.

The host routes focused committed text, Home/End and Left/Right with optional Shift, Backspace/Delete before navigation. Unmodified non-repeating Enter/Escape at the field invoke Apply/Cancel; logical Cancel at any direct operation invokes the same live Cancel owner. Raw Tab/arrows and Enter/Space map once to ordinary traversal/navigation/activation when not used by editing; unsupported modified keys remain unmapped. Pointer primary press focuses a live eligible activation owner without caret placement. Logical keyboard/gamepad traversal and Navigate reveal the operation Buttons and Activate executes the same commands. Direct gamepad text requires an injected text source.

`numeric_eligibility` stages host eligibility with the complete display. Refresh and collapse preserve exact draft bytes, selection, owner/revision and accepted setting. Collapsing while focus is inside controls recovers/reveals the controls header; expansion retains header focus. All command candidates stage owned settings/drafts, disclosure, command snapshot, focus/revealed offset, document/styles, layout, inspection and paint while keeping the old view alive through executor validation. Returned measurement/paint errors retain their source locations within the command result diagnostic bound (with an omission count when truncated) and preserve every accepted observation; the failed sequence is consumed and a fresh request retries. The synthetic setting handler has no external renderer side effect or acknowledgement protocol.

`route` calls `input` and increments `camera_events()` only for a valid unconsumed event. `last_consumed()` records panel recognition independently of a returned error. Panel Scroll, recognized editing/navigation/activation/Cancel and disabled panel pointer hits are consumed, including preparation/validation errors. A primary stream begun in the viewport remains claimed through release/cancel across accepted replacements even though replacement cancels dispatcher activation. A stream begun outside stays outside through its terminal event; unsupported keys/text or outside streams can reach the synthetic camera once. This counter models delivery, not scene motion or a native input adapter.

The [ambient boundary](#implemented-ambient-strength-control-boundary) extends the same policies to a second independent draft. The [fixture](../../tests/integrations/renderer_diagnostics_tests.cpp) joins operation parity, exact retained state, failure/retry, input arbitration and accepted-view CPU/replay observations. The seven-file copied example exercises normalized entry, gamepad adjustment, semantic adjustment and telemetry refresh through this host. Broader settings and generic numeric/input frameworks use their own consumer promotion rules.

## Implemented MSAA choice boundary

[Msaa and MsaaControl](../../examples/renderer-diagnostics/panel.hpp) compose ordinary Buttons alongside direct strength. [Host](../../examples/renderer-diagnostics/host.cpp) owns accepted samples, capabilities and eligibility independently of telemetry and numeric state. No choice widget or semantic role is added. Compose a labeled MSAA group under `disclosure-controls`, with stable `msaa-1`, `msaa-2`, `msaa-4` and `msaa-8` activation owners and `msaa-accepted` Text. Each Button name includes its sample count and an explicit selected marker when it matches the accepted count. All four choices remain visible while expanded; unsupported choices are disabled. The selected supported choice remains enabled when the setting is eligible, allowing equal-value requests to be observed separately from changes. These are Button semantics, with no implicit radio-group or native selector behavior.

`Host::msaa()` exposes owned `Msaa` observations (`accepted`, `supported`, `enabled`); `msaa_capabilities(supported, enabled, text)` stages capability and eligibility changes separately from `Snapshot` and the direct-strength draft. Initial samples are 1, supported samples are {1,2,4}, and eligibility is true. Capabilities are a nonempty set drawn exactly from {1,2,4,8} and must contain the accepted count; duplicate vector entries reject. A capability/eligibility update stages a complete candidate and never changes accepted samples to repair an invalid set. A set excluding the accepted count rejects even if MSAA is disabled or controls are collapsed. Telemetry refresh changes neither capabilities nor settings.

Each live choice resolves its own fixed sample value through an ordinary command; an activation cannot supply another choice's value. `request_value("msaa", value, source)` resolves a typed node-free set request. Resolution checks numeric type, finite bounds, host eligibility and expanded controls; execution checks integral membership in {1,2,4,8} and the supported set before staging. A membership rejection enters the setting handler and consumes its sequence without publishing a candidate. Numeric range checking alone is insufficient. Do not coerce strings, Booleans or fractional values. Both routes share the existing executor and increasing sequence stream with disclosure and direct-strength operations, and recheck the accepted command/presentation at execution. Capability, eligibility or presentation replacement invalidates held requests; obtaining a fresh request uses the new accepted capability set. Unsupported and disabled choices cannot bypass rejection through node-free requests.

The host exposes accepted samples, capabilities and eligibility as owned observations. `setting_attempts()` includes entries into MSAA, direct-strength, outlines or scene-lights setting handlers. Rejection before host entry adds no handler attempt; a host-entered failed stage adds one attempt. `setting_changes()` counts successful operations that change an accepted setting value. Activating the accepted sample count adds one attempt and accepts one staged presentation but adds no value change. Disclosure, draft commands, telemetry and capability/eligibility updates add no setting attempt or change. These observations describe synthetic host requests, not GPU execution.

An MSAA operation changes only accepted samples. Preserve the exact direct-strength accepted value and draft bytes, selection, lifetime owner and revision, including incomplete or invalid text; changing MSAA neither parses nor canonicalizes that draft. Retain eligible focus by author ID and reveal it through ordinary scrolling. Collapsing controls while focus is inside controls recovers/reveals `disclosure-controls`; re-expansion retains header focus. Disabling a focused choice or removing it from capabilities uses ordinary focus recovery; other eligible focus retains its author identity. Collapse and capability/eligibility updates preserve both settings and the pending draft.

Stage samples, capabilities, eligibility and the unchanged numeric/disclosure state together with command observations, focus/offset, document/styles, layout, inspection and paint. Retain the accepted view through executor result validation. Returned measurement/paint failures preserve all accepted state and produce bounded located diagnostics. An entered setting command consumes its sequence even when staging fails; retry resolves a fresh request against the retained accepted presentation. A capability update has no setting-command side effect. Real device reconfiguration and acknowledgement require a separate renderer integration policy.

Pointer release, normalized keyboard/gamepad traversal or Navigate plus Activate, and semantic activation reach the same choice commands. Apply the shared panel/camera arbitration policy to supported and disabled choice hits and failed staging. A panel-claimed pointer stream remains consumed across capability/presentation replacement through release/cancel, while replacement cancels its pending activation. Recognized raw activation maps once; a consumed event cannot also operate the camera. Direct-strength editing keeps its existing key routing, and moving focus to MSAA does not commit a draft. No popup, shortcut, wheel or continuous-gesture policy is implied. The [fixture](../../tests/integrations/renderer_diagnostics_tests.cpp) verifies these boundaries separately from accepted-view replay reconstruction; the [copied main](../../examples/renderer-diagnostics/main.cpp) and [guide](../guides/renderer-diagnostics.md) show host use.

## Verification requirements

Declare initial snapshots, stable identities, available capabilities, bounded sample sequence, normalized inputs, clock, viewport/scale, shaper/fonts and capture backend under the [testing guide](../guides/testing.md). Verify:

- Text/inspection agrees with the supplied statistics, units, counter totals and unavailable/zero distinctions. Refreshing telemetry preserves focused control, disclosure/selection and valid scroll offsets without issuing setting commands.
- Expanded rows and the history plot agree with one accepted sample sequence. Small aligned tables preserve readable labels and values; clipping and scrolling agree across paint, hit testing and inspection. Keyboard/gamepad navigation reaches and reveals lower controls.
- Representative choices, toggles, numeric entry/adjustment and reset reach the same host operation through pointer, keyboard/gamepad and semantic routes. Invalid/non-finite/out-of-range values, unsupported choices, disabled owners and stale requests reject without changing accepted settings.
- Returned presentation errors retain accepted observations and host settings. Pending numeric input has a declared retention/cancellation policy during refresh and section collapse. Input consumed by the panel produces no camera request in the synthetic host arbitration check.
- Repeated accepted-view replay, semantic/layout/paint comparisons and selective CPU captures reproduce under declared inputs. State clearly whether replay executes the command host or reconstructs accepted replacement views; synthetic timings are fixture data, not performance measurements.
- Independent source consumption and affected checks run in Debug and Release. Native renderer/GPU/window integration needs its own evidence, including device/resource ownership and completion-safe submission; the core fixture does not establish hydra-toon migration or live GPU measurements.

Stop subsystem expansion when the promoted panel operations, coherent refresh, input and observation boundaries pass. Full ImGui feature parity, native window management, generalized tables/plots/virtualization, scene editing and renderer performance work are separate consumer decisions.
